## 1. System Classification

**System Type:** Hybrid (RAG-adjacent wiki + autonomous tool-use agent loop; Phase 2 scope is **reliability / tool-injection infrastructure** layered on the existing agent — not a new agent capability)

**Description:**
Aura is a **self-hosted, single-user personal second-brain assistant** — one Go binary that bundles a Telegram bot, an OpenAI-compatible LLM agent loop, a Markdown wiki under git, a Qdrant-backed vector memory, and an embedded React dashboard. The user (the project maintainer) talks to the bot from Telegram; the bot maintains the user's own notes, ingested PDFs, and scheduled tasks as durable, searchable, version-tracked Markdown pages. There is no third-party data, no multi-tenant boundary, no customer-facing surface. Phase 2 specifically delivers **reliability and tool-intelligence infrastructure** on top of the existing agent: an explicit `write_wiki_page` tool with optimistic-concurrency ETags (replacing brittle text-heuristic detection of LLM-emitted YAML), an error-classifying retry wrapper that escalates temperature only on content-validation failures (not on HTTP 429/5xx), an async slug-only reindex worker that decouples user-facing latency from Qdrant/embedding-API roundtrips, an `unversioned: true` audit flag on git-commit failure, and Qdrant-backed semantic tool retrieval (top-K=5 over an always-on core of 7) that replaces the deprecated `tool_search` tool. "Good" in this phase means: high reliability under provider flakiness (429 storms don't burn the temperature budget), zero silent wiki data loss (file write + git commit + reindex are all observable, with a dashboard badge whenever any of the three falls behind), low single-user cost (no LLM hops added to the happy path), and tool retrieval that surfaces the right tool on turn one without falling over when Qdrant is cold or down.

**Critical Failure Modes:**
1. **Silent wiki data loss** — `WritePage` succeeds (file is on disk), but `gitCommit` fails AND the reindex submission is dropped, AND the `Unversioned` badge round-trip is broken (D-17..D-20). The user thinks the page is saved; search and git history can't find it. This is the single highest-stakes failure path because the user's curated knowledge is the entire reason Aura exists.
2. **Concurrent-edit silent overwrite** — the LLM reads page X at `updated_at=T1`, the user manually edits via the dashboard at `T2 > T1`, the LLM later calls `write_wiki_page` carrying its stale `expected_updated_at=T1`, and the ETag check is skipped or evaluated outside the per-slug `fileMutex` critical section (D-01..D-05, PITFALLS.md #6). The user's edit is silently destroyed.
3. **Retry-budget burn on infrastructure blips** — the CONTENT-bucket policy fires on a transient HTTP 429 or `context.DeadlineExceeded`, escalating temperature `0 → 0.3 → 0.7` for no semantic reason and exhausting the 3-retry CONTENT budget on what should have been a single same-temperature TRANSIENT retry (D-06..D-08, PITFALLS.md #7). Wiki writes intended to be deterministic at `temperature=0` come back at `0.7`, the user pays 4× tokens, and the page that does eventually get written is structurally noisier than intended.
4. **Secret leakage through the classifier `cleaned` message** — `Classify(error)` pattern-matches on the raw provider error string, and the wrapper surfaces that raw string into a zap log unredacted (D-09, CLAUDE.md "Tool argument privacy"). URLs with bearer tokens, base64 image payloads, `Authorization:` headers, or API keys end up in `data/aura.log` — which is the user's filesystem, but is also what gets attached to a GitHub bug report or screenshotted in a community post. This is the single biggest reputational/trust violation for a self-hosted tool.
5. **Cold-start tool retrieval returns an empty toolset** — on the first turn after `/start` the conversation has only a system message; a naive `latestUser := messages[len(messages)-1]` returns the system prompt, Qdrant either matches randomly or returns nothing, and the LLM sees zero tools (D-22, D-23). The agent cannot call `write_wiki_page` or any other tool on turn one. The user's first interaction with the bot after restart looks like a regression even though the underlying retrieval is "working".

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Personal knowledge management (PKM) / self-hosted AI tooling — developer-tooling-adjacent. The closer practitioner reference points are Simon-Willison-style PKM-with-LLMs setups, NotebookLM-shaped RAG over a personal corpus, and self-hosted agent runtimes (LiteLLM gateways, local Ollama-fronted assistants). Aura is NOT in healthcare, legal, finance, customer service, or enterprise SaaS, and any rubric that imports the failure modes of those verticals would be evaluating the wrong system.

**User Population:** A **single user** — the project maintainer (Davide) — who is simultaneously the operator, the data owner, and the only consumer of outputs. Access is via Telegram (mobile-first conversational UX) and a small embedded React dashboard (desktop, for inspecting/editing wiki pages and reviewing maintenance queues). All data is the user's own notes, PDFs the user uploaded, and tasks the user scheduled. No third-party PII is processed. No federated/multi-tenant deployment is in scope. (If a future phase opens this to multiple users — see Phase 3+/v5 — the threat model and stakes change materially and this section must be re-researched.)

**Stakes Level:** **Medium overall — with one Critical sub-dimension.** Medium because the system is single-user and self-hosted: a failure does not page anyone, expose customer data, or create regulatory exposure; the worst happy-path failure is a degraded user experience (a wrong tool injected, a needless retry, a page not yet reindexed). Critical specifically for **secret leakage through the classifier `cleaned` message and tool-argument logs** — Aura runs against the user's real LLM API keys, real cloud secrets injected via `aura-secrets`, and an MCP surface that may carry tokens for third-party services; a single regex false-negative in the redactor is the single biggest trust violation a self-hosted tool can commit. Critical also for **silent wiki data loss** as the operator-facing trust contract — if the user can't trust that "I told Aura to remember X" actually persists to durable, version-tracked storage, the entire product proposition collapses.

**Output Consequence:** What happens downstream when each of Phase 2's outputs is acted on:
- A successful `write_wiki_page` tool result → a Markdown file at `WIKI_PATH/<slug>.md` is updated atomically, a git commit is attempted, a reindex `Job` is enqueued (non-blocking), and the LLM tool-call result JSON `{"status":"ok","slug":...,"updated_at":...}` is fed back into the next agent-loop turn. The user sees a Telegram reply summarizing the change; the dashboard reflects the new page within seconds (after the async reindex completes).
- A `conflict` tool result (D-03) → the LLM is expected to re-read the page via `search_memory`/`read_memory` and retry with the fresh `actual_updated_at`. The user does NOT see a raw error; the recovery happens inside the agent loop.
- A retry classification decision → determines whether the user pays 1× or up to 4× tokens for a single user turn, whether the wall-clock cost grows by 0s or up to ~5×30s of jittered backoff, and whether wiki writes stay at deterministic `temperature=0` or end up at `0.7` (the latter only legitimately when the LLM produced structurally invalid frontmatter).
- A tool injected on a turn → directly determines whether the LLM can satisfy the user's next request. Wrong tool selected = user repeats themselves; right tool selected = task completes silently.
- A reindex job processed (or dropped) → determines whether `search_memory` returns the latest page content. Drop-newest is safe because the worker re-reads from disk, but a *systematically* dropping queue (worker stopped, channel never drained) means the vector index lags arbitrarily behind the filesystem source of truth.

### Known Failure Modes in This Domain

These are domain-specific to a self-hosted Go agent runtime with an LLM-facing tool surface and an async indexing sidecar — drawn from PITFALLS.md (Phase 2 tagged), the Phase 1 carry-forward, and operational observations on similar self-hosted setups:

1. **Reindex worker goroutine leak on shutdown** (PITFALLS.md #4) — the drain goroutine sits in `select { case <-ctx.Done(): … case j := <-jobs: process(ctx, j) }`. If `Stop()` only closes `jobs` without cancelling `ctx`, an in-flight `ReindexWikiPage` (Qdrant call + embedding API call, each with their own ~30s timeouts) keeps the goroutine alive for up to 30s per pending job. Across N restarts, `runtime.NumGoroutine()` grows by ~1×N until memory exhaustion in long-running operator setups.

2. **Classifier "last writer wins" inside a single retry attempt** — both the TRANSIENT and CONTENT branches mutate `req.Temperature` (TRANSIENT preserves caller temp by re-assigning `callerTemp`; CONTENT escalates). If the wrapper code path conditionally writes one branch and falls through into the other, the second write wins and the temperature contract of D-08 is silently broken. Hard to spot in code review, easy to spot with a table-driven test.

3. **Channel double-close race in `Worker.Stop()`** (D-13) — the classic Go anti-pattern: producer (`wiki.Store`) holds a stale reference and is mid-`select { case w.jobs <- j: default: drop() }` while a shutdown goroutine calls `close(w.jobs)`. Result: `send on closed channel` panic that crashes the entire bot. Mitigation is structural (worker exclusively owns the channel; producers never close), not defensive.

4. **`internal/wiki/store.go` god-class growth** — currently 755 LOC, over the 600-LOC hard rule already; the soft ceiling for this phase is 800. Adding `expected_updated_at` checking + `Unversioned` set/clear logic + reindex submission glue is on track to push it past 800 if the developer follows the path of least resistance and adds everything in `store.go`. The PR will ship "working" but in violation of CLAUDE.md.

5. **Cold-start tool injection returns an empty toolset** (D-23) — `latestUser := messages[len(messages)-1]` returns the system message on turn one after `/start`, Qdrant either matches randomly or returns nothing, and the agent loop's `Tools` slice is empty for the entire first user turn. The bot replies with an apology that "I can't do that right now" and the user reasonably concludes Aura is broken.

6. **Provider-specific error messages slipping past the OpenAI-compatible classifier** — Anthropic-style "thinking signature mismatch" errors, OpenRouter "policy block" responses, and Cerebras-style streaming-truncation errors don't match the OpenAI / OpenAI-compatible patterns Phase 2 covers. They classify as `BucketPermanent` (no retry) when they should be `BucketTransient` or `BucketContent`. CONTEXT.md explicitly defers provider-specific extensions, but the failure mode is real and must be flagged in production sampling.

7. **Secret-redactor regex false-negative** — the redactor strips `?api_key=`, `Bearer `, `https://...:...@host`, base64 over a length threshold, and `Authorization:` headers. It does NOT (today) strip OpenRouter-style `sk-or-v1-...` API keys appearing as bare tokens in error narratives, AWS pre-signed URL signatures, or JWT tokens carrying user-identifying claims. A single regex miss in the classifier's `cleaned` output is the biggest trust failure in this codebase.

8. **`select/default` Submit silently drops after `Stop()`** — `select { case ch <- v: default: drop() }` is correct ONLY when the worker is alive. After `Stop()` the worker has exited, the channel buffer fills, every Submit hits `default` and "drops" — but those drops are post-shutdown, which is operationally distinct from queue-full drops. Without a `Stopped()` atomic flag plus a separate `reindex_dropped_after_stop` counter (D-16), a shutdown-time backlog is invisible.

### Regulatory / Compliance Context

**None identified — single-user, self-hosted, user's own data.** Aura is run by the operator on their own hardware (or their own VPS), against their own LLM provider account, persisting their own notes. No third-party PII is processed. The **GDPR personal/household-use exemption applies** (Recital 18 / Art. 2(2)(c)) — the user is processing personal data exclusively in the course of a personal activity, on systems they administer, with no commercial or shared-controller dimension. No HIPAA, no SOC 2, no PCI-DSS, no FCA, no GLBA — none of these regimes have a hook into this deployment context, and inventing them in a rubric would be evaluating the wrong system.

**Forward note:** if a future roadmap phase opens Aura to multiple users (shared hosting, federated deployment, or a managed offering), the picture changes materially — secret-isolation, per-tenant data boundaries, log-PII handling, and possibly GDPR controller obligations all become live concerns. That is explicitly out of scope for v4.0 / Phase 2 and must be re-researched at that future inflection point.

## 2. Framework Decision

**Selected Framework:** `custom-llm-client-go` — in-tree extension of `internal/llm.Client` + Go stdlib concurrency

**Version:** N/A (in-tree code; key external pins: `github.com/go-git/go-git/v5 v5.19.0` per D-21, existing Qdrant HTTP client from Phase 1, `go.uber.org/zap` for structured logging)

**Rationale:**
Phase 2 is reliability infrastructure on an existing Go binary that already owns its OpenAI-compatible LLM client interface (`internal/llm.Client`), tool registry (`internal/tools/registry.go`), Qdrant integration (`internal/qdrant/`), and agent loop (`internal/agentloop/`). The work — classify-then-retry wrapper, slug-only async reindex worker, optimistic-concurrency `write_wiki_page` tool, Qdrant-backed tool retrieval — extends shapes that already exist. CONTEXT.md decisions D-29..D-32 lock package layout (`internal/reindex/`, `internal/llm/classify.go`, `internal/tools/wiki.go`) and explicitly forbid umbrella packages. REQUIREMENTS.md "Out of Scope" bans worker-pool libraries. Every cataloged agent framework (LangChain, LangGraph, CrewAI, Claude Agent SDK, OpenAI Agents SDK, AutoGen, LlamaIndex, Haystack) is Python/TS/Java/.NET — none target Go. A framework swap would violate SCOPE CONTROL, FOLLOW EXISTING PATTERNS, and the god-class rule simultaneously.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangChain / LangGraph / CrewAI / Claude Agent SDK / OpenAI Agents SDK / AutoGen / LlamaIndex / Haystack | Wrong language ecosystem (Python/TS/Java/.NET — no first-class Go SDK that fits). Wrong layer of change (Phase 2 is reliability infra, not agent orchestration). Would require gutting and rewriting `internal/agentloop`, `internal/llm`, and `internal/tools`, violating "composition-only changes around `agentruntime/agentloop`" carry-forward from Phase 1. |
| OpenTelemetry instrumentation library (`go.opentelemetry.io/otel`) | Could be added at the LLM-wrapper observability layer, but **out of scope** for Phase 2 — the production-monitoring/tracing decisions are deferred and `internal/logging` (zap) already provides structured logging. ### Common Pitfalls

These are drawn from `D:\Aura\.planning\research\PITFALLS.md` (verified Phase-2-tagged) and from gaps the planner specifically called out in this brief. Each is specific — no generic "use async where supported" entries.

1. **Reindex worker goroutine leak on shutdown** (PITFALLS.md #4). The drain goroutine sits inside `select { case <-w.ctx.Done(): return; case j := <-w.jobs: w.process(w.ctx, j) }`. If `Stop()` only closes `w.jobs` without cancelling `w.ctx`, an in-flight `ReindexWikiPage` (which calls Qdrant + the embedding API, both with their own 30s timeouts) keeps the goroutine alive for up to 30 seconds per pending job. **Fix:** the worker owns a dedicated `ctx, cancel := context.WithCancel(parent)` and `Stop()` calls `cancel()` first, then waits on a `done chan struct{}` closed by the goroutine on exit. NEVER close the jobs channel from outside the worker — let GC reclaim it (D-13).

2. **Tool-write vs. dashboard-edit silent overwrite** (PITFALLS.md #6). The per-slug `fileMutex` in `wiki.Store` prevents file *corruption* but not stale-write *data loss*. The LLM reads page X at `updated_at=T1`, the user edits via the dashboard at `T2 > T1`, the LLM calls `write_wiki_page` carrying its stale `expected_updated_at=T1` — without an ETag check, the user's edit is silently overwritten. **Fix:** `WritePage` compares `expected_updated_at` against the on-disk `updated_at` INSIDE the existing `fileMutex(slug)` critical section, returning the structured conflict JSON of D-03 so the LLM can re-read and retry deterministically (D-01..D-05).

3. **Temperature staircase burned on infrastructure failures** (PITFALLS.md #7). The current `RetryClient` retries blindly on any error. If retries escalated temperature (0 → 0.3 → 0.7) on HTTP 429 or context timeout, every concurrent user pays 3× the LLM cost during a provider blip and still fails. **Fix:** the wrapper escalates temperature ONLY on the CONTENT bucket; TRANSIENT preserves the caller's `Request.Temperature` (so wiki writes stay at 0 across retries), and PERMANENT exits immediately with zero retries (D-06..D-08).

4. **Classifier `Message` field leaking secrets into logs** (D-09 + CLAUDE.md "Tool argument privacy"). The Hermes classifier's pattern-match step inspects the raw error string. If the wrapper surfaces that raw string into the zap log unredacted, URLs with bearer tokens, base64 image payloads, and API keys can leak. **Fix:** `Classify` returns a `cleaned` message run through the same redactor used by `internal/logging` (URL-token strip, base64 truncate, `Authorization:` header strip) BEFORE any zap field is set. Pattern matching runs on the raw string in-memory; only the cleaned variant ever escapes the function.

5. **Buffered channel double-close race** (D-13). The classic Go anti-pattern: producer (`wiki.Store`) calls `close(jobs)` on shutdown while a stale `Submit` still holds a reference. **Fix:** the channel is owned exclusively by the worker; no caller closes it. Producers send via `select { case w.jobs <- j: default: log.Warn("reindex_dropped_total"); return false }`. The worker exits on `ctx.Done()` and the channel is GC-reclaimed when the last submitter releases its reference.

6. **`internal/wiki/store.go` god-class threshold** (CLAUDE.md "GOD CLASS" rule + `<specifics>` in CONTEXT.md). The file is **755 LOC today** (verified via `wc -l`); the rule is "no file >600 LOC" and the soft ceiling for this phase is 800. Adding `expected_updated_at` checking + `Unversioned` flag set/clear logic + reindex submission glue will push past 800. **Fix:** factor a sibling file `internal/wiki/store_writes.go` (same package, no API change) holding `WritePage`, `DeletePage`, the new `unversioned` helpers, and the reindex enqueue — keep `store.go` as construction + reads + git plumbing. Same package; new file only.

7. **Cold-start tool retrieval returns an empty toolset** (D-23). The retrieval query is "the latest user message" — but on the very first turn after `/start`, the conversation only has a system message. A naive `latestUser := messages[len(messages)-1]` returns the system prompt, which Qdrant matches randomly or returns nothing. The agent then sees no tools at all and can't call `write_wiki_page`. **Fix:** the `ToolsProvider` closure detects "no user message yet" and returns the always-on **core (7) only** — never an empty toolset (D-22, D-23). Same fallback as Qdrant-down (D-25).

8. **`select/default` Submit appears to drop but actually races** (PITFALLS.md "Channels are not queues"). The pattern `select { case ch <- v: default: drop() }` is correct ONLY when the worker is the sole receiver and is alive. If the worker has already exited (e.g., during shutdown), Submit silently drops every job. **Fix:** the worker reports `Stopped()` via an atomic flag; `Submit` checks the flag first and logs `reindex_dropped_after_stop` distinctly so a shutdown-time backlog is observable in `Worker.Health()` (D-16).

## 4. Implementation Guidance

**Model Configuration:**

Phase 2 is **model-agnostic infrastructure** — the LLM is configured at runtime via `internal/settings`, not hard-coded here. What this phase pins is the *temperature contract* between the wrapper and its callers:

| Path | First-attempt `Request.Temperature` | On TRANSIENT retry | On CONTENT retry | Notes |
|------|------------------------------------|--------------------|------------------|-------|
| `write_wiki_page` tool execution | `Float64Ptr(0)` (deterministic, existing convention) | preserve `0` (D-08) | escalate `0.0 → 0.3 → 0.7` (D-07) | Wiki writes stay deterministic on the happy path; temperature climbs only when the LLM produces invalid frontmatter or wiki-link syntax. |
| Chat / agent loop turn | `nil` (provider default) | preserve `nil` | escalate by writing `Float64Ptr(0.3)` etc. | Caller intent (`nil` = "let the API decide") is preserved across TRANSIENT retries (D-08). |
| Streaming token consumption | unchanged from Phase 1 | n/a | n/a | Streaming retry only applies to the initial connection error, not mid-stream — see `Stream()` semantics in `internal/llm/client.go`. |

Other parameters (`Model`, `Tools`, `Messages`) are set by callers exactly as today; the wrapper does NOT mutate them. The `Tools` slice on each turn is built by the per-turn `ToolsProvider` closure (D-28). The embedding model uses the separate `EMBEDDING_BASE_URL` / `EMBEDDING_API_KEY` endpoint with no fallback to chat credentials (existing convention from `internal/llm`).

The retry wrapper's inner loop, written for clarity:

```go
// internal/llm/retry.go (rewritten — sketch)
func (r *ClassifyRetryClient) Send(ctx context.Context, req Request) (Response, error) {
    callerTemp := req.Temperature
    contentAttempt := 0
    transientAttempt := 0
    var lastErr error

    for {
        resp, err := r.inner.Send(ctx, req)
        if err == nil {
            return resp, nil
        }
        lastErr = err

        bucket, retryable, cleanedMsg := Classify(err) // D-09
        r.logger.Warn("llm_call_failed",
            slog.String("bucket", bucket.String()),
            slog.Bool("retryable", retryable),
            slog.String("message", cleanedMsg))         // PRE-redacted (D-09)

        switch bucket {
        case BucketPermanent:
            return Response{}, err                     // D-07: zero retries
        case BucketTransient:
            if !retryable || transientAttempt >= r.maxTransient {
                return Response{}, lastErr
            }
            // Preserve caller temp (D-08); jittered backoff (D-07).
            req.Temperature = callerTemp
            d := jitteredBackoff(transientAttempt, r.baseDelay, r.maxDelay, r.jitterRatio)
            transientAttempt++
            select {
            case <-ctx.Done():
                return Response{}, ctx.Err()
            case <-time.After(d):
            }
        case BucketContent:
            if contentAttempt >= len(r.contentTemperatures) {
                return Response{}, lastErr
            }
            // Override temperature ONLY on CONTENT (D-08).
            t := r.contentTemperatures[contentAttempt]
            req.Temperature = &t
            // Append validation-error nudge as a system-style follow-up (D-07).
            req.Messages = appendValidationNudge(req.Messages, cleanedMsg)
            contentAttempt++
            // No backoff: content failures aren't throughput-related.
        }
    }
}
```

```go
        "properties": map[string]any{

    }
}

func (t *WriteWikiPageTool) Execute(ctx context.Context, args map[string]any) (string, error) {
    title, _ := args["title"].(string)
    body, _ := args["body"].(string)
    expected, _ := args["expected_updated_at"].(string) // empty string is a valid sentinel (D-02)

    page := &wiki.Page{
        Title:         title,
        Body:          body,
        Category:      stringArg(args, "category"),
        Tags:          stringSliceArg(args, "tags"),
        Related:       stringSliceArg(args, "related"),
        Sources:       stringSliceArg(args, "sources"),
        SchemaVersion: wiki.CurrentSchemaVersion,
        PromptVersion: "v1", // tool-write provenance
        // CreatedAt / UpdatedAt are set inside store.WritePage; the LLM does NOT control them (D-01).
    }

    if err := t.store.WritePage(ctx, page, expected); err != nil {
        // Structured conflict result (D-03) — JSON the LLM can parse deterministically.
        var conflict *wiki.ConflictError
        if errors.As(err, &conflict) {
            payload, _ := json.Marshal(map[string]string{
                "error":               "conflict",
                "slug":                conflict.Slug,
                "expected_updated_at": conflict.Expected,
                "actual_updated_at":   conflict.Actual,
            })
            return string(payload), nil // tool RESULT, not tool ERROR — LLM sees the JSON
        }
        return "", err // schema/IO errors propagate as tool errors (CONTENT-bucket on retry)
    }

    if t.submitter != nil {
        _ = t.submitter.Submit(reindex.Job{Slug: wiki.Slug(title), Op: reindex.OpUpsert})
    }
    return fmt.Sprintf(`{"status":"ok","slug":%q,"updated_at":%q}`, wiki.Slug(title), page.UpdatedAt), nil
}
```

| What | Where | How updated |
|------|-------|-------------|
| Wiki page content | Filesystem (`WIKI_PATH`/`<slug>.md`) — Markdown body + YAML frontmatter | Atomic temp+rename inside `fileMutex(slug)`; existing pattern unchanged. |

| Reindex queue state | In-memory `chan reindex.Job` (cap 100) — never persisted | Drop-newest on full (D-12). Lost-on-restart is acceptable because the next wiki write to that slug re-enqueues, and a maintenance "reindex everything" job already exists in `internal/api/maintenance`. |

| LLM retry counters | Per-call locals in the wrapper — never shared across calls | Each `Send`/`Stream` invocation gets a fresh `transientAttempt`/`contentAttempt` pair. The wrapper is stateless across requests (no rate-limit memory) — that's a Phase 3 concern (LLM-03 circuit breaker). |

**Context Window Strategy:**

Phase 2's context-window concern is **the prompt**, not the conversation buffer. Conversation history is already managed by the existing 50-message sliding window in `internal/conversation/` and is **out of scope** here.

The new constraint is the *tool definitions* portion of the prompt:

| Component | Per-turn budget | Source |
|-----------|----------------|--------|
| Always-on core tools | exactly 7 definitions | hard-coded list (D-22) |
| Retrieved supplemental tools | top-K=5 (cap) | Qdrant semantic match against the latest user message (D-22, D-23) |
| **Total tool definitions injected** | **≤ 12** | composition in the per-turn `ToolsProvider` closure |

Retrieval rules (verbatim from CONTEXT.md):

- **Query is the LATEST USER MESSAGE only** — single-step retrieval per arXiv 2511.01854. NOT the full conversation, NOT the last N turns. Embeddings are name+description only — no examples (D-24).
- **Cold-start (no user turn yet)** → core (7) only. Never an empty toolset (D-22, D-23).
- **Qdrant down or zero-doc index** → inject the FULL toolset and log degraded mode at WARN (D-25). Never fail the turn because retrieval failed.
- **Fallback hierarchy in code:** `retrieved, err := index.SearchTopK(ctx, latestUserMsg, 5); if err != nil || len(retrieved) == 0 { return registry.Definitions() /* full set */ }; return dedupAndAppend(coreDefs, retrieved)`.

Why this works inside the existing 50-turn buffer: the tool-definitions block is a *header* on every turn, so a 12-cap is a flat overhead independent of conversation length. The 50-turn sliding window plus a 12-tool header fits well inside any modern LLM's input budget at the model sizes Aura targets.

## 4b. AI Systems Best Practices

> Cross-cutting Go patterns every developer touching this phase needs — translated from the Python/Pydantic-flavored template into the Go-native idiom Aura uses.

### Structured Outputs with Pydantic

The Pydantic-equivalent in Go is the **tagged struct + JSON Schema returned from `Tool.Parameters()` + post-execute validation**. There is no Python "model that validates on construction" — instead, the registry validates the tool-call arguments BEFORE `Execute` runs, and the LLM's response (when it carries tool-call args) is structurally checked by the same JSON Schema the LLM was shown. Re-validation on retry is the CONTENT bucket's job (D-06).

The shape mirrors `D:\tmp\picobot\internal\agent\tools\write_memory.go`: a Go struct holds the canonical fields, `Parameters()` returns the JSON Schema the LLM sees, `Execute()` extracts and re-validates from `map[string]any` (defensive — providers occasionally send extra keys or wrong types).

```go
// internal/tools/wiki.go — Go-native equivalent of a Pydantic write_wiki_page model

// Args is the canonical Go shape. Populated by extracting from the LLM-provided
// map[string]any inside Execute(). The `json:` tags also drive the dashboard
// passthrough (api/wiki.go) so client and server share one source of truth.
type WriteWikiPageArgs struct {
    Title             string   `json:"title"`
    Body              string   `json:"body"`
    ExpectedUpdatedAt string   `json:"expected_updated_at"`           // empty == create-only (D-02)
    Category          string   `json:"category,omitempty"`
    Tags              []string `json:"tags,omitempty"`
    Related           []string `json:"related,omitempty"`
    Sources           []string `json:"sources,omitempty"`
}

// Validate is the Pydantic-equivalent post-extract check. Returns a sentinel
// the classifier maps to BucketContent so the retry wrapper escalates
// temperature on re-attempt (D-06).
func (a *WriteWikiPageArgs) Validate() error {
    var errs []string
    if a.Title == "" { errs = append(errs, "title required") }
    if a.Body == "" { errs = append(errs, "body required") }
    // expected_updated_at can be empty (sentinel) but cannot be missing.
    // RFC3339 shape check ONLY when non-empty — empty is a valid sentinel.
    if a.ExpectedUpdatedAt != "" {
        if _, err := time.Parse(time.RFC3339, a.ExpectedUpdatedAt); err != nil {
            errs = append(errs, "expected_updated_at must be RFC3339 or empty string")
        }
    }
    if len(a.Tags) > 10 { errs = append(errs, "tags exceeds 10") }
    if len(errs) > 0 {
        return fmt.Errorf("%w: %s", llm.ErrSchemaValidation, strings.Join(errs, "; "))
    }
    return nil
}
```

**How the framework integrates the schema** (Go-native answer to "LangChain `.with_structured_output()`"):
1. `Tool.Parameters() map[string]any` returns the JSON Schema fragment to the LLM via `Registry.Definitions()`. The LLM sees it inside the `tools` array of the request.
2. The provider streams back tool-call argument fragments. `internal/llm/client.go` accumulates them in the streaming parser; consumers receive a fully-formed `ToolCall.Arguments map[string]any` only on `Token.Done=true`.
3. `Registry.Execute(ctx, name, args)` dispatches to `Tool.Execute`. Inside, the tool extracts to its typed struct and calls `Validate()`. A validation failure returns `llm.ErrSchemaValidation` — recognized by `Classify()` and bucketed as CONTENT (D-06).
4. The `ClassifyRetryClient` re-invokes the call with `Temperature` advanced along the staircase `0.0 → 0.3 → 0.7` (D-07) and a system-style nudge appended:
   `{Role: "system", Content: "Previous tool-call arguments failed validation: <cleaned>. Retry with corrected output."}`
5. After `MaxContentRetries=3` (D-07) the wrapper surfaces the original error to the caller. Logging at every step uses `bucket=content` and `attempt=N` zap fields so dashboards can plot CONTENT-retry rates separately from TRANSIENT.

What gets logged: the tool name, the **argument keys** (already redacted by `argKeys` in `internal/tools/registry.go:271`), the validation error message (via `Classify`'s redactor), the bucket, the attempt number. NEVER the argument values, NEVER the LLM's raw output (which may carry quoted user content), NEVER the raw error string from the provider (which may carry URLs with tokens).

### Async-First Design

Go's async story is goroutines + channels + `context.Context`. The Phase 2 reindex worker is the canonical shape — copy it for any future async work.

**The pattern (D-13, mirrors `internal/conversation.BufferedAppender`):**

```go
// internal/reindex/worker.go (sketch)
type Worker struct {
    jobs      chan Job
    reindexer search.WikiPageReindexer

    ctx    context.Context
    cancel context.CancelFunc
    done   chan struct{}

    droppedTotal atomic.Int64
    stopped      atomic.Bool
    logger       *slog.Logger
}

func NewWorker(cfg Config) *Worker {
    ctx, cancel := context.WithCancel(context.Background())
    return &Worker{
        jobs:      make(chan Job, cfg.QueueSize),
        reindexer: cfg.Reindexer,
        ctx:       ctx,
        cancel:    cancel,
        done:      make(chan struct{}),
        logger:    cfg.Logger,
    }
}

func (w *Worker) Start() { go w.drain() }

// Submit is non-blocking. drop-newest on full (D-12).
func (w *Worker) Submit(j Job) bool {
    if w.stopped.Load() {
        w.logger.Warn("reindex_dropped_after_stop", slog.String("slug", j.Slug))
        return false
    }
    select {
    case w.jobs <- j:
        return true
    default:
        w.droppedTotal.Add(1)
        w.logger.Warn("reindex_dropped_total", slog.String("slug", j.Slug))
        return false
    }
}

// Stop cancels the worker context (cancels in-flight reindex), waits for
// the goroutine to exit, and only then returns. Safe to call once.
func (w *Worker) Stop() {
    w.stopped.Store(true)
    w.cancel()  // cancels in-flight ReindexWikiPage Qdrant + embedding calls (D-13)
    <-w.done    // wait for drain goroutine to actually exit
    // NEVER close(w.jobs) — let GC reclaim it after the last Submitter releases.
}

func (w *Worker) drain() {
    defer close(w.done)
    for {
        select {
        case <-w.ctx.Done():
            return
        case j := <-w.jobs:
            // Pass w.ctx (NOT context.Background) so Stop cancels in-flight work.
            if err := w.reindexer.ReindexWikiPage(w.ctx, j.Slug); err != nil {
                w.logger.Warn("reindex_failed", slog.String("slug", j.Slug), slog.Any("error", err))
            }
        }
    }
}
```

**The one common mistake — closing the channel from the producer side.** A wiki write happens, `wiki.Store` calls `submitter.Submit(...)`, then someone "helpfully" tries to `close(w.jobs)` during shutdown. Race: if a producer is mid-`select` while another goroutine closes the channel, you get a `send on closed channel` panic that crashes the whole bot. **Fix:** the channel is owned exclusively by the worker; producers never close it; the worker exits on `ctx.Done()` and the channel is GC-reclaimed when the last submitter goes out of scope. This is also why `Stop()` cancels the context BEFORE waiting on `done` — it lets the in-flight `ReindexWikiPage` call return promptly instead of running its full 30s embedding timeout.

**Stream vs. await analog:** Go has only one shape — synchronous calls inside goroutines. The streaming-vs-await split in Python collapses to:
- `llm.Client.Stream` returns `<-chan Token` — read it for live UX (Telegram progressive edits in `internal/telegram/streaming.go`).
- `llm.Client.Send` returns `(Response, error)` — use it when you need the full structured-output JSON before acting (e.g., validation in the CONTENT-retry loop). Streaming a tool call's argument fragments works because the parser accumulates them, but the validator must wait for `Done=true` before deciding whether to retry.

### Prompt Engineering Discipline

**System vs. user separation.** The agent's persona and tool-use rules live in the prompt overlays loaded every turn from `PROMPT_OVERLAY_PATH` (`SOUL.md`, `AGENTS.md`, `USER.md`, `TOOLS.md` — see CLAUDE.md "Key Conventions"). Phase 2 does NOT add a new overlay. Instead:

- The `WriteWikiPageTool.Description()` (D-04) is the contract documentation for the LLM. Treat it like a one-paragraph prompt — version it intentionally; review it like code. The exact wording is locked by D-04: "Always read the page first to obtain `updated_at`; pass `expected_updated_at=''` only when creating; on conflict, re-read and retry."
- The CONTENT-retry nudge (D-07) is itself a prompt fragment. Version it (a constant in `internal/llm/classify.go`) and never let the raw provider error string leak into it — only the redacted `cleaned` message.
- Tool definitions are NEVER hand-edited in the prompt. They flow from `Registry.Definitions()` → `ToolsProvider()` → `Request.Tools`. The LLM sees the schema; the schema is the prompt.

**Few-shot vs. dynamic retrieval.** Tool retrieval is dynamic (D-22). Few-shot examples are NOT embedded into the tool index (D-24) — name+description is sufficient and keeps the embedding budget cheap. If a future phase adds in-context examples, they belong on a per-tool basis inside the description string (still embedded as one document), not as a separate "examples" field. This matches the Red Hat 2025-11-26 Tool-RAG finding.

**`max_tokens`.** The existing `internal/llm.Request` does not carry an explicit max-tokens field — providers default to a sensible cap. Phase 2 does not change this. The CONTENT-retry path is bounded by `MaxContentRetries=3` (D-07), and the TRANSIENT-retry path by `MaxRetries=5`, so the wrapper itself caps total token spend at `(1 + 3 + 5) × per-call-budget` per user turn in the worst case. Add explicit max-tokens only if a future provider integration shows runaway completions; it's deferred for now and the per-call wrapper bounds are the production safety net.

### Context Window Management

Two scopes — keep them separate:

**Tool-definitions header (Phase 2 introduces this).** Cap is 12 (7 core + top-K=5, D-22). Embedding strategy is name+description only (D-24). The retrieval query is the latest user message string (D-23). Cold-start and Qdrant-down both fall back to a non-empty toolset — core-only on cold start, FULL on Qdrant-down (D-22, D-25). The 12-tool cap is a flat overhead independent of conversation length, so it does not interact with the 50-turn buffer.

**Conversation history (out of scope for Phase 2 — DO NOT touch).** The existing 50-message sliding window in `internal/conversation` already handles this. Summarisation/compaction is a Phase-3+ concern (mentioned in research SUMMARY.md but not requirement-tagged). If a future phase needs compaction, the natural insertion point is between conversation reading and request building inside `internal/agentloop/loop.go` — not inside the LLM wrapper.

**RAG-style truncation.** The `search_memory` and `read_memory` tools already truncate result bodies; reranking is implicit in `Registry.Search`'s lex+vector blend (`internal/tools/registry_search.go`). Phase 2 changes nothing here.

### Cost and Latency Budget

**Per wiki-write turn (the new hot path):**

- 1 LLM call to decide to call `write_wiki_page` (chat path, may stream).
- 1 file write + 1 git commit attempt — both **synchronous to the user** (low ms; no network).
- 1 reindex enqueue — **non-blocking; returns immediately** (D-12).
- 0 LLM calls and 0 Qdrant/embedding calls on the user-facing critical path. The wiki-write tool returns as soon as the file is on disk.

The reindex worker amortizes the embedding/Qdrant cost asynchronously. The `EmbedCache` in `internal/search/embed_cache.go` makes repeated reindex of the same content effectively free (SHA-keyed cache hit). Drop-newest is safe because the worker re-reads from disk (D-11) — Qdrant always converges to the latest snapshot, even if N intermediate writes drop their submit signals.

**Per LLM-call worst case under retry:**

| Bucket | Max additional calls beyond first | Token-cost multiplier (vs. first attempt) | Wall-clock added |
|--------|------------------------------------|-------------------------------------------|------------------|
| TRANSIENT (HTTP 429, 5xx) | 5 (D-07) | 1× per attempt | sum of jittered backoffs, capped at ~5× 30s with jitter |
| CONTENT (schema fail) | 3 (D-07) | up to 3× (each retry replays the request + appends one nudge message) | minimal — no backoff, just provider RTT |
| PERMANENT (401/403/400) | 0 (D-07) | 0 | 0 |

The CONTENT-bucket worst case (4× the per-call cost) is the dominant cost driver. The temperature staircase 0.0 → 0.3 → 0.7 (D-07) is biased to fail FAST on the second attempt if the model's output is structurally broken — temperature 0.3 typically resolves frontmatter formatting issues that 0.0 produced deterministically. Expect ~95% of write_wiki_page calls to succeed on attempt 1, with a long tail on 2.

**Caching.** Two existing caches stay in scope:
1. **Embedding cache** (`internal/search/embed_cache.go`) — SHA-keyed, content-addressed. Reindex of an unchanged page is a cache hit and skips the embedding API entirely. This is what makes the worker's "rebuild on every reindex" cost-acceptable in Phase 2 (D-15) — incremental upsert is a deferred optimization.
2. **Qdrant warm cache** (Phase 1, QDRANT-01) — `points_count > 0` short-circuits the boot-time index rebuild. The tool-vector index inherits the same pattern (D-26).

There is no exact-match cache on chat completions and there should not be — chat replies are temperature-conditioned and per-user. Adding one is a Phase-3+ topic.

**Cheaper models for sub-tasks.** The classifier and the ToolsProvider closure run **without an LLM** — pure Go pattern matching for `Classify` (Hermes-style, D-09), pure Qdrant similarity for retrieval (D-24). No "router LLM" is introduced. This is intentional: every LLM hop is a cost+latency multiplier, and Phase 2 adds zero new LLM hops on the happy path.

### Eval Tooling

**Primary tool: `go test -race ./...` — the existing test discipline.**

Phase 2's eval suite is an **extension of the existing Go test convention**, not a new framework. Every dimension above except #12 (LLM judge for CONTENT-retry nudge) is a Go-level invariant that a table-driven test verifies deterministically. Proposing RAGAS / Promptfoo / DeepEval here would be miscasting Go bugs (classifier misclassification, channel-shutdown semantics, regex coverage) as LLM output drift — they are not.

**Why no RAGAS / Promptfoo / DeepEval:**
- RAGAS targets free-form RAG answers (faithfulness, answer relevance over generated text). Phase 2's "RAG-adjacent" surface is the wiki itself, but the wiki *content* is already produced and validated by Phase 1 + the existing ingestion pipeline. Phase 2 only changes *how the LLM commits a write* (a Go-level concern: ETag, retry, reindex enqueue) — none of which RAGAS evaluates.
- Promptfoo is a CLI prompt-regression harness for prompt-tuning workflows. There is exactly one Phase 2 prompt fragment that needs versioning: the CONTENT-retry nudge. A 6-8-example LLM judge (dimension #12) at quarterly cadence is the right scale; standing up a Promptfoo runner for one prompt fragment is overhead with no payoff.
- DeepEval is Python; the production runtime is Go-only.

**Setup (no new dependencies):**

```bash
# Phase 2 evals run inside the existing Go test toolchain.
# No installs, no platform accounts, no Docker sidecars beyond what already exists.
go test -race ./internal/llm/         # dimensions 1, 2, 3, 9, 13
go test -race ./internal/reindex/     # dimension 6
go test -race ./internal/tools/       # dimensions 4, 7, 8
go test -race ./internal/wiki/        # dimensions 5, 10
go test       ./internal/...          # dimension 11 (godclass scan; no race needed)
```

**Tool-retrieval fixture infrastructure** (dimension 7 — the only piece of infrastructure new to Phase 2 evals):

```
internal/tools/testdata/
└── retrieval_fixture.jsonl    # 15 lines, hand-labeled by the maintainer
```

Each line: `{"prompt":"<latest user message>","expected":"<supplemental tool name>"}`. The test harness boots the existing Qdrant test container (already used in Phase 1 search tests), populates the tool-vector index from the live `Registry`, and runs `Search(ctx, prompt, 5)` against each fixture line. No external eval platform involved.

**CI/CD Integration:**

```bash

```

**Tracing for offline eval analysis:** structured zap logs already emitted by the wrapper (`bucket=…`, `attempt=…`, `slug=…`, `tool_count_total=…`, `tool_count_retrieved=…`) — see Section 7. Offline batch analysis reads `data/aura.log`; no separate eval trace store is introduced in Phase 2.

**Composition (what the dataset deliberately exercises):**
- **Critical paths:** clean wiki write, clean retry-then-succeed, cold-start tool injection, normal Qdrant retrieval.

## 7. Production Monitoring

### Tracing Tool

**Recommendation: structured zap logs (`internal/logging`) with OTLP-compatible field shapes — defer Arize Phoenix as a future-friendly upgrade, do NOT pin it for Phase 2.**

The GSD default is Arize Phoenix; this is a deliberate deviation, justified by:

1. **Single-user, self-hosted Go binary in Docker.** Phoenix is an OTLP collector + UI server; adding it means another service in `compose.yaml`, another port, another set of credentials, another database/storage backend, and another moving piece for the *single user* to operate. The marginal value of a trace-visualization UI for a one-person debugging surface is low — `data/aura.log` plus `docker compose logs -f aura` already gives the maintainer everything they need.
2. **No Python in production.** Phoenix's strongest integrations are with Python LLM frameworks (LangChain, LlamaIndex). Aura is Go-only at runtime. The Go OTLP path works but adds complexity for capability the maintainer hasn't asked for.
3. **`internal/logging` (zap) already exists** and already enforces the redactor convention (D-09, CLAUDE.md "no secrets in logs"). Re-shaping the new Phase 2 fields as structured zap entries is zero new infra.

**Forward-compatible shape — what Phase 2 emits now:**

```go
logger.Warn("llm_call_failed",
    slog.String("trace_id", traceID),       // request-scoped UUID, propagated through retries
    slog.String("bucket", bucket.String()), // transient | content | permanent
    slog.Int("attempt", contentAttempt+transientAttempt),
    slog.String("provider", req.Model),     // e.g. "openai/gpt-4o-mini"
    slog.String("message", cleanedMsg),     // PRE-REDACTED (D-09)
)

logger.Info("write_wiki_page_executed",
    slog.String("trace_id", traceID),
    slog.String("slug", slug),
    slog.String("op", "upsert"),            // upsert | conflict | create_only_rejected
    slog.Bool("expected_supplied", expected != ""),
    slog.Bool("unversioned_after", page.Unversioned),
)

logger.Info("tools_provider_invoked",
    slog.String("trace_id", traceID),
    slog.Int("tool_count_total", 7+len(retrieved)),
    slog.Int("tool_count_retrieved", len(retrieved)),
    slog.String("fallback_reason", fallbackReason), // ""|"cold_start"|"qdrant_down"|"empty_on_user_turn"
)

logger.Warn("reindex_dropped_total",
    slog.String("trace_id", traceID),
    slog.String("slug", slug),
    slog.String("reason", "queue_full"),     // queue_full | after_stop
)
```

These field names are deliberately the **exact shape** an OTLP span would carry — `trace_id`, `bucket`, `attempt`, `provider`, `slug`, `op`, `tool_count_*`, `reason`. If/when the maintainer wants Phoenix (or Langfuse, or any OTel-compatible collector), the spans are already shaped right; the migration is a `zap-otel-bridge` tap on the logger, not a fields rewrite.

**Alternative considered and noted for the follow-up issue:** if a future phase ever opens Aura to multiple users (Phase 3+ multi-tenant work — see §1b "Forward note"), Arize Phoenix or Langfuse become much more valuable because the operator-facing log surface stops being one user's local file. Pinning the choice now would be premature; pinning the field *shapes* now is good engineering hygiene.

### Key Metrics to Track

Five metrics — each is a counter or gauge already implied by Section 6's guardrail/flywheel rows. None require new infrastructure beyond the zap fields above; the dashboard's existing `/api/health` endpoint adds three new fields.

| # | Metric | Type | Source | Exposed Via |
|---|--------|------|--------|-------------|
| 1 | `llm_retry_attempts_total{bucket, provider}` | Counter | `ClassifyRetryClient.Send` retry loop | log line + `/api/health.llm.retries_by_bucket` |
| 2 | `wiki_write_conflict_total` | Counter | `WriteWikiPageTool.Execute` on `errors.As(err, &conflict)` (D-03) | log line + `/api/health.wiki.conflicts_total` |

### Alert Thresholds

Single-user economics: there is no PagerDuty, no on-call rotation. "Alert" means **the bot self-messages the maintainer on Telegram**, using the existing bot handle (the operator is also the user). Thresholds are calibrated to be quiet — false alarms in a self-hosted setup train the operator to mute alerts, which is worse than no alerts.

| Trigger | Threshold | Notification |
|---------|-----------|--------------|
| Secret-leakage regex hit | Any non-zero count of `secret_leakage_blocked_total` over a CI run OR a 24h log window | Bot self-message: `"Phase 2 secret-leakage guardrail fired — see WARN secret_leakage_blocked source=classifier in data/aura.log."` PLUS the offending log line is permanently dropped (Section 6 online row 1). |
| `wiki_unversioned_pages_total > 5` | Daily check; threshold 5 OR upward trend day-over-day | Bot self-message: `"Wiki has N pages with unversioned: true. Likely a git-config / filesystem-permission issue — check data/aura.log for git_commit_failed lines."` |
| `reindex_dropped_total{reason=queue_full}` per hour | > 10/hr sustained for 2 consecutive hours | Bot self-message: `"Reindex queue saturating: N drops/hr. Check Qdrant + embedding API health; search results will lag the filesystem until this clears."` |
| `bucket=CONTENT attempt>=2` rate per provider | > 5% of write_wiki_page calls over rolling 7 days | Weekly digest (Sunday) bot self-message: `"CONTENT-retry rate elevated for {provider}: N% of writes hitting attempt>=2. Review classify_fixture.go."` |
| `runtime.NumGoroutine()` baseline regression in CI | Any positive delta over 100 Start/Stop cycles | CI build fails; PR cannot merge. No runtime alert (this is a structural test, not a production signal). |

### Smart Sampling Strategy

**Default sample rate: 5% of production traces** (single-user economics — review burden must fit the maintainer's actual time budget). On top of the random 5%, **always-capture** for any trace that hits a high-signal condition:

| Always-capture condition | Why |
|-------------------------|-----|
| `bucket != "" AND attempt >= 2` (any retry beyond the first) | Retries are the dominant cost driver (§1b row 2) and the most informative signal of provider drift. CONTENT retries also exercise the redactor's secret-leakage path, which is Critical. |
| `bucket=PERMANENT` | Rare by construction; every occurrence is worth eyeballing in case it's a misclassification (e.g., a 503 leaking through as PERMANENT — §1b failure mode #6). |
| `wiki_write_conflict_total` increments | Conflict resolution is the WIKI-02 contract surface; capturing the full trace lets the maintainer verify the LLM correctly re-read and retried (§1b row 4 expert-acceptance criterion). |
| `unversioned_after=true` on a write trace | Git failed; full trace gives the operator the context to root-cause. |
| `tool_retrieval_fallback_total` increments | Cold-start, Qdrant-down, or empty-on-user-turn — all three are operationally distinct and benefit from the full trace context (§1b row 7). |
| `reindex_dropped_after_stop` | Shutdown-time backlog; rare and structurally distinct from queue-full (§1b failure mode #8). |

The 5% random sample provides a baseline for "what does a normal turn look like" so that drift in normal turns (e.g., tool-retrieval precision degrading without crossing a threshold) is detectable. The always-capture set provides full-fidelity traces for the failure-mode tail.

**Manual review cadence:** the maintainer (the only "ops" role) reviews the always-capture set weekly and the 5% random sample monthly. This matches the §1b "Project maintainer (the user)" responsibility line: *"a weekly look at `bucket=content` and `reindex_dropped_after_stop` log lines"*.
