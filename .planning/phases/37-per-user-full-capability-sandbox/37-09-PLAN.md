<objective>
Route background shell jobs into the box — the most invasive of the five tools (RESEARCH Open
Q4 / Assumption A5), scoped as its own final slice. Today `BackgroundShells` holds a host
`*exec.Cmd` with a process group; under a strict profile the registry must instead hold a
**box-exec handle**, mapping start/poll/kill from `exec.CommandContext`+process-group signals to
a **concrete streamed/detached exec verb** on the DockerBackend (`ExecCreate` with attached
stdout/stderr streamed to a registry-read buffer + `ExecInspect` for liveness/exit + ctx-cancel/
box-signal for kill). That streaming verb is a documented DockerBackend method (or a separate
optional interface the router exposes) — it does **NOT** add a 6th verb to the `Backend`
interface, because D-02 locks that seam to exactly Resolve/Exec/Suspend/Resume/Stop so the DGX
`agent-sandbox` E2B impl drops in unmodified. The owner/authority layer (random unguessable IDs,
session/actor binding, TTL, `authorizeCaller`, `localOwnerID`) is orthogonal and stays; only the
process handle behind `bgShell` changes. A routed-but-box-failed start denies (never a host
process); dev/local_trusted keeps the host path unchanged.

Purpose: complete SBX-01's tool set (D-11 lists shell_bg in the routed five). Isolating it last
(after the four non-background tools in 37-07) contains its risk — the registry redesign is the
one place a leak, an authority regression, or a D-02 interface-widening could slip in. The
streaming verb resolves RESEARCH A5's Medium risk (the buffered ExecResult is insufficient for a
long-running background job) by naming the concrete mechanism explicitly instead of assuming
`backend.Exec` can stream.
Output: the concrete streamed/detached exec verb on the DockerBackend + the box-exec-handle
background registry + poll/kill mapping + the fail-CLOSED start + the strict-background
integration test.
</objective>
