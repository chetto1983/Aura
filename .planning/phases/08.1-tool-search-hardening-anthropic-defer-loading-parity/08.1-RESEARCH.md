# Phase 08.1: Tool Search hardening — Anthropic defer_loading parity - Research

**Researched:** 2026-06-03
**Domain:** In-process tool retrieval (BM25 ranking), JSON-Schema field extraction, MCP tool-name namespacing, prompt-cache-safe tool metadata
**Confidence:** HIGH (ground-truth code + Codex reference impl read directly; one external dependency decision resolved against Aura's own dependency-discipline constraints)

## Summary

This is a HOW-phase. The deferred-tool mechanism already exists and works (`Spec.Deferred`, the non-deferred `tool_search` hook, `Registry.Render` alphabetical-stable manifest). Phase 08.1 upgrades the *quality* of `tool_search` to Anthropic `defer_loading` parity along four locked axes (D-01..D-10): (1) substring → BM25 over an expanded per-tool "search document", (2) a `max_results` top-K cap defaulting to 5, (3) `<server>__<tool>` namespacing in the `mcptools` bridge with sanitize + 64-byte cap + collision hash, and (4) two parity extras — a registry-derived tool-categories blurb inside the `tool_search` Description, and a ≥1-non-deferred fail-closed guard.

The single open research question (D-04) is the BM25 implementation. The evidence is decisive: **hand-roll a ~120-180 LOC in-house BM25 ranker** (tokenizer + IDF/TF scorer) rather than add a Go dependency. Reasoning below — the candidate Go libraries are 6-14-star single-maintainer ports (slopcheck/supply-chain risk), some still require you to supply your own tokenizer, and D-01 explicitly says "no new infra dependency"; the math is ~50 LOC and fully testable. Codex itself uses the Rust `bm25` crate (a mature 2.3.2 ecosystem package) — but Go has no equivalent of comparable maturity, so the dependency tradeoff inverts.

**Primary recommendation:** In-house BM25 in a new `internal/agent/tools/bm25.go` (Okapi BM25, k1=1.5, b=0.75, lowercase + `[a-z0-9]+`-on-non-alphanumeric tokenizer, field-flattened search document built once at registry-build time and memoized on the `ToolSearch` struct). Mirror Codex's `default_tool_search_text` / `append_schema_search_text` recursion for the search document. Keep BM25 ranking confined to `tool_search` *output* — never touch `Render()` manifest order (cache-load-bearing). Namespacing mirrors `codex-mcp/src/tools.rs` adapted to Go.

- **D-05:** Top-K cap via a new optional `max_results` arg on `tool_search` (default **5**). Reject `max_results == 0`. BM25 selects top-K. Keyword/free-text capped; **`select:` stays uncapped**.
- **D-06:** Bridged MCP tools namespaced `<server>__<tool>` (double-underscore). `Mount`/`Bridge` take the server/namespace name as input and apply the prefix.

### Pattern 1: Search-document construction (mirror Codex, adapted to Go)
**What:** Flatten each deferred tool into one whitespace-joined string the BM25 indexes.
**Codex algorithm (`tools/src/tool_search.rs:70-139`), transcribed:**
```
default_tool_search_text(name, spec):
    parts = []
    push(name)                          # e.g. "web_fetch"
    push(name.replace('_', ' '))        # e.g. "web fetch"   ← critical: lets "fetch" match "web_fetch"
    push(namespace)                     # if present
    # for a function tool:
    push(tool.name); push(tool.name.replace('_',' ')); push(tool.description)
    append_schema_search_text(parameters)
    return parts.join(" ")

append_schema_search_text(schema):      # RECURSIVE
    if schema.description: push(it)
    for (propName, propSchema) in schema.properties:
        push(propName)                  # ← parameter NAME indexed
        append_schema_search_text(propSchema)   # recurse into nested object
    if schema.items: append_schema_search_text(items)        # arrays
    for variant in schema.anyOf: append_schema_search_text(variant)  # unions
    # push_search_part trims and drops empties
```
**Go adaptation note:** Aura's `Spec.Parameters` is `json.RawMessage` (raw JSON-Schema bytes — see `spec.go:23`). Codex has a typed `JsonSchema`; Go must `json.Unmarshal` into a recursive struct or `map[string]any`. Recommended typed shape (avoids `any` churn, easy to test):
```go
type schemaNode struct {
    Description string                 `json:"description"`
    Properties  map[string]schemaNode  `json:"properties"`
    Items       *schemaNode            `json:"items"`
    AnyOf       []schemaNode           `json:"anyOf"`
    // OneOf/AllOf optional — add if any Aura tool uses them; currently none do.
}
```
Unmarshal `Spec.Parameters` into `schemaNode`; on unmarshal error, fall back to Name+Description only (never panic — a malformed schema must degrade gracefully). **Determinism caveat:** `map[string]schemaNode` iteration order is random in Go — sort property names before appending so the search document (and any snapshot test of it) is byte-stable. (It does not affect BM25 scores, which are bag-of-words, but stable docs make tests deterministic.)

### Pattern 2: Okapi BM25 over a small in-memory corpus
**What:** Score each deferred-tool document against the query terms.
**Formula (Okapi BM25):** for query term `t`, document `d` of length `|d|`, average doc length `avgdl`, corpus size `N`, docs-containing-`t` = `n_t`:
```
idf(t)   = ln( (N - n_t + 0.5) / (n_t + 0.5) + 1 )     # +1 keeps idf ≥ 0 (Lucene-style; avoids negative idf on common terms)
score(d) = Σ_t  idf(t) · ( f(t,d)·(k1+1) ) / ( f(t,d) + k1·(1 - b + b·|d|/avgdl) )
```
**Defaults:** `k1 = 1.5`, `b = 0.75` (standard; matches Lucene/Elasticsearch and the `bm25` crate defaults). These are Claude's-discretion per CONTEXT.md.
**Tokenizer:** lowercase, split on any non-`[a-z0-9]` run, drop empties. No stemming, no stopwords (the `bm25` crate uses `Language::English` with light stemming; for a ~50-doc tool index, plain tokenization is sufficient and more predictable — stopword removal could drop "list"/"get" which are meaningful tool verbs). This is Claude's discretion; document the choice.
**Build once:** compute per-document term frequencies + doc lengths + the IDF table at registry-build time, memoize on the `ToolSearch` struct (the Registry is immutable for the run — `spec.go:48-53`). Since the Registry is fixed, the index can be lazily built on first search or eagerly in a constructor. Lazy + `sync.Once` is the cleanest (no constructor signature change). **Concurrency:** if lazy, guard the build with `sync.Once`; reads after build are immutable so no further locking needed.

### Pattern 3: MCP namespacing + sanitize + collision hash (mirror Codex `codex-mcp/src/tools.rs`)
**Sanitize (`mcp/mod.rs:394-409`), transcribed:** keep `[A-Za-z0-9_]`, replace every other char with `_`; if result empty → `"_"`. **Note D-07 wants `[a-zA-Z0-9_-]` (hyphen allowed)** — Aura's spec is slightly more permissive than Codex (Codex maps `-`→`_`). Follow D-07: allow `-` too.
**Delimiter:** `__` (double underscore). Constants from Codex: `MAX_TOOL_NAME_LENGTH = 64`, hash via SHA-1 hex, `CALLABLE_NAME_HASH_LEN = 12` (suffix `_<12hex>`).
**Algorithm (simplified for Aura — single namespace per Mount call):**
```
for each bridged tool d:
    base = sanitize(namespace) + "__" + sanitize(d.Name)
    if len(base) > 64:  truncate tool-name part, append "_<12hex(rawIdentity)>" fitting in 64B
    if base collides with an already-chosen name in this Mount batch OR with a Registry name:
        base = base + "_<12hex(rawIdentity)>"   (or apply per D-07: namespace-first then tool-name hash)
    name = base
```
**Codex's full collision handling** (`normalize_tools_for_model_with_prefix`, `unique_callable_parts`, `fit_callable_parts_with_hash`) handles cross-server namespace collisions and length-aware hash fitting. Aura's `Mount` is single-server all-or-nothing, so a simplified version suffices: prefix → sanitize → cap-with-hash-if-too-long → if residual collision with existing registry names, append hash. Keep the existing `Mount` all-or-nothing refusal (`bridge.go:99-121`) as the outer guard AFTER namespacing (CONTEXT.md `code_context`: "namespacing slots in *before* the collision check").
**rawIdentity for the hash:** use `namespace + "\0" + toolName` (Codex uses server+namespace+tool+connector joined by `\0`); a stable distinct string so the suffix is deterministic.

### Pattern 4: Dynamic source orientation in the tool_search Description (D-09, mirror `tool_search_spec.rs`)
**What:** Build the `tool_search` `Description` at Spec()-time from the Registry's mounted tools/sources.
**Codex template (`tool_search_spec.rs:49-51`), transcribed:**
```
"# Tool discovery\n\nSearches over deferred tool metadata with BM25 and exposes matching tools for the next model call.\n\nYou have access to tools from the following sources:\n{source_descriptions}\nSome of the tools may not have been provided to you upfront, and you should use this tool (`tool_search`) to search for the required tools."
```
where `{source_descriptions}` = `"- <name>: <desc>"` per source, deduped, sorted (Codex uses a `BTreeMap` → sorted), or `"None currently enabled."` if empty.
**Aura mapping:** Aura has no "source/namespace" concept on `Spec` today. For 08.1, "sources" = the set of deferred tool names (or, once MCP is mounted, the namespace prefixes). Minimal parity: list deferred tool Name+Summary, or — better — group by namespace prefix (`<ns>__`) when present. **Cache-safety (critical):** because `ToolSearch.Spec()` now reads the Registry, and the Registry is immutable for the run, the Description is byte-stable across turns → does NOT bust the OpenRouter implicit cache. But `tool_search` is non-deferred, so its full Description **does** appear in the manifest sent every turn — verify the Description is computed deterministically (sorted source list) so two `Spec()` calls are byte-identical. **Do NOT read any clock or per-turn value in the Description** (same rule as `prompt.go`).

### Anti-Patterns to Avoid
- **Re-sorting `Render()` by BM25 score.** BM25 affects only `tool_search` *output*; `Render()` stays alphabetical-by-Name (`manifest.go:39`). Any reshuffle busts the prompt cache (`reference_aura_cache_poisoning_sites_2026-05-27`).
- **Putting categories in `SystemPrompt`.** `prompt.go` is a byte-stable package constant; enumeration would cache-bust every turn (D-09).
- **Reading a clock / per-turn value in `tool_search.Spec().Description`.** Same byte-stability rule.
- **`map` iteration in the search-document builder without sorting keys.** Non-deterministic doc strings break snapshot tests (scores are unaffected, but tests must be deterministic).
- **Hand-ordering bridged tool names.** `Render()` auto-sorts; namespacing changes names → re-verify alphabetical stability holds after the rename (a `github__x` vs a built-in `web_fetch` reshuffles the manifest legitimately — that's a one-time change at mount, still deterministic per run).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Inverted index / segment store | A Lucene-style posting list | Naive O(N·terms) scan over ≤~50 docs | N is tiny; an inverted index is wasted complexity and LOC |
| Stemmer / language analyzer | Snowball/Porter port | Plain lowercase tokenizer | Tool verbs (list/get/create) must NOT be stemmed/stopword-dropped; predictability > recall here |
| JSON-Schema validation | A schema validator | `json.Unmarshal` into a minimal recursive struct + graceful fallback | We only *read* descriptions/prop-names, not validate |
| SHA hashing | Custom hash | `crypto/sha1` (Codex parity) or `hash/fnv` | stdlib; sha1 matches Codex's suffix scheme exactly |

**Key insight:** The *scorer math* is the one thing worth writing yourself here — it's ~50 LOC, fully deterministic, trivially unit-testable, and frees the phase from a 6-14★ dependency. Everything *around* it (index structures, analyzers) would be over-engineering for a ≤50-tool corpus.

## Common Pitfalls

### Pitfall 1: Cache-poisoning via manifest reshuffle
**What goes wrong:** Sorting `Render()` by BM25 score, or making `tool_search.Spec().Description` non-deterministic, busts OpenRouter's implicit prefix cache → silent cost/latency regression.
**Why it happens:** Conflating "rank tool_search output" (correct) with "reorder the manifest" (wrong).
**How to avoid:** BM25 lives only in `ToolSearch.Execute`. `Render()` stays `sort.Slice(... Name < Name)` (`manifest.go:39`). `tool_search.Spec().Description` computed from a *sorted* source list, no clock.
**Warning signs:** A test asserting manifest order changes; `cmd/aura/cache_audit.go` reporting a busted prefix.

### Pitfall 2: `name-with-_-as-spaces` omitted from the search document
**What goes wrong:** Query "fetch web" fails to match tool `web_fetch` because the underscore form isn't tokenized into "web"+"fetch".
**Why it happens:** Forgetting the `name.replace('_',' ')` part Codex explicitly pushes (`tool_search.rs:73,109`).
**How to avoid:** Push BOTH the raw name and the space-substituted name into the search document. This is D-02's stated leverage point.
**Warning signs:** Ranking test where a multi-word query over an underscore-named tool returns nothing.

### Pitfall 3: Non-deterministic search document from map iteration
**What goes wrong:** Recursing `schemaNode.Properties` (a Go map) yields different doc strings per run → flaky snapshot/property tests.
**How to avoid:** Sort property keys before appending. Scores are bag-of-words (order-independent) so this is purely for test determinism — but it matters.
**Warning signs:** A `bm25_test.go` snapshot that passes/fails intermittently.

### Pitfall 4: `max_results == 0` or negative not rejected
**What goes wrong:** `0` returns nothing silently; a negative slice index panics.
**How to avoid:** D-05 — reject `max_results == 0` with a model-facing error (Codex `tool_search.rs:93-97` returns "limit must be greater than zero"). Treat absent → default 5. Clamp top-K to `len(matches)`. `select:` ignores `max_results` (uncapped).
**Warning signs:** Empty result on a query that clearly matches; a panic on negative input.

### Pitfall 5: ≥1-non-deferred guard counting tool_search itself
**What goes wrong:** Guard passes because `tool_search` is non-deferred, even if every *capability* tool is deferred → the model can never act, only search.
**How to avoid:** D-10 — exclude `tool_search` from the count (Anthropic's exact semantics: "At least one tool must be non-deferred" excluding the search tool). Encode structurally that `tool_search` cannot be deferred (its `Spec().Deferred` is hardcoded `false`; optionally assert it in `Validate()`).
**Warning signs:** An all-deferred registry (plus tool_search) boots without error.

### Pitfall 6: Windows/WSL test specifics
**What goes wrong:** None specific to this phase — these are pure functions, no filesystem/network/container. `go test ./internal/agent/tools/ ./internal/agent/mcptools/` runs identically on Windows and WSL.
**Note:** `-race` is irrelevant to the math (no goroutines) BUT the `sync.Once` memoization (if used) is the one concurrency point — add one `-race` test that calls `Execute` from multiple goroutines to exercise the `Once`. Per CLAUDE.md, run `go test -race` on touched packages anyway (WSL native, or `BASH_ENV=~/.aura-toolchain.sh` on Windows).

```go
// Source: mirror of D:\tmp\codex\codex-rs\tools\src\tool_search.rs:107-139
func searchDocument(s Spec) string {
    var parts []string
    push := func(p string) {
        if p = strings.TrimSpace(p); p != "" {
            parts = append(parts, p)
        }
    }
    push(s.Name)
    push(strings.ReplaceAll(s.Name, "_", " ")) // critical: "web_fetch" → "web fetch"
    push(s.Description)
    var node schemaNode
    if err := json.Unmarshal(s.Parameters, &node); err == nil {
        appendSchema(node, push)
    } // on error: degrade to Name+Description only — never panic
    return strings.Join(parts, " ")
}

func appendSchema(n schemaNode, push func(string)) {
    push(n.Description)
    keys := make([]string, 0, len(n.Properties))
    for k := range n.Properties {
        keys = append(keys, k)
    }
    sort.Strings(keys) // determinism
    for _, k := range keys {
        push(k) // parameter NAME is indexed (D-02)
        appendSchema(n.Properties[k], push)
    }
    if n.Items != nil {
        appendSchema(*n.Items, push)
    }
    for _, v := range n.AnyOf {
        appendSchema(v, push)
    }
}
```

### Okapi BM25 scorer (Go)
```go
// Source: standard Okapi BM25; defaults match the Rust bm25 2.3.2 crate Codex uses.
const (
    bm25K1 = 1.5
    bm25B  = 0.75
)

func tokenize(s string) []string {
    return strings.FieldsFunc(strings.ToLower(s), func(r rune) bool {
        return !(r >= 'a' && r <= 'z') && !(r >= '0' && r <= '9')
    })
}

// scoreDoc returns the BM25 score of one doc's term-freq map against query terms,
// given precomputed idf and corpus stats.
func scoreDoc(tf map[string]int, docLen int, qterms []string, idf map[string]float64, avgdl float64) float64 {
    var score float64
    for _, t := range qterms {
        f := float64(tf[t])
        if f == 0 {
            continue
        }
        denom := f + bm25K1*(1-bm25B+bm25B*float64(docLen)/avgdl)
        score += idf[t] * (f * (bm25K1 + 1)) / denom
    }
    return score
}
// idf(t) = ln( (N - n_t + 0.5)/(n_t + 0.5) + 1 )   // Lucene-style, non-negative
```

### MCP namespacing (Go, adapting Codex)
```go
// Source: mirror of D:\tmp\codex\codex-rs\codex-mcp\src\tools.rs + mcp/mod.rs:394-409
const (
    nsDelimiter   = "__"
    maxToolNameLen = 64
    hashLen        = 12
)

func sanitizeName(s string) string {
    var b strings.Builder
    for _, r := range s {
        switch {
        case r >= 'a' && r <= 'z', r >= 'A' && r <= 'Z', r >= '0' && r <= '9', r == '_', r == '-':
            b.WriteRune(r) // D-07 allows [a-zA-Z0-9_-] (Codex maps '-'→'_'; Aura keeps '-')
        default:
            b.WriteByte('_')
        }
    }
    if b.Len() == 0 {
        return "_"
    }
    return b.String()
}

func hashSuffix(rawIdentity string) string {
    h := sha1.Sum([]byte(rawIdentity))
    return "_" + hex.EncodeToString(h[:])[:hashLen]
}
// namespacedName: sanitize(ns)+"__"+sanitize(tool); if >64B fit-with-hash; if collision append hashSuffix.
```
