## Warnings

### WR-01: `namespacedName` can exceed the 64-byte cap when the namespace prefix is large

**File:** `internal/agent/mcptools/name.go:54-59`
**Issue:** The cap branch computes `keep := maxToolNameLen - len(prefix) - len(suffix)`
and clamps `keep` to `0` when negative, then returns `prefix + sanitizeName(tool)[:keep] + suffix`.
The clamp protects the *slice index* (no panic), but it does NOT protect the *output
length*: when `len(prefix)` alone is large (a namespace ≥ ~51 bytes, since `suffix` is
13 bytes), the returned `prefix + suffix` already exceeds `maxToolNameLen`. The function's
own doc comment ("the whole capped at maxToolNameLen") is then violated. MCP server names
are user/config-supplied JSON keys with no length bound (`internal/config/config.go:241`
`validateMCPServers` trims but never length-checks the name), so a 60-char server name in
`AURA_MCP_SERVERS_JSON` produces a tool name > 64 bytes — the exact LLM-contract breach
the namespacing was added to prevent. `TestNameLengthCap` only exercises a long *tool*
part, never a long *namespace*, so the gap is untested.
**Fix:** Bound the prefix too — truncate the sanitized namespace before joining, or
length-check server names at config load. Minimal in-function fix:
```go
func namespacedName(namespace, tool string) string {
	prefix := sanitizeName(namespace) + nsDelimiter
	base := prefix + sanitizeName(tool)
	if len(base) <= maxToolNameLen {
		return base
	}
	suffix := hashSuffix(namespace + "\x00" + tool)
	// Reserve room for the suffix; if even the prefix overflows, truncate it.
	budget := maxToolNameLen - len(suffix)
	if budget < 0 {
		budget = 0
	}
	if len(prefix) > budget {
		return prefix[:budget] + suffix
	}
	return prefix + sanitizeName(tool)[:budget-len(prefix)] + suffix
}
```
Plus a `validateMCPServers` length guard would be the more honest fix-closed.

### WR-02: Mount collision-hash append can push an already-capped name past 64 bytes

**File:** `internal/agent/mcptools/bridge.go:119-122`
**Issue:** When two distinct raw tool names sanitize to the same namespaced name,
the second survivor gets `name += hashSuffix(...)`. But `name` here is `bt.spec.Name`,
which was already produced by `namespacedName` and may already sit at the full 64-byte
cap (when the tool part was truncated). Appending the 13-byte `_<12hex>` suffix yields up
to 77 bytes — over the cap, with no re-truncation. `TestMount_CollisionHash` uses short
names (`a.b` / `a/b`) so the over-cap path is never exercised. The collision suffix and
the length cap are layered independently and neither re-checks the other.
**Fix:** Route the collision disambiguation back through a cap-aware helper instead of a
bare `+=`, e.g. re-derive from the raw name with a collision salt, or truncate before
appending:
```go
if _, dup := chosen[name]; dup {
	suf := hashSuffix(namespace + "\x00" + bt.name)
	if len(name)+len(suf) > maxToolNameLen {
		name = name[:maxToolNameLen-len(suf)]
	}
	name += suf
	bt.spec.Name = name
}
```

## Info

### IN-01: `max_results <= 0` is rejected even for `select:` queries, where the cap is ignored

**File:** `internal/agent/tools/search.go:137-143`
**Issue:** `Execute` validates `max_results` (rejecting `<= 0` with a model-facing error)
*before* dispatching to `match`. But the `select:` branch in `match` ignores `limit`
entirely (correctly, per D-05). So a model that sends `{"query":"select:foo","max_results":0}`
gets an error even though `max_results` is documented as "Ignored for 'select:' queries."
The schema description and the validation disagree for the select path. Harmless
(defensive), but it can confuse the model into thinking its select failed.
**Fix:** Move the `max_results <= 0` rejection into the keyword branch of `match` (after
the `select:` prefix check), so select queries never see it; or document that
`max_results` must still be omitted/positive for selects.

### IN-02: `crypto/sha1` import will trip security linters (gosec G505 / G401)

**File:** `internal/agent/mcptools/name.go:4`
**Issue:** `crypto/sha1` is used purely as a non-cryptographic collision disambiguator
(the comment at `name.go:36-37` documents this explicitly and correctly). However,
`gosec` flags any `crypto/sha1` import (G505) regardless of intent, which will surface
as a finding in the `make vuln`/lint matrix and could block CI or generate noise that
masks real findings. Not a real vulnerability — flagging it so the linter result is
expected, not a surprise.
**Fix:** Either switch to a non-crypto hash for disambiguation (`hash/fnv` or
`hash/maphash` produces a stable hex digest with no security-linter baggage), or add a
scoped `//nolint:gosec // G505: non-cryptographic collision disambiguator, documented`
suppression so the intent is machine-readable.

### IN-03: `searchDocument` indexes `Description` but not `Summary` — confirm this is the intended BM25 corpus

**File:** `internal/agent/tools/bm25.go:34-49`
**Issue:** The BM25 search document pushes `Name`, the underscore-spaced name,
`Description`, and recursive param names/descriptions — but never `Summary`. The
`search_test.go:72-96` comment justifies this as Codex parity (description, not a separate
summary field). This is a deliberate, tested choice, but it is a behavioral asymmetry
worth flagging: a deferred tool whose distinctive keyword lives only in its one-line
`Summary` (and not its `Description`) is unfindable by keyword. Since `Summary` is the
only field the manifest shows for deferred tools, a model could reasonably search for a
word it saw in the Summary and get "no matching tools."
**Fix:** No code change required if the parity decision stands. If broader recall is
wanted, add `push(s.Summary)` to `searchDocument` — it is byte-stable and cannot regress
the existing tests.
