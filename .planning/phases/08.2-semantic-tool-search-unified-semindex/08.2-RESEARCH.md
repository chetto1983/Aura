### D-02 — Semantic ranker: pure embedding over the bm25-doc text, guarded BM25 tiebreak

**Status: BUILDABLE. The embedding input and the tiebreak signal both already exist.**

- **Embedding input = `searchDocument(spec)`** (`bm25.go:34-49`) — NOT raw description. This is the
  flattened `name + name-with-spaces + description + sorted schema property names/descriptions` already
  built for BM25. Reuse it verbatim (spike-056 "bm25doc-enriched input"). It is already byte-stable
  (property keys sorted, `bm25.go:55-72`), so it is a deterministic embedding key.
- **Guarded tiebreak (spike-056 VALIDATED, NOT RRF):** BM25 contributes only when its result-set ≤ 5
  results AND the tool is in embedding's top-15; else strict no-op. On the IT corpus this is **≡ pure
  embedding** (9/13 top-1, MRR 0.799 — spike-056 results table) but safe for English/keyword queries.
  Naive/weighted RRF **regress** (6/13) and are rejected. The BM25 path (`bm25Index.rank`, `bm25.go:130-145`)
  stays; it now feeds the guard, not the primary order.
- **Env kill-switch (D-02a):** exactly ONE — `AURA_TOOLSEARCH_FUSION=guarded|off` (default `guarded`).
  Gate constants (`≤5`, `top-15`) are hard-coded with the spike as provenance. No other tuning env.
- **`select:` path unchanged** — `search.go:188-198` (`strings.CutPrefix(q, "select:")`, uncapped,
  substring/exact load-by-name). Do not touch.

**Landing site:** `ToolSearch.match` (`search.go:187-210`). Today it calls `idx.rank(q)` (BM25) at
`search.go:201`. Target: rank via `semindex.Ranker` over the embedded bank, then apply the guarded BM25
tiebreak. The `match → Execute → NewResult` shape (`search.go:165-182`) is unchanged, preserving the
result-rendering and spillover path.

### D-03 — Incremental re-embed on MCP mount

**Status: BUILDABLE. The hook seam is exactly where CONTEXT says.**

- Seam: `mcptools.Mount` (`bridge.go:208-221`) registers an `setRefreshHook(func(){ invalidateToolSearch(reg) })`
  at `bridge.go:217-218`; `invalidateToolSearch` (`bridge.go:223-228`) resolves `tool_search` from the
  registry and calls `ts.InvalidateIndex()`.
- Today `InvalidateIndex()` (`search.go:36-41`) **nils the whole memoized index** (`ts.index = nil; ts.deferred = nil`)
  → next search does a full rebuild via `indexSnapshot` (`search.go:214-236`). For BM25 that is cheap; for an
  embedding bank a full re-embed of N tools is ~7ms × N (spike-055) and wasteful.
- **Target:** add an incremental append path. Replace the full-drop with "embed only the newly-advertised
  tools (~5–8ms/tool, spike-055) and append to the cached embedding bank." Concurrency is the wrapper
  `sync.RWMutex` (D-01) — concurrent mount(append, write-lock) + search(read-lock) must be race-clean.

**Mismatch to reconcile (MEDIUM — needs a new seam, not just behavior swap):** `InvalidateIndex()` is a
*signal-only* method (no args); it does not know *which* tools are new. The current `indexSnapshot`
recomputes the deferred set from `Registry.All()` each rebuild (`search.go:218-231`). For an incremental
append the `ToolSearch` must diff the registry's current deferred set against the cached bank's keys (by
tool Name) and embed only the additions. The planner should design `ToolSearch` to **detect the delta
itself** at search/refresh time (compare `Registry.All()` deferred names vs the bank's keyed names), so the
existing zero-arg hook still works — no new argument needs to thread through `mcptools`. This keeps the
`bridge.go` seam untouched (it stays "signal: something changed") and confines the delta logic to
`ToolSearch`. **Acceptance test (Req-3): mounting an N-tool server triggers exactly N new `Embed` calls** —
assert via a counting fake embedder.

### D-06 — Detection signal + two-tier oracle

**Status: BUILDABLE (net-new, but the detector is cheap and spike-validated R=1.0).**

- **Detection (spike-057):** a turn is a mis-route candidate when a **shell/fs fallback tool was used OR
  used-tool ≠ ranker top-1**. The shell/fs-fallback heuristic alone is P0.88/R1.00 and needs **no embedding**
  — it directly encodes the bitcoin failure mode. Tool identity must be **symmetric** (`sameTool`):
  namespaced (`whatsapp__send_message`) vs bare (`send_message`) compared via the `nsDelimiterStr = "__"`
  split (`search.go:93`). Spike-057's investigation trail explicitly hit this — an order-sensitive suffix
  match gave a spurious FP; `sameTool` fixed precision 0.78→0.88.
- **Free labeling:** ranker top-1 when its top-2 margin is high (confident) — reuse `Ranker`'s margin.
- **Escalation oracle = the EXISTING LLM router (DeepSeek)** — the same `Oracle.Label` shape the reasoning
  learner uses (`runner/reasoning_learner.go:20-43`). **No new sidecar** (Req-8). Aura has NO local
  text-gen Gemma — the 9c sidecars are OCR/STT/TTS only (confirmed via memory
  `project_9c_multimodal_engine_pivot`). The escalation is mandatory for the hard ~40% where the free ranker
  is itself wrong (spike-057: free ranker labels only 4/7 mis-routes correctly; the other 3/7 it would teach
  the WRONG label — the gravity-well amplification).
- **No-paid-runs guardrail:** margin-gated + async + post-turn + bounded + self-limiting (fewer uncertain
  turns as the bank grows). Kill-switch `AURA_TOOLSELECT_ORACLE=on|off` (default on).

**Open question for the planner (genuine):** *where* does the used-tool signal get captured? The detector
needs `(request, tool-actually-used)` per turn. The agent loop records tool invocations
(`ToolInvocationStore` is wired in the runner) — the planner must locate the hot-path observation point that
sees both the user request and the executed tool name, off the hot path. (Not answered by the locked
artifacts; see §6.)

### D-07 — Learned-signal mechanism: positives-only Rocchio centroid + margin-gated stage-2 boost

**Status: BUILDABLE. The Neo4j template is `:ReasoningExample` verbatim.**

- A confirmed `(query-embedding → tool)` pair folds into a **per-tool centroid** of confirmed query
  exemplars via `semindex.Classifier(Centroid)` **keyed by tool** (same Centroid mode as reasoning — proves
  the unified-core thesis). This is positives-only Rocchio (γ=0) = a prototype.
- **Fusion = margin-gated conditional boost** (retrieve→rerank; cosine stage-1, learned centroid stage-2).
  Fires only when `centroid_cos > τ` and confidently separated; else strict no-op. When it fires the boost
  is additive β with α (base description) ≥ β (learned), `boost ≤ ε·desc_cos` (PRPO clamp).
- **Anti-amplification guards (Req-5):** (1) min-support floor N≥3–5 confirmed exemplars before a tool's
  centroid is eligible — the highest-value guard; (2) boost cap; (3) seeds/descriptions authoritative +
  content-hash dedup + bounded bank; (4) oracle-in-loop (ranker never self-confirms).
- **Neo4j schema:** new label `:ToolSelectionExample {hash, tool, embedding, query, source}` mirroring the
  shipped `:ReasoningExample {hash, tier, embedding, text, source}` (`reasoningstore/store.go:34-42`). Written
  via a NEW tool-selection `Store` with its own Cypher, mirroring `reasoningstore`.

**Confirmed Neo4j seam (HIGH):** `reasoningstore.GraphClient` (`store.go:19-22`) is `Read`/`Write(ctx, query, params)`;
`*knowledge.Client` satisfies it (`knowledge/client.go:226,234`). **No SQL migration** — the
`:ReasoningExample` node is created on first MERGE (`store.go:5` package doc + `saveQuery` `store.go:39-41`).
The new `:ToolSelectionExample` likewise needs **no migration** (Neo4j is schemaless; MERGE-on-hash creates
on first write). **Two non-obvious Cypher constraints to copy verbatim** (these are documented gotchas in
`reasoningstore`, `store.go:31-42`): (a) the mcp-neo4j-cypher **read** tool returns NULL for list-valued
columns, so the embedding MUST be serialized with `apoc.convert.toJson(e.embedding)` on read and parsed in
Go (`store.go:34-35,95-101`); (b) a top-level list param `$embedding` is **dropped** by the write tool, so
the embedding must be nested in an `UNWIND $rows AS row` map (`store.go:38-41`). The new store MUST mirror
both or it will silently lose embeddings.

**Proposed new files for D-06/D-07:** a `toolselect`-flavored store + oracle + detector. Suggested
placement: `internal/toolselectstore/store.go` (mirrors `reasoningstore`, ~120 LOC) and the loop wiring
(detector + oracle adapter) either in `internal/agent/tools` or a small `internal/toolselectlearn` package,
each ≤600 LOC. The planner chooses package boundaries; the constraint is the active-learning *mechanism*
lives in `internal/activelearn` (D-05) and only the *I/O* (Neo4j Cypher, the LLM oracle adapter) is
per-consumer.

## 5. Risks / Landmines (grounded in the read code)

1. **The ≥90% gate is documentation drift, not a shipped gate (§3).** Planning against "≥90%" will fail the
   live test (floor is 80/88) or silently never run it (wrong function name). **Highest-value flag.** Use
   `TestReasoningClassifierLive` / tag `reasoning_live` / floor 80/88, or deliberately raise it with operator
   sign-off.

2. **Stale one-arg `NewReasoningClassifier` in the live test** (`...live_test.go:61`) — compile blocker under
   `-tags reasoning_live`. Must be fixed in the same commit that touches the file (DEEP-REFACTOR-ON-TOUCH).

3. **Namespaced-vs-bare tool identity in detection (D-06).** Spike-057's investigation trail shows an
   order-sensitive suffix match produced a spurious FP; `sameTool` (symmetric, split on `nsDelimiterStr="__"`
   `search.go:93`) is mandatory. A naive `strings.HasSuffix` will reintroduce the bug and silently lower
   detection precision.

4. **Neo4j Cypher list-param gotchas (D-07).** The new `:ToolSelectionExample` store MUST copy
   `reasoningstore`'s two workarounds verbatim: `apoc.convert.toJson(embedding)` on read (lists come back NULL
   otherwise, `store.go:31-35`) and `UNWIND $rows AS row` nesting on write (top-level list params are dropped,
   `store.go:38-41`). Miss either and embeddings vanish without an error.

5. **RWMutex contention under concurrent mount+search (D-01/D-03).** The wrappers hold one `sync.RWMutex`;
   D-01 defers copy-on-write "unless a benchmark shows read-lock contention." The incremental append (D-03)
   takes the write lock; searches take the read lock. Validate race-cleanliness under `-race` (extend
   `TestToolSearchConcurrentExecute`, `search_test.go:322-338`) AND benchmark read contention at corpus size
   before deciding COW is unnecessary.

6. **Cache-poisoning sites (Req-7).** The `tool_search` Description is built from `sourceOrientation`
   (`search.go:107-145`), is byte-stable, and ships in **every** manifest because `tool_search` is
   non-deferred. Per-query semantic ranking MUST happen **inside `Execute`** (`search.go:147-182`) only —
   never mutate the Description, the manifest ordering, or `messages[0]`. The `descClockShape` guard
   (`search_test.go:318`) already exists; extend the invariant to N queries. See
   `feedback_aura_cache_poisoning_sites_2026-05-27`.

7. **No-paid-runs guardrail for the escalation oracle (D-06).** The DeepSeek oracle is a paid call. It MUST
   be margin-gated + async + post-turn + bounded + kill-switched (`AURA_TOOLSELECT_ORACLE=on|off`). The
   shipped `reasoninglearn` already encodes this discipline (margin floor `learner.go:96`, drop-on-full
   `learner.go:104-107`, `Observe` non-blocking `learner.go:95`) — the tool-selection loop must inherit it,
   not reinvent a hot-path call. See `feedback_no_unsolicited_paid_runs_batch_calls`.

8. **Self-amplification if the free ranker teaches itself (D-06/D-07).** Spike-057 proved the free ranker
   mislabels 3/7 hard mis-routes (the gravity well). The two-tier oracle (LLM escalation) is **mandatory**,
   not optional — a free-only loop amplifies its own bias. The anti-amplification guards (min-support N≥3–5,
   boost cap, seeds authoritative, oracle-in-loop) are correctness-bearing, not polish.

9. **Embed-sidecar hard-dep must NOT leak into the reasoning classifier (Req-6 vs Req-4).** `tool_search` is
   the hard-dep surface; the classifier KEEPS its soft fallback (`Classify` returns `("", false)` on embed
   failure, `reasoning_classifier.go:148,151-153`). Wiring the embedder as a hard dep at the composition root
   (`runner.go:162`) must not change the classifier's nil/error tolerance.

10. **MERGE-on-hash idempotency depends on a stable hash key.** `reasoningstore` keys on `sha256(text)`
    (`store.go:80-83`). The tool-selection store keys on the query (or query+tool). If the hash input is the
    raw query, two phrasings of the same intent create two nodes — acceptable (more exemplars), but the
    dedup is per-exact-text, matching the reasoning loop's semantics. Confirm the chosen hash input is
    documented so re-labeling the same query is idempotent.

## 6. Open Questions for the Planner (genuine; the design is otherwise locked)

1. **The Req-4 threshold (the §3 consequence).** The locked artifacts say "≥90%"; the shipped gate is
   **80% accuracy / 88% none-vs-rest** (`reasoning_classifier_live_test.go:92-97`). "Behavior-preserving"
   most naturally means "stays at or above the existing gate" → use **80/88**. Raising to 90/92 is a
   deliberate scope addition needing operator sign-off. **Pick one and state it in the plan.** (Recommend:
   keep 80/88, note the SPEC drift; do not silently inflate the gate.)

2. **Req-6 boot fail-fast vs per-call-only (CONTEXT D-04/Claude's Discretion explicitly leaves this open).**
   CONTEXT recommends a **boot health-check log + per-call explicit error**, NOT fail-fast-on-boot (to avoid
   coupling unrelated surfaces — e.g. `aura chat` with no MCP tools — to embed availability). Confirm the
   plan adopts the recommendation (health-check log at `aura serve` boot; per-call `ToolResult` error in
   `Execute`), and where the health-check lives (composition root near `runner.go` embedder wiring).

3. **Where the `(request, used-tool)` detection signal is captured (D-06).** The detector needs both the user
   request and the executed tool name, off the hot path. The runner wires a `ToolInvocationStore`; the
   planner must locate the exact observation point (likely post-turn in the runner or the agent loop) that
   sees both. Not answered by the locked artifacts.

4. **`internal/activelearn` label seam shape (D-05).** The core must depend on neither `prompt` nor a tool
   type. Two viable seams: (a) `Oracle.Label(ctx, text) → (saved bool)` where the consumer's oracle does its
   own label+save; or (b) core observes `(text, vec)` and the consumer owns the `process` step. D-05 settles
   the *strategy* (extract mechanism, copy I/O) but not the exact interface. The constraint: keep the
   reasoning E2E green (highest Req-4 risk).

5. **Package home for the tool-selection loop wiring (D-06/D-07).** `internal/toolselectstore` (Neo4j, mirrors
   `reasoningstore`) is clear. The detector + oracle adapter + loop wiring could live in `internal/agent/tools`,
   a new `internal/toolselectlearn`, or the runner. The constraint is the *mechanism* in `internal/activelearn`
   and each file ≤600 LOC; the boundary is the planner's call.
