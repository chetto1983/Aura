# Phase 08.2: Code Review Report

**Reviewed:** 2026-06-12
**Depth:** standard
**Files Reviewed:** 18
**Status:** issues_found

## Summary

Reviewed the semantic `tool_search` ranker (`semindex` core + `Ranker`/`Classifier` wrappers + `search*.go`), the three async active-learning loops (`activelearn`, `reasoninglearn`, `toolselectlearn`), the Neo4j tool-selection store, and the runner wiring/capture path.

The pure-math core (`semindex/core.go`) is clean: the `-2.0` length-mismatch sentinel, zero-vector guard, empty-bank nil centroid, and top-2 margin all hold and are non-panicking. The Cypher store is fully parameterized — no injection. The activelearn queue/dedup/drop-on-full mechanism is goleak-clean and the oracle paid-call gate (margin + `AURA_TOOLSELECT_ORACLE`) cannot be bypassed into unbounded LLM calls. The KV-cache invariant holds: per-query ranking happens inside `Execute`/`ensureBank` and never mutates the cached `tool_search` Description or any shared tool spec.

The dominant defect is a **detached-context, blocking hot-path capture** (CR-01): the tool-selection `Observe` is documented as non-blocking/off-hot-path but in fact runs up to three synchronous embed-sidecar round-trips inline on the turn iteration while the per-thread runner lock is held, using `context.Background()` so the turn's `/cancel` and deadline budget do not apply. Six warnings cover a stale-embedding-after-reconnect bug, an unsynchronized read of a mutex-guarded field, a mislabeled "margin" on a single-tool corpus, and several robustness gaps.

## Critical Issues

### CR-01: Tool-selection `Observe` blocks the user turn on a detached, uncancellable embed round-trip

**File:** `internal/runner/runner_persist.go:132-134`, `internal/toolselectlearn/learner.go:70-86`, `internal/agent/tools/search_learn.go:77-95`
**Issue:**
`r.toolSelectLearner.Observe(tr.userMsg, ti.ToolName)` is called **synchronously inside the `for ev := range la.Run(ic)` loop** in `runner.turnLocked` (via `persistEvent` → `persistToolTurn` on every `ToolInvocationEnd`). That loop runs while the per-thread mutex acquired in `Runner.Turn` (`runner.go:344-347`) is held. The capture is documented as non-blocking and off the hot path:

- `toolselectlearn/learner.go:66-69`: "It is NON-BLOCKING and must NOT abort the turn ... this runs post-turn in persistEvent's best-effort branch".

In reality `Observe` runs blocking network I/O on the live turn:
1. `isMisroute` → `top1Of` → `RankForLearner` → `ensureBank` embeds any not-yet-banked deferred tools (`ts.Embed.Embed`, search.go:356), then `embedQuery` embeds the request (search.go:288) — two sidecar calls;
2. if flagged, `toolselectlearn.Observe` does a **third** embed of the request (`l.embedder.Embed`, learner.go:81).

All three use `context.Background()` (search_learn.go:78,82; learner.go:81), so the turn's cancellation and the agent `Budget` deadline (`buildAgent`, runner.go:541) do **not** propagate. If the granite sidecar hangs, the user-visible turn wedges for the full `http.Client` timeout (or indefinitely if none) while holding the thread lock — and a `/cancel` of the turn cannot abort it. This is a cancellation-propagation defect and a robustness/availability risk, not merely a latency one: the loop the design promised was asynchronous is on the synchronous user path.

**Fix:** Make `Observe` truly fire-and-forget OR derive its context from the turn so cancellation propagates and the work is bounded. Minimal, behavior-preserving shape — hand the raw `(request, usedTool)` to the background worker and do BOTH the misroute ranking and the embed there, off the turn goroutine:
```go
// toolselectlearn: enqueue the raw signal; do detection + embed on the worker.
func (l *Learner) Observe(request, usedTool string) {
    if l == nil || l.inner == nil {
        return
    }
    // Non-blocking handoff: the activelearn worker (already a goroutine) runs
    // isMisroute (which may embed) + the exemplar embed, so the turn never waits.
    l.inner.ObserveRaw(request, usedTool) // new bounded, drop-on-full enqueue
}
```
If keeping the current shape, at minimum thread the turn ctx through `Observe`/`RankForLearner` (replace the two `context.Background()` calls) and run the whole capture in a `go func()` spawned from `persistToolTurn` so it cannot block the locked iteration or outlive cancellation uncontrollably. Either way, remove the false "NON-BLOCKING / off the hot path" comments or make them true.

## Warnings

### WR-01: Stale tool embedding survives an MCP reconnect that changes a tool's description

**File:** `internal/agent/tools/search.go:62-70`, `internal/agent/tools/search.go:343-369`
**Issue:**
`InvalidateIndex` drops `ts.bm25` and `ts.specs` but deliberately keeps the append-only embedding bank (`ts.ranker`) and the `ts.banked` name-set (search.go:65-69). `ensureBank` only embeds tools whose Name is **not** in `banked` (search.go:345-349). On a transport reconnect, `bridgedTool` atomically swaps its spec (description/parameters can change) and fires `refreshHook → invalidateToolSearch`. Because the tool's Name is unchanged, it stays in `banked`, so its **old** embedding vector is never refreshed — the semantic ranking for that tool is computed against its stale description forever. The BM25 tiebreak rebuilds correctly (specs dropped), masking the staleness in tests, but the primary embedding signal is wrong.

**Fix:** On invalidate, drop the embedding for any tool whose `searchDocument(spec)` changed (or, simpler and correct, re-embed the delta of changed-doc tools). Track a per-tool doc hash:
```go
// ensureBank: re-embed when the searchDocument hash differs from the banked one.
doc := searchDocument(s)
if h, ok := ts.bankedDocHash[s.Name]; !ok || h != hashDoc(doc) {
    newSpecs = append(newSpecs, s) // first-seen OR changed-on-reconnect
}
```
and replace (not append) the changed tool's vector in the ranker. If by-Name append-only is an intentional constraint, document that reconnect description changes are NOT reflected in semantic ranking.

### WR-02: `match` reads the mutex-guarded `ts.learned` field without the lock

**File:** `internal/agent/tools/search.go:271`, `internal/agent/tools/search_learn.go:53-58,63-68`
**Issue:**
`ts.learned` is written under `ts.mu` (`EnableLearnedBoost`, search_learn.go:55-57) and read under `ts.mu` (`FoldLearned`, search_learn.go:64-66), but `match` reads it **without** holding `ts.mu`: `ranked = ts.learned.rerank(ranked, qVecs)` (search.go:271). Today this is safe only because `EnableLearnedBoost` happens once at boot before any turn; nothing in the type enforces that. A field with a documented guarding mutex that is read lock-free is a latent data race the moment wiring order changes, and `go test -race` will flag it if `EnableLearnedBoost` is ever exercised concurrently.

**Fix:** Snapshot under the lock, mirroring `FoldLearned`:
```go
ts.mu.Lock()
learned := ts.learned
ts.mu.Unlock()
ranked = learned.rerank(ranked, qVecs)
```

### WR-03: `RankForLearner` returns a raw cosine (not a top-2 margin) on a single-tool corpus, inflating oracle "confidence"

**File:** `internal/agent/tools/search_learn.go:86-94`, `internal/toolselectlearn/oracle.go:85-91`
**Issue:**
When the deferred corpus has exactly one tool, `RankForLearner` falls through the `if len(scored) > 1` branch and returns `margin := scored[0].Score` — the absolute cosine, not a top-2 gap. `twoTierOracle.label` then treats `margin >= confidentMargin (0.05)` as "the free ranker is confident" and trusts the top-1 as a gold label (oracle.go:88). A single-tool bank trivially produces a cosine ≥ 0.05 for almost any request, so the free tier auto-confirms the only tool for arbitrary mis-routed queries and persists a polluting exemplar — exactly the gravity-well amplification the two-tier gate exists to prevent. The same inflated value flows back to `isMisroute` as the disagreement signal.

**Fix:** Return a margin of 0 (or `ok=false`) when fewer than two tools are scored, so a single-tool corpus is treated as "uncertain" and escalates rather than auto-confirming:
```go
if len(scored) < 2 {
    return scored[0].Label, 0, true // no top-2 gap ⇒ not confident
}
margin := scored[0].Score - scored[1].Score
```

### WR-04: `Save` persists a node even when the embedding is empty

**File:** `internal/toolselectstore/store.go:91-102`
**Issue:**
`Save` writes the `:ToolSelectionExample` node unconditionally, including `embedding: vec` even when `vec` is empty/nil. `LoadExamples` then skips that row (`len(vec)==0`, store.go:73-75), so the node is permanently un-loadable dead data that still consumes the `hash`-keyed MERGE slot — and because `LabelAndSave` reports `saved=true` on a successful write, activelearn keeps the content hash in its seen-set (activelearn/learner.go:91-97), so the same query is never retried with a valid embedding. The toolselect `Observe` guards `len(vecs[0]) == 0` upstream (learner.go:82), so this is defense-in-depth today, but the store is a public seam and should not silently persist unrecoverable rows.

**Fix:** Reject an empty embedding at the store boundary so a bad write is retryable:
```go
func (s *Store) Save(ctx context.Context, query, tool string, vec []float64) error {
    if tool == "" || len(vec) == 0 {
        return fmt.Errorf("toolselectstore: refusing to save empty tool/embedding")
    }
    ...
}
```

### WR-05: Reasoning-tier self-improvement gate also silently governs tool-selection learning

**File:** `cmd/aura/chat.go:191-204,237-239`
**Issue:**
`toolSelectStore` (and therefore the entire tool-selection active-learning loop) is only constructed inside `if cfg.LLM.ReasoningLearning { ... }`. There is no env var named for tool-selection learning; it is silently coupled to `AURA_LLM_REASONING_LEARNING`. An operator who wants tool-selection self-improvement but not reasoning learning (or vice versa) cannot express that, and the coupling is undocumented at the config surface. This is a correctness-of-configuration gap: the feature's on/off condition does not match its name or its `AURA_TOOLSELECT_ORACLE` sub-gate, which only controls the *paid* tier, not whether the loop runs at all.

**Fix:** Either document explicitly (in config + CLAUDE.md env catalog) that tool-selection learning rides the reasoning-learning flag, or give it its own gate. If coupling is intended, add a comment at chat.go:193 stating the tool-selection loop has no independent enable and is governed by the reasoning flag.

### WR-06: Boot health-check embeds "healthcheck" through the production embed path without bounding non-timeout failures

**File:** `internal/runner/runner.go:253-258`
**Issue:**
The boot probe calls `embedder.Embed(ctx, []string{"healthcheck"})` with a 3s timeout context and logs on error — fine. But this runs on the synchronous boot path of every `aura chat`/`aura serve` start. If the sidecar is reachable-but-slow (TCP accepts, no response), the 3s ctx bounds it, so this is acceptable; however the probe result is discarded and never gates anything, so a sidecar that is up at boot but returns malformed/empty vectors is not detected — the first real turn surfaces it instead. Lower severity because it is explicitly best-effort by design, but the "operator sees the dependency" promise (runner.go:230-233) is weak: a 200-with-garbage sidecar logs nothing.

**Fix:** Validate the probe shape, not just the error, so a misconfigured-but-reachable sidecar is logged at boot:
```go
vecs, err := embedder.Embed(ctx, []string{"healthcheck"})
if err != nil || len(vecs) != 1 || len(vecs[0]) == 0 {
    slog.Warn("embed sidecar boot probe returned no usable vector; tool_search free-text ranking will error until it recovers", "error", err)
}
```

## Info

### IN-01: Post-`Close` `Observe` silently buffers into a drained channel

**File:** `internal/activelearn/learner.go:62-75,103-111`
**Issue:** After `Close()` cancels the ctx and the worker exits, `l.ch` is never closed. A late `Observe` does `select { case l.ch <- ...: default: }` — no send-on-closed panic (good), but a non-full buffer accepts the observation into a channel nobody drains, so it is silently lost rather than dropped at the gate. Harmless, but the "drop-on-full" mental model does not cover "drop-after-close".
**Fix:** Optionally guard `Observe` with an atomic `closed` flag set in `Close` so post-close observations short-circuit at the top, matching the documented drop semantics.

### IN-02: `learnedEpsilon` clamp is relative to each tool's own score, not the global ranking gap

**File:** `internal/agent/tools/search_learn.go:170-177`
**Issue:** The comment "never rank worse than the safe model" (search_learn.go:23-25) is true per-tool but the clamp `boost <= learnedEpsilon * s.Score` is computed against the candidate's own `desc_cos`, so a learned signal can still flip the top-1 (a 0.39-desc tool boosted to 0.49 overtakes a 0.40-desc tool with no learned centroid). This is the intended stage-2 behavior, but the inline comment overstates the guarantee. No code change required; tighten the comment to "never demote a tool below its own safe score" to avoid future readers assuming order-stability.
**Fix:** Reword the doc comment; no behavior change.

### IN-03: `confidentMargin` and activelearn `defaultMarginFloor` share the value 0.05 with unrelated meanings

**File:** `internal/toolselectlearn/oracle.go:29`, `internal/activelearn/activelearn.go:45`
**Issue:** `confidentMargin = 0.05` (free-vs-escalate top-2 cosine gap) and `defaultMarginFloor = 0.05` (activelearn enqueue gate) are numerically identical but semantically independent. A future tuner adjusting one may assume they are linked. Both are magic constants validated by different spikes (057 vs 053).
**Fix:** No change needed; a one-line comment noting the coincidence-not-coupling would prevent accidental "unification".

### IN-04: `fallbackTools` includes `text_response`, which can flag legitimate no-tool answers as mis-routes

**File:** `internal/toolselectlearn/detector.go:53-57,95-97`
**Issue:** `text_response` is in `fallbackTools`, so any turn that legitimately answered with prose (no capability tool needed — e.g. a greeting that slipped past the reasoning pre-filter) is flagged as a mis-route candidate and embedded/escalated. The downstream margin/oracle gates absorb most of these, but it widens the flagged set and feeds borderline exemplars into the loop. Spike-057 may have validated this; if so it is intentional.
**Fix:** Confirm spike-057 intended `text_response` as a fallback signal; if not, drop it from `fallbackTools`. No change if validated.

### IN-05: `anyInt` truncates `float64` token counts silently

**File:** `internal/runner/runner_persist.go:432-443`
**Issue:** `anyInt` converts a `float64` to `int` via a bare cast (`return int(n)`), truncating toward zero. Token counts arriving as JSON `float64` (the common wire shape) with any fractional component (shouldn't happen for counts, but the StateDelta is `UseNumber`-decoded and re-typed elsewhere) would silently truncate. Cosmetic for integer-valued counts; noted for completeness.
**Fix:** None required for integer counts; if defensiveness is wanted, `int(math.Round(n))`.
