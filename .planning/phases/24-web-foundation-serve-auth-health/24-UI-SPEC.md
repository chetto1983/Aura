# Phase 24 — UI Design Contract

> Visual and interaction contract for the Phase 24 frontend surfaces: the **login page** (WEB-03), the **read-only runtime health panel** (WEB-04), and the **SPA app shell + not-found view** (WEB-01). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This phase does NOT introduce a new visual language.** Phase 23 locked the dark-operator design system (`web/tokens/tokens.json` → Tailwind 4 `@theme` in `web/src/styles/theme.css`, decisions D-07/D-08). Every token below is the real, committed value — Phase 24 consumes it, it does not redefine it. The login page and health panel are the first *real product surfaces* rendered on that system.

## Spacing Scale

Spacing is **density-driven** via the locked CSS variable `--space-unit` (Phase 23 D-07). The default density is `operator` (`--space-unit: 4px`). The 8-point-derived scale below is the operator-tier rendering; `compact` multiplies by 3/4 (`--space-unit: 3px`) and `review` by 6/4 (`--space-unit: 6px`). Authors compose with Tailwind spacing utilities that resolve to multiples of `--space-unit`.

| Token | operator value | Usage |
|-------|----------------|-------|
| xs | 4px (`--space-unit` ×1) | Icon gaps, status-dot offset, inline chip padding |
| sm | 8px (×2) | Compact element spacing, form-row gaps, header `py-2` |
| md | 16px (×4) | Default element spacing, login card padding, panel `px-4` |
| lg | 24px (×6) | Section padding, gap between health rows groups |
| xl | 32px (×8) | Layout gaps, login card outer margin from viewport edge |
| 2xl | 48px (×12) | Vertical centering offset of the login card |
| 3xl | 64px (×16) | Page-level breathing room (rarely needed on these dense surfaces) |

Exceptions:
- **Interactive target floor 24×24px (WCAG 2.5.8 AA).** The login submit button, logout control, and any health-panel refresh/retry control must meet ≥24px; recommended comfortable size 44×44px for the primary login submit (touch). The `operator` row-height token is `--row-h: 32px` — use it as the control height floor on these surfaces.
- **Density tokens are NOT free spacing.** Do not introduce raw `px` paddings that bypass `--space-unit`; everything composes from it so `compact`/`review` reflow correctly (Phase 23 D-07 density contract).

## Typography

Type is **density-driven** via `--font-base` (operator = 13px). The roles below are the operator-tier rendering. There are exactly **4 sizes** and **2 weights** (regular 400 + medium 500), matching the existing `AppShell.tsx` conventions (`text-sm`, `text-xs`, `font-medium`).

| Role | Size (operator) | Weight | Line Height | Usage |
|------|-----------------|--------|-------------|-------|
| Display / Login title | 20px (1.25rem) | 500 (medium) | 1.2 | The single "Aura" / "Sign in" heading on the login card; the only large type on these surfaces |
| Heading / Panel title | 16px (1rem) | 500 (medium) | 1.3 | Health-panel section title ("Runtime"), 404 view heading |
| Body / Label | 13px (`--font-base`, `text-sm`) | 400 (regular); 500 for active nav/labels | 1.5 | Form labels, health-row labels, body copy, button text |
| Caption / Eyebrow | 11px (0.6875rem, `text-xs`) | 500 (medium), `uppercase tracking-wider` | 1.4 | Sidebar eyebrows (existing AppShell pattern), status sub-labels, field hints |

Rules:
- **Mono for machine values.** Bind address, build version, and any raw status string render in `--font-mono` at the Body size so they are visually distinct from prose (RESEARCH.md WEB-04 surfaces `cfg.AGUIBind` + `buildInfo()`).
- **Body line-height 1.5; headings 1.2–1.3.** No tighter — these are dense operator surfaces but must stay readable at the `compact` tier (12px base).
- **Sentence case, never ALL CAPS for content** (the eyebrow `uppercase` is a styling transform on short labels only, per the existing AppShell pattern).

## Color

The locked dark-operator palette (`web/tokens/tokens.json`, dark theme — the only theme this milestone ships). Applied before paint via the `web/index.html` `<head>` script (`data-theme="dark"`). The 60/30/10 split maps directly onto the existing surface tokens.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0B0E14` (`--color-bg`) | App background, login page backdrop, chat/main content area |
| Secondary (30%) | `#121620` (`--color-surface`) + `#1A1F2B` (`--color-surface-2`) | Cards, sidebar, health panel surface, nav, login card; `surface-2` for raised/active rows (active nav item, hovered health row) |
| Accent (10%) | `#5BA8FF` (`--color-accent`) | See reserved-for list below |
| Destructive | `#E5484D` (`--color-danger`) | Login failure message, session-expired notice, future destructive confirmations |

Supporting semantic tokens (status only — NOT accents):
- `#3FB37F` (`--color-success`) — a healthy `/healthz`/`/readyz`/dependency status dot + label.
- `#E0A23C` (`--color-warning`) — a degraded/not-ready dependency, or a fail-fast-config warning surfaced in the UI.
- `#5BA8FF` (`--color-info`) — informational status (same hex as accent; use the `info` token name in status contexts for intent clarity).

Text tokens (not a 60/30/10 slot, but locked): `#E6E9EF` (`text`), `#9AA4B2` (`text-muted`), `#5B6675` (`text-faint`).

Borders/radius: `#2A3140` (`--color-border`); radii `sm 4px` / `md 6px` / `lg 10px` (login card = `lg`, controls/rows = `md`, chips/dots = `sm`).

**Accent (`#5BA8FF`) reserved for — explicit list (never "all interactive elements"):**
1. The **login submit button** (primary CTA) — solid accent fill, `#0B0E14` text for contrast.
2. The **focus-visible ring** on interactive controls (`:focus-visible` outline; verify ≥3:1 against `--color-surface` and `--color-bg` — `#5BA8FF` on `#0B0E14` passes).
3. The **active primary-nav mode** indicator in the app-shell header (currently `surface-2` background per `AppShell.tsx`; accent reserved for the active text/underline if an emphasis is added).
4. A **healthy-status link/affordance** in the health panel (e.g. "View details" if added later) — text accent only.

Accent is NOT used for: every link, every border, body text, status dots (those use `success/warning/danger`), or decorative fills. The cockpit's trust signal is **status color + provenance**, not accent saturation (ux-spec §147 "industrial / less decorative").

Contrast (WCAG AA, dark theme):
- Body `#E6E9EF` on `#0B0E14` and on `#121620` — passes 4.5:1.
- `text-muted #9AA4B2` on `#0B0E14` — use for ≥13px body only (passes AA for normal text); do NOT use `text-faint #5B6675` for essential content (it is an eyebrow/decorative tone, ~3:1).
- Accent button text: use `#0B0E14` (near-black) ON `#5BA8FF`, not white-on-accent.
- **Never color-only signaling** (WCAG 1.4.1): every status dot pairs with a text label ("Ready" / "Degraded" / "Down"), and the login error pairs `#E5484D` with an icon + text and `role="alert"`.

## Copywriting Contract

Operator-facing, plain, active voice (frontend-design skill: "active voice as default", "errors don't apologize"). English-only UI strings per project convention. Honors the ux-spec Copy Contract — **no marketing hero text, no decorative badges, no tutorial paragraphs** in the primary viewport.

### Login page (WEB-03)

| Element | Copy |
|---------|------|
| Page/card title | `Aura` (brand, from `public/Logo.png` lockup) with a sub-line `Sign in to continue` |
| Field label | `Operator passphrase` (the `AURA_WEB_AUTH_SECRET` value; do NOT call it "password" — it is the operator secret, not a per-user account) |
| Field hint (caption) | `Required when Aura is exposed beyond loopback.` |
| Primary CTA | `Sign in` (button text; the action keeps this name through the flow — frontend-design "an action keeps the same name") |
| In-flight CTA state | `Signing in…` (disabled, non-blocking) |
| Error — wrong passphrase | `That passphrase didn't match. Check it and try again.` (`role="alert"`, `#E5484D`; never reveal whether the secret is set, never echo the entered value) |
| Error — auth not configured (secret empty server-side) | `Sign-in isn't available — this Aura instance has no operator passphrase configured.` (fail-closed posture from RESEARCH `validateSecret`; shown only if a login is attempted against an unconfigured instance) |
| Error — network/server | `Couldn't reach Aura. Check the server is running and try again.` |

### Runtime health panel (WEB-04)

| Element | Copy |
|---------|------|
| Panel title | `Runtime` |
| Row labels | `Liveness` (→ `/healthz`), `Readiness` (→ `/readyz`), `Postgres`, `Neo4j`, `Bind address`, `Build` |
| Healthy status | `Ready` (success dot) — for `/readyz` and dependencies; `Live` for `/healthz` |
| Degraded status | `Degraded` (warning dot) — readiness probe reports a dependency not ready |
| Down status | `Unavailable` (danger dot) — endpoint returned non-2xx or unreachable |
| Empty / loading state | `Checking runtime…` (while the first React Query poll is in flight; a quiet skeleton, not a spinner storm) |
| Error state (panel-level, all probes unreachable) | `Can't read runtime status. The health endpoints aren't responding — the server may be starting or down.` |
| Stale-data note | `Last checked {relative time}` (caption under the panel; React Query `dataUpdatedAt`) |

### App shell / not-found (WEB-01)

| Element | Copy |
|---------|------|
| 404 client-route view heading | `Page not found` |
| 404 body + next step | `That cockpit page doesn't exist. Return to the dashboard.` with a `Return to dashboard` link (client-route back to `/`). NOTE: this is the SPA's *client-side* 404 for unknown React Router routes — it is NOT the server's real API 404 (RESEARCH Pitfall 1: API/`/api/`/`/agent`/health prefixes return a real server 404, never this view). |
| Session-expired (caught by `RequireAuth` redirect) | On redirect to login show `Your session expired. Sign in again to continue.` (caption above the form; `#E0A23C` warning tone, not an error — it's expected) |

### Destructive actions

| Action | Confirmation approach |
|--------|----------------------|
| **Log out** (the only state-changing user action this phase) | Direct action, **no modal** — logging out is reversible (sign back in) and low-risk. Button `Log out`; on success redirect to login with no confirmation dialog. Per frontend-design: don't gate low-risk reversible actions behind ceremony. |

There are **no DESTRUCTIVE (irreversible) actions** in Phase 24. Governance writes, MCP/skill removal, and `/agent/run` mutations with confirmation land in Phases 25/28/29 — out of scope here (CONTEXT.md `<deferred>`).

## Interaction & Accessibility Contract

This phase ships the **first authenticated, keyboard-reachable product surfaces**, so the a11y floor is contractual (accessibility skill, WCAG 2.2 AA):

- **Login form (WCAG 3.3.2 / 3.3.8):** the passphrase input has a programmatically associated `<label>`; `type="password"` with `autocomplete="current-password"` so password managers/paste work (3.3.8 accessible authentication — no cognitive-test gate). Submit is a native `<button type="submit">` inside a `<form>` so Enter submits.
- **Error announcement (3.3.1):** login + panel errors render in a `role="alert"` / `aria-live="assertive"` region, set `aria-invalid="true"` on the field, and move focus to the first error on failed submit.
- **Focus visible (2.4.7):** `:focus-visible` outline `2px solid var(--color-accent)` with `outline-offset: 2px`; never `outline: none` without a replacement. Verify the ring ≥3:1 on both `--color-bg` and `--color-surface`.
- **Status not color-only (1.4.1):** every health status pairs a colored dot with a text label; never the dot alone.
- **Target size (2.5.8):** interactive controls ≥24×24px; primary login submit ≥44px tall (use `--row-h`).
- **Reduced motion (2.3):** any login/panel transition respects `@media (prefers-reduced-motion: reduce)`; the theme/density apply-before-paint script (Phase 23 D-08) must not animate.
- **Page language (3.1.1):** `<html lang="en">` already set in `web/index.html` — keep it.
- **Landmark/heading order (1.3.1):** login card uses a single `<h1>`; the health panel title is an `<h2>` under the shell's heading hierarchy; the app shell already exposes `header`/`nav`/`main`/`aside` landmarks (`AppShell.tsx`).
- **No flash (FND-04 / D-08):** theme + density apply before React mounts; the login page and health panel inherit `data-theme="dark"`/`data-density="operator"` from the root — they must render correctly on first paint with no light-mode flash.
