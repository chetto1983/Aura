# Phase 45.1: Native MCP client - Research

**Researched:** 2026-08-16
**Domain:** MCP client/transport migration (Go SDK v1.7.0 client-side adoption)
**Confidence:** HIGH for SDK API surface (read directly from the pinned module-cache source
tree, `C:/Users/chett/go/pkg/mod/github.com/modelcontextprotocol/go-sdk@v1.7.0`, which is the
literal artifact `go build` uses); HIGH for Aura's current tree (read directly); MEDIUM-LOW for
the actual negotiated protocol version and keepalive/reconnect behaviour of the two Python-based
sidecar forks (`aura-pim-mcp`, `whatsapp-mcp`), which live outside this repo and were not
fetched — flagged explicitly below as needing a live probe.

This research corrects three claims in `45.1-CONTEXT.md` / `REQUIREMENTS.md` against the pinned
SDK source. They are not small wording issues — they change what the plan must build. See
**Corrections** immediately after the Summary.

## Summary

The SDK client half (`github.com/modelcontextprotocol/go-sdk@v1.7.0/mcp`) is a complete,
production-grade MCP client: `NewClient`/`Connect`, two transports (`CommandTransport` for
stdio, `StreamableClientTransport` for HTTP with an injectable `*http.Client`), a sending/
receiving middleware chain (`AddSendingMiddleware`), `_meta` plumbing built into every `Params`
type via an embedded `Meta map[string]any`, an in-memory transport pair for daemon-free tests
(`NewInMemoryTransports`), and the full 2026-07-28 stateless core Aura's own `cmd/arcadedb-mcp`
already speaks server-side. The migration described in `45.1-CONTEXT.md` is directionally sound
and the bulk of the ≈1,970 LOC deletion is real and safe.

Three things need correcting before planning, all found by reading the actual source rather than
inferring from doc comments or the roadmap:

1. **`ClientOptions.KeepAlive` is a documented no-op for the exact protocol version Aura's own
   `cmd/arcadedb-mcp` negotiates.** It cannot be `bridge_ping.go`'s "wholesale" replacement for
   that server. `bridge_ping.go`'s poll-loop *shape* survives; only its call target changes.
2. **The SDK does not "auto-fulfill" elicitation/sampling/roots requests when no handler is
   registered — it fails the call with an error.** Aura's current posture (no `ElicitationHandler`)
   is already fail-closed, not "permissive-by-omission." This does not change the decision to add
   a handler (D-102/MCPC-05 still stands on its own merits), but the stated *reason* for it is
   wrong and should not be carried into the plan's rationale.
3. **The "automatic reconnect with exponential backoff" cited from `streamable_client.go:122-139`
   is a design-doc comment describing the *standalone SSE stream*, which is unconditionally
   removed under the 2026-07-28 protocol Aura's own server negotiates** (`streamable.go:2095-2098`,
   an explicit `if` in the shipped code, not a comment). Under that protocol, "recovery from a
   killed sidecar" works for an entirely different reason: every `ClientSession` call is a fresh
   HTTP POST (`streamable.go:2244-2269`), so a killed-then-restarted sidecar is simply reachable
   again on the *next* call — no reconnect state machine runs or is needed. This still satisfies
   Success Criterion 3, but the mechanism claimed and the mechanism that actually fires are
   different, and the plan's verification step should assert the right one.

**Primary recommendation:** Build the swap exactly as scoped in `45.1-CONTEXT.md` (D-100..D-111),
but (a) keep `bridge_ping.go`'s poll-loop, retargeted at `ClientSession.Ping`, gated on a live
per-server protocol-version probe rather than deleted outright; (b) drop the "permissive-by-
omission" framing from MCPC-05's rationale — the elicitation handler is still worth building, for
a different and better reason (SEP-2322 compliance and giving the operator visibility, not
"closing a hole"); and (c) treat `domain_outcome.go`'s and `tool_error.go`'s re-attachment to the
SDK's typed `CallToolResult` as a concrete, non-trivial task in its own right, not an incidental
part of "policy re-attaches unchanged."

## Corrections to `45.1-CONTEXT.md` / ROADMAP (read this before planning)

### Correction 1 — `KeepAlive` does not work on the protocol Aura's own server speaks

> **⚠ SUPERSEDED 2026-08-16 by § SDK liveness surface — full enumeration (below).** The *conclusion*
> of Correction 1 holds — `KeepAlive` is inert against a 2026-07-28 peer — but the **mechanism stated
> here is wrong**, and the mechanism is what the plan depends on. There is **no client-side protocol
> gate**: `client.go:403` is a bare `if c.opts.KeepAlive > 0 { cs.startKeepalive(...) }`. The
> keepalive goroutine starts, its first `ping` is refused by the peer, and it then **silently retires
> itself**. Correction 1's recommendation (retain `bridge_ping.go`'s poll loop, retargeted) is also
> **withdrawn** — the enumeration found a native push-based death signal that makes any poll loop
> unnecessary. Read the enumeration section, not this one, when planning.

`ClientOptions.KeepAlive` (`mcp/client.go:195-199`):

```go
// If non-zero, defines an interval for regular "ping" requests.
// If the peer fails to respond to pings originating from the keepalive check,
// the session is automatically closed.
// NOTE: The keepalive feature is only available for protocol versions < 2026-07-28
KeepAlive time.Duration
```
`[VERIFIED: go-sdk@v1.7.0 mcp/client.go:195-199]`

Aura negotiates protocol version by trying `server/discover` (SEP-2575) first
(`mcp/client.go:318-377`); `cmd/arcadedb-mcp` is built with the *same* pinned SDK
(`cmd/arcadedb-mcp/main.go:9,171`, `mcp.NewServer(&mcp.Implementation{...})`) and, with no
version override configured, will accept `server/discover` and negotiate to
`latestProtocolVersion = "2026-07-28"` (`mcp/shared.go:50-51`). So for the memory server —
the one that had the F-013-adjacent 0-tools boot race and the one D-108's `_meta` cutover
targets — `KeepAlive` is a documented no-op. `bridge_ping.go` (`internal/agent/mcptools/
bridge_ping.go:12-20`) exists precisely because "a dead server is otherwise discovered only when
a tool call fails mid-run" — losing it for the memory server silently reintroduces exactly the
gap it was written to close.

**The two other built-in recipes may differ.** `compose.yaml:815,994` shows
`ghcr.io/chetto1983/whatsapp-mcp:sidecar` and `ghcr.io/chetto1983/aura-pim-mcp:sidecar` are
externally-built images (forks Aura controls, per D-17, but not built from this Go module), and
`internal/mcp/tool_error.go:96-113`'s comment references "FastMCP" and "Pydantic" by name for the
WhatsApp server — i.e. that sidecar is very likely a Python MCP SDK, not this Go SDK. Python MCP
SDKs have historically lagged the newest protocol revisions; if either sidecar does not implement
`server/discover`, the client falls back to the legacy `initialize` handshake capped at
`protocolVersion20251125` (`mcp/client.go:371-377`, `mcp/shared.go:72-78`) — **and `KeepAlive`
would work correctly for that server.** `[ASSUMED]` — not verified against the actual sidecar
source, which is outside this repo. **This is a live-probe item for the planner/executor**: after
step 1 of D-111 lands, log the negotiated `InitializeResult.ProtocolVersion` per mounted server
(`ClientSession.InitializeResult()`, `mcp/client.go:506`) and decide `bridge_ping.go`'s fate (or a
narrower per-server KeepAlive config) from the actual, not assumed, fleet.

**Recommendation:** Do not delete `bridge_ping.go` as a blanket "the SDK replaces it." Retarget
its poll goroutine to call `ClientSession.Ping(ctx, nil)` (`mcp/client.go:1221-1225`, a plain RPC,
works on every protocol version) instead of Aura's own `Client.Ping`. This is a small, mechanical
change (the function signature Aura calls today is already `Ping(ctx) error`; the SDK's is
`Ping(ctx, *PingParams) error`), not a deletion. Set `ClientOptions.KeepAlive` too, for the
sidecars where it turns out to be live — it costs nothing and gives the SDK's own session-closing
behavior as a second signal where the protocol version supports it.

### Correction 2 — the SDK fails closed on unhandled elicitation, it does not auto-accept

The phase description states: *"The SDK auto-fulfills input requests by default and Aura
registers no handler today, so the current posture is permissive-by-omission."* This is not what
the code does.

MRTR (`ClientOptions.MultiRoundTrip`) is enabled by default (`mcp/client.go:79-81`) and its
sending middleware (`clientMultiRoundTripMiddleware`, `mcp/mrtr.go:73-115`) does retry the call
after invoking a handler — but the handler invocation for elicitation is:

```go
func (c *Client) elicit(ctx context.Context, req *ElicitRequest) (*ElicitResult, error) {
    if c.opts.ElicitationHandler == nil {
        return nil, &jsonrpc.Error{Code: jsonrpc.CodeInvalidParams, Message: "client does not support elicitation"}
    }
    ...
```
`[VERIFIED: go-sdk@v1.7.0 mcp/client.go:862-865]`

`fulfillInputRequest` (`mcp/mrtr.go:255-268`) calls exactly this for an `*ElicitParams` entry,
and `fulfillInputRequests` (`mcp/mrtr.go:233-253`) propagates any handler error through an
`errgroup`, which `clientMultiRoundTripMiddleware` then returns as the `CallTool`/`GetPrompt`/
`ReadResource` error (`mcp/mrtr.go:107-110`, `if err != nil { return nil, err }`). **A server-
initiated elicitation with no `ElicitationHandler` registered fails the whole tool call with an
error — it is never silently approved.** The same pattern holds for `CreateMessage` (sampling,
`mcp/client.go:749-756`, `"client does not support CreateMessage"`).

Separately: `Client.capabilities()` (`mcp/client.go:255-298`) only advertises the elicitation
capability when `ElicitationHandler != nil`. A spec-compliant server should not attempt
server-initiated elicitation against a client that never declared support for it — so in
practice, without a handler, a well-behaved server should not even try, and if a
badly-behaved one does, the call errors rather than silently succeeding.

**Consequence for the plan:** MCPC-05 is still worth building (SEP-2322 compliance; giving the
operator visibility into a server's mid-call question instead of a bare error; hermes parity per
D-15/D-102) — but its rationale in the plan should read "gives Aura a *working* path for a
capability that today hard-fails" rather than "closes a permissive-by-default hole." No security
posture actually regresses by deferring this to a later commit within the phase, since a call
that would otherwise silently succeed cannot happen — it errors either way. `[VERIFIED: go-sdk@v1.7.0
mcp/client.go:862-913, mcp/mrtr.go:107-115,233-268]`

### Correction 3 — "automatic reconnect" is the standalone SSE stream, and it is removed under 2026-07-28

The design-doc comment CONTEXT.md cites (`streamable_client.go:122-139`) describes the
**standalone SSE stream** — a persistent background `GET` connection a legacy (<2026-07-28)
streamable-HTTP client keeps open so the server can push messages without the client first
POSTing. The shipped code that decides whether to open it:

```go
func (c *streamableClientConn) sessionUpdated(state clientSessionState) {
    ...
    // Under SEP-2575 (protocol version >= 2026-07-28) the standalone HTTP GET
    // SSE stream is removed.
    if state.InitializeResult == nil ||
        state.InitializeResult.ProtocolVersion >= protocolVersion20260728 {
        return
    }
    if !c.disableStandaloneSSE {
        c.connectStandaloneSSE()
    }
}
```
`[VERIFIED: go-sdk@v1.7.0 mcp/streamable.go:2090-2118]`

So for a server (like `cmd/arcadedb-mcp`) that negotiates 2026-07-28, there is **no persistent
connection to lose and no reconnect loop to run** between calls. What actually delivers
Success Criterion 3 ("killing a sidecar mid-conversation and restarting it recovers ... live"):
`streamableClientConn.Write` issues a fresh `http.NewRequestWithContext` + `c.client.Do(req)`
**per outgoing message** (`mcp/streamable.go:2244-2269`); a `client.Do` failure is wrapped with
`jsonrpc2.ErrRejected` specifically so the jsonrpc2 layer does **not** mark the whole connection
broken (`mcp/streamable.go:2262-2267`, comment: *"Any error from client.Do means the request
didn't reach the server ... so the jsonrpc2 connection doesn't set writeErr and permanently break
the connection"*). The **next** `CallTool` after the sidecar comes back up is simply a new POST
that succeeds. There is no state to resynchronize because the 2026-07-28 protocol is stateless
(SEP-2567 removes `Mcp-Session-Id`; `mcp/client.go:511-514`, `usesNewProtocol()`).

For `CommandTransport` (stdio), this doesn't apply at all — `Connect` starts the subprocess once
and there is no retry mechanism anywhere in `mcp/cmd.go` (confirmed: the whole file is 109 lines,
`Connect` at `mcp/cmd.go:29-47`, nothing else touches process lifecycle beyond `pipeRWC.Close`'s
graceful-shutdown sequence). This fully confirms D-105 as written.

**Consequence for the plan:** SC#3's live verification step should kill and restart the sidecar
container and then issue a **new** tool call, and should NOT expect to observe any log line about
"reconnecting" for a 2026-07-28-negotiated server — there won't be one, by design. If the plan's
verification narrative describes watching a reconnect happen, rewrite it to describe watching the
next call simply succeed.

### Finding A — `KeepAlive` is not version-gated; it is silently refused and self-retires

The doc comment says *"only available for protocol versions < 2026-07-28"*. The shipped code tells a
different and more useful story:

1. **No client-side gate.** `client.go:403-404` — `if c.opts.KeepAlive > 0 { cs.startKeepalive(c.opts.KeepAlive) }`.
   Nothing consults the negotiated version. The goroutine starts against any peer.
2. **The server refuses it.** `server.go:1879-1887` — an SDK-built server hits
   `case methodInitialize, methodPing, notificationInitialized, …:` and, `if validatedMeta.usesNewProtocol`,
   returns `jsonrpc.CodeMethodNotFound` with `"%q is not supported in the new protocol"`.
   `methodPing` is otherwise a fully registered server method (`server.go:1785`).
3. **The client quietly gives up.** `shared.go:869-872` — inside the keepalive loop,
   `if errors.Is(err, jsonrpc2.ErrMethodNotFound) { return }`, commented *"Peer doesn't support ping,
   stop the keepalive process."* No session close, no error raised to the host.

**Consequence, and it is a trap worth naming in the plan:** setting `KeepAlive` against a
2026-07-28 peer produces a configuration that *looks* live in code review and does nothing at
runtime, logging only on the **server** side. Do not set it as a liveness mechanism for
`cmd/arcadedb-mcp`. (It remains correct for a peer that negotiates below 2026-07-28 — see the still-open
question on the two external sidecars.)

For completeness, `startKeepalive` (`shared.go:841-890`) is a competent implementation — ticker,
per-ping timeout of `interval/2`, consecutive-failure threshold, structured warn/error logging. It is
strictly better than a hand-rolled loop **where ping is answered at all**.

### Finding B — the native death signal is push, not poll: `ClientSession.Wait()`

The complete exported `*ClientSession` surface (v1.7.0 `mcp/client.go`), liveness-relevant rows:

| Method | Line | What it gives |
|---|---|---|
| `Wait() error` | `client.go:584` | **Blocks until the connection is closed and returns why.** Delegates to `cs.conn.Wait()`. |
| `Close() error` | `client.go:559` | Graceful close; idempotent and concurrency-safe; cancels keepalive, listeners and resource subscriptions. |
| `Ping(ctx, *PingParams) error` | `client.go:1222` | Active probe — refused by 2026-07-28 SDK servers (Finding A). |
| `ID() string` | `client.go:547` | Session id where the transport has one. |
| `InitializeResult() *InitializeResult` | `client.go:506` | Carries `.ProtocolVersion` — **the negotiated version is a field read.** |
| `ListTools` / `CallTool` / `Tools(…) iter.Seq2` | `1259` / `1280` / `1551` | The call surface `bridge.go` re-points onto. |

`Wait()` is the answer to the operator's question. One goroutine per session, blocked on `Wait()`,
delivers session death **when it happens** — no interval, no missed-window, no ping that the peer is
entitled to refuse. It is strictly more accurate than a poll and it is roughly one goroutine of code.

### Verdict — no Aura poll loop is needed (option (a))

- **`bridge_ping.go` (113 LOC) deletes outright.** Its job — notice that a server died — is done by
  `Wait()`, natively and sooner. **SC#2 stands exactly as written**; no amendment needed, and
  Correction 1's "retain the poll loop" recommendation is withdrawn.
- **Open Question #4 dissolves.** "What protocol version do `aura-pim-mcp` and `whatsapp-mcp`
  negotiate?" needs no live spike: log `session.InitializeResult().ProtocolVersion` at connect for
  every mounted server. It becomes one observability line, and it is worth keeping permanently —
  it is the fact that decides whether any peer could still use `KeepAlive`.
- **What legitimately remains Aura's** is *redial policy*: `Wait()` reports the death, but deciding
  whether/when/how often to redial, and with what backoff, is a supervision decision no MCP library
  can make for a host. `reconnectingServer` already owns that. Being honest about which side of the
  operator's line this falls on: **a supervisor that redials is policy, not protocol** — it contains
  no JSON-RPC framing, no session model, no wire handling. It is permitted. A reimplementation of
  ping/keepalive/session-state would not be, and is no longer proposed.

### Finding C — `_meta` is first-class, and the SDK already writes to it

- `Meta map[string]any` with `GetMeta()`/`SetMeta()` is embedded in **every** `Params` type
  (`shared.go:483-490`; the `Params` interface at `shared.go:738-740`).
- `injectRequestMeta` (`client.go:522`) stamps the SEP-2575 triple on every outgoing request under
  the new protocol: `MetaKeyProtocolVersion` = `io.modelcontextprotocol/protocolVersion`,
  `MetaKeyClientInfo`, `MetaKeyClientCapabilities` (`protocol.go:2363-2369`).
- **Crucially: `"Keys already present in params.Meta are not overwritten"`** (`client.go:~527`). So
  Aura's identity key coexists with the SDK's own triple without contention — MCPC-04's `_meta`
  channel is additive, and Aura's pre-existing `_meta["aura"]` namespacing convention
  (`internal/mcp/tool_methods.go:27-40`) carries over unchanged.
- **Server-side accessor** (for the D-108 fail-closed guard the operator chose): the exported path is
  `req.Params.GetMeta()` on the handler's `*mcp.CallToolRequest`. A tool-error rejection is returned
  as `&mcp.CallToolResult{IsError: true, Content: …}` — **not** a Go `error`, which would become a
  protocol-level error instead (`CallToolResult.IsError` doc, `protocol.go`: *"Any errors that
  originate from the tool should be reported inside the Content field, with IsError set to true, not
  as an MCP protocol-level error response"*).

### Finding D — transports, and what they do not do

- `StreamableClientTransport{Endpoint string; HTTPClient *http.Client; MaxRetries int; DisableStandaloneSSE bool; OAuthHandler}`
  (`streamable.go`). `MaxRetries` defaults to 5, negative disables. **`HTTPClient` is a plain
  `*http.Client`** — `newHardenedHTTPClient` (`internal/mcp/transport_ssrf.go:41-51`) drops in with
  no adapter, confirming MCPC-02's re-attachment point.
- `CommandTransport{Command *exec.Cmd; TerminateDuration time.Duration}` (`cmd.go`) — **two fields.**
  There is no respawn, no restart policy, no supervision. **This confirms D-105 as written**: a dead
  stdio child stays dead until the host redials.
- `NewInMemoryTransports() (*InMemoryTransport, *InMemoryTransport)` (`transport.go:160-163`) — a
  `net.Pipe()` pair. Yields a **real** `*ClientSession`, so dropping the `Server` interface (the
  operator's decision on Open Question #1) costs nothing in testability: daemon-free tests bind a
  real client to a real in-process server. This is now load-bearing and it holds.

### Finding E — elicitation fails closed (confirms Correction 2, exact shape)

`client.go:862-864`: with no `ElicitationHandler`, `c.elicit` returns
`&jsonrpc.Error{Code: jsonrpc.CodeInvalidParams, Message: "client does not support elicitation"}`.
The SDK does **not** auto-fulfill. Aura's current posture is already fail-closed; MCPC-05's
*rationale* must be rewritten (SEP-2322 compliance + operator visibility), though the requirement
itself stands.

### Pattern 1: HTTP transport with policy re-attached as a custom `*http.Client`

**What:** `StreamableClientTransport.HTTPClient *http.Client` is the injection point for SSRF/
egress policy. No wrapper type is needed — Aura's existing `newHardenedHTTPClient` already
returns the right shape.

**When to use:** Every streamable-HTTP mount (all three built-in recipes today; any future
operator-added HTTP server).

**Example:**
```go
// Source: mcp/streamable.go:1933-1970 (StreamableClientTransport fields, HTTPClient *http.Client)
//         internal/mcp/transport_ssrf.go:41-51 (existing newHardenedHTTPClient, unchanged)
policy := mcp.RuntimeEgressPolicy(strictProfile, server) // unchanged, internal/mcp/egress_policy.go:57-59

}

transport := &sdkmcp.StreamableClientTransport{

session, err := client.Connect(ctx, transport, nil)
```

### Pattern 2: `_meta` identity + idempotency stamping via `AddSendingMiddleware`

**What:** Both host-side derived fields Aura injects today (`user_identifier` argument today,
`_meta.aura.operation_key/...` already via `_meta`) become one middleware.

**When to use:** Registered once per `Client` at construction, applies to every session/call.

**Example:**
```go
// Source: mcp/client.go:1120-1133 (AddSendingMiddleware, ordering: first arg runs first)
// Source: mcp/shared.go:110 (Middleware func(MethodHandler) MethodHandler)
func identityMiddleware(identityKey string) mcp.Middleware {
    return func(next mcp.MethodHandler) mcp.MethodHandler {
        return func(ctx context.Context, method string, req mcp.Request) (mcp.Result, error) {
            if method != "tools/call" {
                return next(ctx, method, req)
            }
            params, ok := req.GetParams().(*mcp.CallToolParams)
            if !ok {
                return next(ctx, method, req)
            }
            m := params.GetMeta()
            if m == nil {
                m = map[string]any{}
            }
            m[identityMetaKey] = identityctx.IdentityID(ctx) // custom key, NOT one of the
            params.SetMeta(m)                                 // SDK's reserved MetaKeyXxx constants
            return next(ctx, method, req)
        }
    }
}
client.AddSendingMiddleware(identityMiddleware(auraIdentityMetaKey))
```
Server side, `cmd/arcadedb-mcp`'s tool handler receives this through
`request.Params.GetMeta()[auraIdentityMetaKey]` (`CallToolRequest = ServerRequest[*CallToolParamsRaw]`,
`requests.go:10`; `CallToolParamsRaw` embeds `Meta`, `protocol.go:238-245`).

### Anti-Patterns to Avoid

- **A translation-layer `Server` interface that still speaks Aura's `mcp.ToolDef`/`(string,
  error)` shape.** D-103 forbids this outright — it would be exactly the facade the operator
  directive removed. The narrow interface at `bridge.go:27-32` must be reshaped to the SDK's own
  types (`*sdkmcp.Tool`, `*sdkmcp.CallToolResult`), not kept as an Aura-flavored abstraction over
  them. See Open Questions #1 for the two viable shapes.
- **Relying on `ClientOptions.KeepAlive` as the sole liveness signal for a server on the
  2026-07-28 protocol.** It is a documented no-op there (Correction 1).
- **Assuming a missing `ElicitationHandler` is a security gap to close.** It already fails
  closed (Correction 2); building the handler is about UX/spec-compliance, not closing a hole.

| Daemon-free MCP round-trip tests | Fake `Server` interface implementations, hand-mocked JSON | `mcp.NewInMemoryTransports()` (`mcp/transport.go:154-162`) — construct a real client+server pair over an in-process pipe | Exercises the SDK's actual wire encode/decode, not a hand-maintained stub; directly satisfies D-110's coverage-floor requirement |

**Key insight:** Every mechanical piece of MCPC-03's deletion list (framing, pagination,
reconnect, in-memory testing) is already built and better-tested in the SDK than Aura's
hand-rolled equivalent. The one place a genuine Aura-specific translation is needed —
tool-result → typed domain outcome → Go error — has no SDK equivalent and must be explicitly
re-plumbed, not assumed to "just re-attach."

## Common Pitfalls

### Pitfall 1: Deleting `decodeToolResult`'s content-extraction logic with `client.go` and losing the domain-outcome chain silently

**What goes wrong:** `tool_methods.go:45-51` (on the deletion list) is the *only* current call
site for `decodeToolResult` (client.go, deleted) → `decodeToolCallError` (tool_error.go,
preserved but currently unexported and only called from the deleted file). If the plan deletes
`tool_methods.go`/`client.go` without explicitly re-plumbing this chain, `domain_outcome.go`'s
false-negative detection (a tool that returns `isError=false` but a `{"success": false}` payload)
and `tool_error.go`'s stable `ToolOutcome`/`ToolEffect` vocabulary silently stop firing — every
MCP tool error degrades to a generic Go error string, and `llm_agent_retry.go:181`'s
`var toolCallErr *mcp.ToolCallError` type-assertion (used for retry/idempotency-effect decisions
per HARN-01..09) stops matching, silently changing Phase 45's already-shipped retry semantics.

**Why it happens:** The deletion list (`client.go`, `http_client.go`, `tool_methods.go`) and the
preservation list (`tool_error.go`, `domain_outcome.go`) are drawn at the file level, but the
actual call graph crosses that boundary at one specific, easy-to-miss function pair.

**How to avoid:** Explicitly plan a task that (1) exports `decodeToolCallError` (or a thin
package-level wrapper) from `internal/mcp`, (2) writes a new text/structured-content extractor
against the SDK's `CallToolResult.Content []Content` / `.StructuredContent` / `.IsError`
(iterate `Content`, type-assert `*mcp.TextContent`, concatenate `.Text` — mirrors
`decodeToolResult`'s current logic exactly, just against typed fields instead of raw JSON), and
(3) calls both from `bridgedTool.Execute`'s new result-handling path. Write a test asserting
`llm_agent_retry.go`'s `*mcp.ToolCallError` type-assertion still matches post-swap.

**Warning signs:** A tool call that used to surface `mcp "memory": tool memory_upsert_fact
rejected: ...` now surfaces a bare "unexpected error" string; `TestMain`'s goleak pass is green
but a retry-semantics test that checks `DeterministicNoEffect()` starts failing.

### Pitfall 2: The `ToolIdentityArgument` fail-closed transport guard has no stated `_meta` successor

**What goes wrong:** `internal/mcp/http_client.go:44-53`'s `HTTPConfig.ToolIdentityArgument`
today is a **transport-level** fail-closed guard: a call to the memory server without a
`user_identifier` argument never reaches the network, specifically to protect against "a
readiness probe building its map literally" or "any future direct caller" bypassing the bridge's
injection. D-108 removes `user_identifier` as an argument and moves identity to `_meta` — but the
CONTEXT.md decisions do not specify an equivalent presence-check for the `_meta` path. Without
one, a bug in the new `AddSendingMiddleware` identity injector (or a caller that constructs a
`*CallToolParams` directly, bypassing the middleware chain entirely — which is possible, since
middleware wraps `Client`, not the type) could silently reach `cmd/arcadedb-mcp` with no identity
`_meta` key at all.

**Why it happens:** D-108's discussion focuses on the *dual-source* hazard (a fallback that could
select the wrong database) and correctly rejects it — but "no fallback" is not the same claim as
"still fail-closed if absent entirely." These are two different requirements that got conflated
in the discussion.

**How to avoid:** This is a genuine open question, not a research-time answer — flag it for the
plan/discuss layer rather than deciding it here (see Open Questions #3). At minimum, `cmd/
arcadedb-mcp`'s tool handlers should reject a call whose identity `_meta` key is absent/empty with
a clear MCP tool-error (not silently proceed with an empty identity, which per the schema comment
at `tool_memory.go:27` — *"each identity has its own database and cannot reach another's"* —
would be a correctness bug, not merely a missing feature).

**Warning signs:** A test that constructs a `*CallToolParams` bypassing the middleware chain and
expects a clean rejection instead gets a call that reaches the server with no identity.

### Pitfall 3: Mixed-fleet protocol version assumptions

**What goes wrong:** The plan (and CONTEXT.md's D-105 evidence) treats "all three built-in
recipes are streamable-HTTP" as sufficient to conclude they behave uniformly under the SDK swap.
Transport shape is uniform; **negotiated protocol version is not necessarily uniform** — see
Correction 1. A plan that assumes `KeepAlive`/reconnect behavior is identical across
`cmd/arcadedb-mcp` (Go SDK, negotiates 2026-07-28) and `aura-pim-mcp`/`whatsapp-mcp` (external
forks, likely Python, unverified negotiated version) risks a false "it works" from testing only
against the memory server.

**Why it happens:** The three recipes are grouped together in `catalog.go:131,144,165` as "the
same shape" for D-105's *stdio-vs-HTTP* argument, which is correct — but that grouping doesn't
extend to protocol-version behavior, a different axis entirely.

**How to avoid:** After landing step 1 of D-111, log `ClientSession.InitializeResult().
ProtocolVersion` for all three mounted servers in a live run and record it in the phase's
VALIDATION.md evidence. Do not assume; measure.

**Warning signs:** SC#3 ("killing a sidecar mid-conversation ... recovers on the SDK's own
reconnect, live") passes for the memory server (stateless, per-call recovery) but the same test
against WhatsApp shows different, session-based, behavior — which would still be correct, just
different, and the plan's verification narrative should account for a possible difference rather
than asserting one behavior for all three.

### Pitfall 4: `_meta` cutover blast radius — already largely addressed in D-109, one addition

**What goes wrong:** D-109 already correctly sizes rehydrated-history/paused-approval/scheduler
risk. One thing not explicitly named: `tool_methods.go:32-40` shows Aura **already** stamps
`_meta.aura.{operation_key, operation_scope, operation_fingerprint}` on every `tools/call` today
— confirmed via a repo-wide grep that **no code in `cmd/arcadedb-mcp` or `internal/idempotency`
currently reads these keys back off an incoming request** (searched `operation_key`/
`operation_fingerprint` across `cmd/arcadedb-mcp` — zero matches outside the idempotency package
itself, which computes/stores them from the *host-side* call, not from the wire). This strongly
suggests the stamp is write-only telemetry/correlation data today (visible in a request log or a
future consumer), not something any current receiver depends on — but this was not exhaustively
proven (only the two grep terms were checked; a consumer keyed on a partial match, or a network
tap/proxy outside this repo, cannot be ruled out from static analysis alone).

**Why it happens:** The existing `_meta.aura.*` stamp predates this phase and was not written as
part of MCPC-04's scope, so it is easy to overlook when reasoning about "what changes when
`_meta` becomes the identity channel."

**How to avoid:** Preserve this stamp (fold it into the same `AddSendingMiddleware` identity/
idempotency middleware — see Pattern 2) rather than dropping it silently during the rewrite. It
costs nothing to keep and there is no evidence it's safe to drop.

**Warning signs:** None observable without a live trace — this is a preserve-by-default
recommendation precisely because absence-of-evidence-of-a-consumer isn't evidence-of-no-consumer.

## Open Questions

> **All four resolved 2026-08-16** — #1 and #3 by operator decision during `/gsd-plan-phase`, #2 as
> this document recommended, #4 dissolved by the liveness enumeration. Resolutions first; the
> original analysis is retained below them unedited, as the reasoning the decisions rest on.

### ✅ RESOLVED — #1: `bridge.go`'s `Server` interface → **dropped**

**Operator decision.** Aura holds `*sdkmcp.ClientSession` **directly**. No narrow interface, no
re-shaped facade, no hand-written test double. This is option (a), the literal reading of D-103.

Testability, which was the only stated cost, is confirmed a non-issue:
`NewInMemoryTransports()` (`transport.go:160-163`) yields a **real** `*ClientSession` bound to a real
in-process server over a `net.Pipe()`, so daemon-free tests exercise the true type rather than a
double. The planner must treat this as load-bearing when rewriting `bridge_test.go`.

### ✅ RESOLVED — #2: CLI diagnostics → **keep `probe.go`, rewritten**

As recommended. `ProbeServerWithEgress` is a use-case function that happens to call the SDK, not a
facade over the SDK's types, so it does not offend D-103. The 13 `cmd/aura` diagnostic files keep
routing through it; it is re-pointed at `mcp.NewClient`/`Connect`/`ListTools`. **Re-point, not
delete** — which contradicts the CONTEXT.md deletion list's inclusion of `probe.go` and MCPC-03's
text; both need amending.

### ✅ RESOLVED — #3: `_meta` identity presence guard → **fail closed server-side**

**Operator decision.** `cmd/arcadedb-mcp`'s memory tool handlers reject any call whose identity
`_meta` key is absent or empty. The fork is ours, so the check belongs in the server — where it also
catches the exact bypass no client-side guard can see (a caller constructing `*CallToolParams`
directly, since middleware wraps `Client`, not the type).

Exact shape, from Finding C: read via `req.Params.GetMeta()`; reject by returning
`&mcp.CallToolResult{IsError: true, Content: …}` — **not** a Go `error`, which would surface as a
protocol-level error rather than a tool error the model can see and self-correct on.

### ✅ RESOLVED — #4: negotiated protocol version → **not a spike; a field read**

Dissolved by Finding B. `session.InitializeResult().ProtocolVersion` (`client.go:506`) exposes the
negotiated version directly. Log it per mounted server at connect and keep the line permanently — it
is the fact that determines whether any peer could still use `KeepAlive`. No live investigation
needed beyond reading the log once the swap lands.
