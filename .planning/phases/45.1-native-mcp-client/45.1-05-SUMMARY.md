# Phase 45.1 Plan 05: _meta identity cutover Summary

**Calling identity moves off the `user_identifier` tool argument onto stateless `_meta.aura.user_identifier` on both ends of the wire at once — nine input-struct fields deleted, one server-side fail-closed read, one client-side middleware, the CLI migrated through the same helper, and two host-driven callers the plan didn't name fixed because the cutover silently broke them.**

## Performance

- **Duration:** ~50 min (commits span 21:18–21:53 CEST; reading/research time not separately timestamped)
- **Tasks:** 3 (all `type="auto" tdd="true"`)
- **Files modified:** 30 (4 created, 26 modified)

## Accomplishments

- Identity travels in `_meta.aura.user_identifier` and nowhere else: the agent bridge's `IdentityMetaMiddleware`, the CLI's `callSessionText`, and `cmd/arcadedb-mcp`'s `identityFromMeta` all go through the one shared field name and the one shared writer (`mcp.SetAuraMetaField`).
- Nine `UserIdentifier` fields removed from `cmd/arcadedb-mcp`'s memory tool input structs; `GraphSchemaInput` is now an empty struct, enforcing structurally what was previously only a doc-comment convention.
- The server refuses absent/empty/whitespace/non-string identity with a model-visible `IsError:true` tool error — proven through the real SDK-generated `ToolHandlerFor` wrapper, not a bypassed Go-level call — and never resolves a tenant on any refusal path (spy-counted).
- All three PITFALLS §4 blast radii (rehydrated history, paused approvals, scheduler) have a tested disposition, including a new diagnostic (`gateway approval ledger miss` INFO log) for the paused-approval case this cutover itself triggers.
- Two host-driven call sites outside the plan's stated file list — automatic memory-context preload and the memory readiness probe — were silently broken by the server-side cutover (their argument-based identity became inert, and the client-side middleware would have defaulted them to the wrong identity). Found and fixed as Rule 1 bugs.

**1. [Rule 1 - Bug] Two host-driven call sites broke silently under the server-side cutover**
- **Found during:** Task 1, after tracing every production caller of `user_identifier` beyond the plan's named files
- **Issue:** `serve_memory_context.go`'s `Context`/`Search` (automatic memory-context preload) and `serve_memory_readiness.go`'s `checkMemoryReadiness` all passed `"user_identifier": <value>` as a wire ARGUMENT, resolved directly against `MountedServer.CallToolText`. Post-cutover this argument is silently ignored server-side (unknown field). Worse: `handles.Memory`'s underlying session always carries `IdentityMetaMiddleware` (since `policy.memory` is true for the real memory mount), and that middleware reads `identityctx.IdentityID(ctx)` — which none of these three call sites set — so every one of them would have silently defaulted to `identityctx.LocalOperatorIdentity` instead of the caller-intended identity (a per-conversation identity for the context preload; a synthetic isolated owner for readiness). This is a real cross-tenant misattribution risk, not a cosmetic break.
- **Fix:** Wrapped `ctx` with `identityctx.WithIdentityID(ctx, intendedIdentity)` before calling `CallToolText` in all three call sites, and removed the now-dead `"user_identifier"` argument.
- **Files modified:** `cmd/aura/serve_memory_context.go`, `cmd/aura/serve_memory_readiness.go`, plus their test fixtures (`serve_memory_context_test.go`, `serve_memory_readiness_test.go`) which needed the same `IdentityMetaMiddleware` wired into their in-memory fixture to observe the fix.

## Acceptance-criteria literal-grep divergences (named explicitly, not silently passed over)

Three of the plan's acceptance-criteria greps do not hold **literally** against the final tree, each for a specific, defensible reason:

1. **`! grep -rn 'withMemoryUserIdentifier\|acceptsUserIdentifier\|scopeMemoryArgs' internal/ cmd/ --include='*.go'`** — this finds matches, but every one is inside a comment citing the deleted symbol's name for historical context (e.g. `bridge_memory.go`'s doc comment: "replacing withMemoryUserIdentifier's argument injection"). This is the exact false-positive class plan 45.1-03's dark-code guard was built to exclude (comment-stripped scanning); a bare-grep literalism was never going to survive legitimate migration prose. Verified separately: `grep -rn '...' --include='*.go' | grep -v '_test.go'` on the three symbol NAMES as live Go identifiers (not substrings inside comments) returns nothing.
2. **`! grep -rn '"user_identifier"' internal/agent/mcptools/ --include='*.go' | grep -v MetaFieldUserIdentifier`** — the literal quoted string appears 4 times, all inside TEST files, asserting either that the key is present in `_meta` (positive case) or absent from `Arguments` (negative case) — assertions that inherently need the literal wire-key string. Verified separately: zero occurrences in non-test production code (`grep -rn '"user_identifier"' internal/agent/mcptools/ --include='*.go' | grep -v _test.go` is empty).
3. **`grep -c 'identityFromMeta(req)' cmd/arcadedb-mcp/*.go` equals 10** — now 2 (inside `resolveCaller` and `memory_recall`'s own check), for the `resolveCaller` extraction reason documented above and in `key-decisions`. All ten tools still perform exactly one identity check.

One plan-stated behaviour did not hold as literally worded: the plan's `<behavior>` bullet for "no `_meta` at all" says the refusal text must contain "the server name", but the plan's own **verbatim** `errMissingIdentityMeta` string (which the `<action>` section gives byte-for-byte and which this plan followed exactly) does not include one.
