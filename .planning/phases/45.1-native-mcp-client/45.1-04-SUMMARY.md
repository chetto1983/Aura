# Plan 45.1-04 — Four-hint tool annotations, escalate-only

## What changed

`internal/mcp/client.go`'s hand-rolled `ToolAnnotations` carried two hints. The SDK's carries
four. Plan 45.1-03 deleted that type, so the truncation went away for free — and "for free" is
exactly when a risk classifier changes behaviour quietly. This plan makes the adoption explicit
and ships its invariant proof in the same commit.

Three named readers, each honouring the SDK's **documented** default rather than Go's zero value:
`annotationIdempotent` (default false), `annotationOpenWorld` (default **true**), and a nil-safe
`explicitDestructive`. The open-world default is the whole reason the reader exists: an absent
pointer means the *more* dangerous reading, so taking Go's zero value would have silently treated
every unannotated tool as closed-world.

One new escalation, `unsafeToRepeatBeyondAura`: a tool that writes, is not declared repeatable,
and reaches an open world gets the operator's eyes even when the server declined to call it
destructive. It sits in the fallback branch only, after the read-only and nil-destructive cases —
placement is what makes escalate-only structural, not merely tested.

## The behaviour change, stated plainly

In the fallback path, `destructiveHint: false` on its own **no longer earns the mutating tier**.
Because `idempotentHint` defaults to false and `openWorldHint` defaults to true, a third-party
server that declares only "not destructive" is still an unrepeatable write landing beyond Aura's
reach, and it now classifies destructive. To reach the mutating tier a server must additionally
declare `idempotentHint: true` or `openWorldHint: false` — it has to earn it.

That is intended, and it is the point: an untrusted mounted server must not be able to talk
itself out of an approval gate by asserting the single cheapest hint. Trusted recipes are
unaffected — their branch was left byte-identical.

## Deviations from plan

- **The TDD RED step was degenerate, by operator decision.** The implementation arrived already
  written in the working tree from an earlier interrupted session, and the operator chose to build
  on it rather than discard and re-derive it. No RED commit was fabricated to paper over this. The
  honest substitute is the exhaustive invariant proof the plan asks for, which does not depend on
  test-first ordering to be meaningful.
- **This plan was completed inline by the orchestrator, not by a gsd-executor subagent.** Three
  consecutive executor dispatches were killed by a 600-second stream watchdog — one at launch with
  an empty transcript, two mid-run. The third had written the implementation and tests but had not
  reached build/commit. The operator authorised inline completion.
- **One pre-existing test case was updated rather than deleted**, with the reason recorded in both
  the code comment and the commit body. See `key-decisions`.

   with the rest of their in-flight change.
