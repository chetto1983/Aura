## What was built

`MountedServer` is the supervisor: it owns exactly one `*sdkmcp.ClientSession`, learns of
that session's death from the SDK's own `Wait()` rather than from an Aura poll, and holds
the one decision no MCP library can make for a host — **when to redial, and whether the
call that failed may be reissued**.

The division is the point. Framing, request-id bookkeeping, the handshake and session
state now belong to the SDK. What stayed is policy: single-flight redial with capped
exponential backoff (500ms→30s), a 3-failure/30s-cooldown breaker, and the two no-replay
guarantees — a mutating tool whose transport failed *after send* is never reissued, and a
call carrying an idempotency operation scoped `ScopeMCPTool` never redials at all. Both
error texts survive verbatim, and both are asserted.

The domain-outcome chain moved off the deletion set before its only call site died with
`tool_methods.go`. `DecodeToolResult` re-expresses the old decoder against typed
`CallToolResult` fields; `decodeToolCallError` was exported unchanged. There is now
**exactly one** call site in the tree (`bridge_supervisor.go:265`), which is what makes
the guarantee structural rather than aspirational: a new caller reaching for
`session.CallTool` directly would have to re-derive the vocabulary by hand to lose it.

The `_meta.aura.operation_*` stamp that lived inside `callToolWith` became
`OperationMetaMiddleware`, SDK sending middleware — the SDK's own idiom, since MRTR ships
that way too. Its test drives a real in-memory client/server pair and asserts on what the
**server received**, not on Aura's own struct: a middleware that mutated a copy would pass
a struct-level assertion and fail on the wire.

Tool-set drift (D-104) flipped from discovered-on-reconnect to server-pushed via
`ToolListChanged`. A name-set change marks the server sticky-dead; a same-name-set change
refreshes the `bridgedTool`'s stored spec in place. The registry map is never written —
`tools.Registry` has no `Unregister` and no lock, so a late `Register` would data-race live
dispatch (T-45.1-07).

594 LOC of bespoke reconnect and poll code are gone, with ~1,244 LOC of their tests. Net
for the two commits: **2,102 insertions against 2,906 deletions.**

## Deviations from the plan

1. **Tasks 2 and 3 landed in one commit, not two.** `bridgedTool` and `MountedServer` are
   mutually referential at the type level — `bridgedTool.srv`'s type, `bridge.go`'s
   `Server` interface deletion and `mount.go`'s retype cannot be separated without either
   leaving the package uncompilable at a commit boundary or duplicating the risk/schema
   shaping for one commit only to delete it in the next. CLAUDE.md forbids the latter.
   Found while satisfying Task 2's *own* acceptance criteria, which require the whole test
   package to already compile.

2. **`jsonrpc2.ErrClosed` does not exist in go-sdk v1.7.0.** The plan's
   `isSessionTransportFailure` sketch cited it; `internal/jsonrpc2` is also unimportable
   from outside the SDK module regardless (Go internal-package visibility). Classification
   uses the SDK's own exported `mcp.ErrConnectionClosed` sentinel
   (`transport.go:31-33,271-284`) plus the portable `io`/`net` closed-pipe signals. This is
   the stronger signal, not merely the available one: it is what the SDK's generic call
   path already produces, rather than a reconstruction of the wire codes by hand.

3. **`isSessionTransportFailure` was corrected before implementation**, in commit
   `94f78468a` against the plan document itself. The plan specified a free function but
   wrote its rule with an `s.deadErr` disjunct that signature cannot see — and `deadErr` is
   written by the watch goroutine and read on the call path, so the shape implied a bare
   cross-goroutine read. This package runs `-race` with `goleak`; it would have failed the
   gate rather than merely misbehaved. Split: the classifier stays state-free (the only
   shape the task's own "unit-test it directly" requirement can test), liveness is consulted
   through `isDead()` under the mutex.

4. **The redial state machine lives in `bridge_supervisor_redial.go`**, not in
   `bridge_supervisor.go` as written. The combined file would have exceeded the 600 LOC
   ceiling; 457 + 208 is the refactor-on-touch split.

5. **Three `cmd/aura` test fixtures gained a `server/discover` handler** returning a
   legacy-fallback error (`mcp_test.go`, `mcp_status_test.go`, `memory_test.go`). These
   predate this plan and only spoke the pre-2026-07-28 handshake; the added handler matches
   the SDK's documented negotiation fallback (`go-sdk@v1.7.0 mcp/client.go:371-377`). Same
   class of finding as 45.1-01's: fakes that had drifted from the real wire while still
   going green.

6. **`managed_mount_test.go`'s HTTP fixture now serves through
   `sdkmcp.NewStreamableHTTPHandler`** instead of a hand-rolled JSON-RPC-over-HTTP fake —
   the last hand-written wire fake in the package.

## Regression found and fixed on touch: the SDK does not honour the caller's deadline

Running plan 02's own `go test -race ./cmd/aura/` — a gate 45.1-01 never ran, which is
why this surfaced here — failed four bounded-timeout tests that neither this plan nor
plan 01 had touched: `TestDoctorProbeMCPServersBoundedByProbeTimeout`,
`TestWriteRuntimeCheckBoundedByProbeTimeout`, `TestWriteRuntimeCheckZeroToolsHTTPEndpointOK`
and `TestBuildRegistryWithMCP_HungServerDroppedHealthySurvives`. All four are D-06/MCPH-04
guards: **a hung MCP server must cost its caller the configured timeout and no more.**

**Measured, 2026-08-16, go-sdk v1.7.0.** A minimal reproducer — unresponsive HTTP endpoint,
1s deadline — showed `OpenSDKSession` returning after **7.005s**, having issued **three POSTs
which the server saw run to completion, none of them cancelled**. The three are the dual-era
fallback ladder the 2026-07-28 spec prescribes in Versioning §"Backward Compatibility":
`server/discover` → legacy `initialize` → the deprecated HTTP+SSE probe. The SDK observes the
deadline only *between* rungs. The returned error (`context deadline exceeded`) was always
correct; it simply arrived seven times later than asked for.

Aura's own code was not at fault and was checked first: `doctor.go:147` does apply the
`WithTimeout`, `obs.Boundary.Start` derives the context rather than replacing it, and both
`Connect` and the transport's `Write` receive the right context. The deadline is dropped
below that, where the jsonrpc2 layer writes on a context that is not the call's.

**Inventory before building anything** (CLAUDE.md STOP BEFORE BESPOKE — the operator was
asked before a line was written): `StreamableClientTransport` exposes only `Endpoint`,
`HTTPClient`, `MaxRetries`, `DisableStandaloneSSE`, `OAuthHandler`; `ClientOptions` has no
call or connect timeout; both structs are **unchanged at upstream HEAD** (`64e454e`), so this
is not a stale-pin problem; `docs/rough_edges.md` does not list it. `http.Client.Timeout` is
not a substitute — it also bounds the response body read, so it would sever the standalone
SSE stream the tool-list-changed subscription rides on for the whole session. There is no
library knob. The host must bound what the library will not.

`internal/mcp/bounded_call.go` is that bound: `BoundedCall` runs an SDK call on its own
goroutine and returns the moment `ctx` is done, releasing a late result rather than dropping
it. Applied at three sites — the HTTP connect, the stdio connect, and `drainTools` — because
the same defect appears on each.

Two further defects fell out of fixing it, each found by measurement rather than reasoning:

1. **The hang was not where it looked.** `TestBuildRegistryWithMCP_HungServerDroppedHealthySurvives`
   still failed after the connect was bounded: the log showed `mcp session open server=hung`,
   so the handshake *succeeded* and the block was the paginated `tools/list` afterwards. Hence
   `drainTools` is bounded too.

2. **A dropped stdio server was never reaped.** With the drain bounded, the mount returned but
   goleak caught a goroutine parked in the SDK's `pipeRWC.Close`, waiting on a child process
   that nothing would ever kill: the process context belongs to the whole daemon, and the
   mount that gave up had no way to end just its own child. `openAttachAndMount` now takes a
   cancellable slice of the process context per attempt and cancels it on every failure path.
   Aura spawns the child, so Aura reaps it. The D-06/D-07 two-context lifetime contract is
   unchanged — cancelling the daemon context still propagates.

The goroutines an abandoned call leaves behind are tracked in a `sync.WaitGroup` and drained
by tests via `WaitForAbandonedCalls`, **not** whitelisted in goleak: whitelisting a known-benign
goroutine is how a real leak hides later.

`TestWriteRuntimeCheckZeroToolsHTTPEndpointOK` was a fourth, separate defect — a test fixture,
not production. It decoded a JSON body on every request, so the SDK's bodiless `GET` for the
standalone SSE stream made it report `decode request: EOF`. The fixture now declines the
optional stream with `405`, which is what a request/response-only server should do.

**What this does NOT prove.** The bound is asserted against an unresponsive *local* endpoint
and a hung *local* child. It says nothing about a peer that answers slowly but does answer, and
nothing about the live fleet's behaviour under real network loss — 45.1-08's live scenario still
has to measure that. It also does not prove the SDK is wrong to behave this way: no spec text
requires a client to abort an in-flight request on deadline, so this is a host-policy gap, not
an SDK bug, and it should not be filed upstream as one.
