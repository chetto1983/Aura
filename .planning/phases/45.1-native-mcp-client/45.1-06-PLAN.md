<objective>
Settle the one genuinely open, genuinely one-way decision in this phase: **which surface a
server-initiated elicitation reaches the operator on, and whether it is allowed to block the
in-flight agent turn while it waits.**

Purpose: MCPC-05 says elicitation "reaches the operator through Aura's existing approval path with
a bounded timeout, naming the asking server." Nothing in CONTEXT.md, RESEARCH.md or PATTERNS.md
resolves *which* approval path, and the two candidates differ in a way the operator will feel:
one writes to `aura.paused_states` and blocks a live turn for up to five minutes, the other does
not. `45.1-PATTERNS.md` § "No Analog Found" flags exactly this: the elicitation handler has no
MCP-side analog in the tree and the gateway's approval idiom does not fit without adaptation.

Output: one recorded decision that plan 45.1-07 implements.
</objective>

<what_is_already_settled>
Not up for discussion in this checkpoint — record them, do not re-open:

- **Aura is already fail-closed today.** With no `ElicitationHandler`, `c.elicit` returns
  `&jsonrpc.Error{Code: CodeInvalidParams, Message: "client does not support elicitation"}`
  (`client.go:862-864`, v1.7.0). The SDK does **not** auto-fulfill. The "permissive-by-omission"
  premise in the original ROADMAP text was falsified by measurement and is already struck through
  in REQUIREMENTS.md MCPC-05. **Registering a handler closes no security hole.** Its justification
  is SEP-2322 compliance and operator visibility: today a server that needs input gets a flat
  refusal nobody sees, so a legitimate multi-round-trip tool simply cannot work.
- **Aura writes only the handler body.** `clientMultiRoundTripMiddleware` (`mrtr.go:73-115`) already
  owns the fulfil-and-retry loop, and MRTR is enabled by default when `MultiRoundTrip` is nil. No
  retry orchestration, no round-trip bookkeeping, no state machine is Aura's to build.
- **URL-mode elicitation is OPT-OUT** (COVERAGE.md): declined cleanly with `Action: "decline"`.
  Honouring it means opening a browser at a server-supplied URL and awaiting
  `notifications/elicitation/complete` — an out-of-band flow with no Aura surface and an obvious
  phishing shape. Hermes declined it for the same reason (`tools/mcp_tool.py:1720-1731`).
- **Setting `ElicitationHandler` non-nil auto-advertises the elicitation capability**, so whichever
  option is chosen, mounted servers will start attempting elicitation where they previously would
  not have.
- **Failure is always decline or cancel**, never accept: timeout, handler error, missing surface,
  unexpected state — all fail closed.
</what_is_already_settled>

<the_constraint_that_makes_this_a_decision>
The SDK invokes `ElicitationHandler` **synchronously, inside the in-flight `CallTool`**. In Aura
that call sits inside `bridgedTool.Execute` → `runTool` → the agent turn. Whatever the handler does,
it does while a turn is held open.

Aura's existing HITL mechanisms are both **asynchronous by construction**:
- `tools.ErrAwaitingUserInput` (`internal/agent/tools/ask_user.go:62-90`) *unwinds* the turn — the
  agent loop pauses, `aura.paused_states` gets a row, and the operator's answer drives a **new**
  Turn. A blocked handler cannot return through it.
- `GatewayApprovals` (`internal/gateway/approvals.go`) is a cross-turn ledger: the gateway returns
  an approval-required **result**, the model relays it, the operator resolves it, and the model
  **re-emits** the call. Also a new Turn.
- `Runner.MintApprovalPause` (`internal/runner/runner_mint_approval.go`) plus
  `channels.ApprovalDeliverer` can push a real HITL prompt to the origin channel (Telegram Sì/No,
  WebUI in-thread) without the model's cooperation — the closest existing analog — but resolution
  still arrives on a later Turn, observable only by polling `askuser.Store` /
  `GetPausedStateByToken`.

So "route through Aura's existing approval path" cannot be taken literally without either blocking
a live turn on a later turn's resolution, or changing what "reaches the operator" means.
</the_constraint_that_makes_this_a_decision>

  <context>
Whatever is chosen, plan 45.1-07 builds the same three things: a bounded-timeout handler that names
the asking server, an `ElicitationConsent` seam interface, and a fail-closed default. The decision
is only about what the seam is wired to at the composition root — but that wiring is what
determines whether a live turn can stall for five minutes and whether a row lands in
`aura.paused_states`, which is why it is not the planner's to take.

Note hermes' own resolution of the same constraint: it offloads the synchronous consent flow to a
**worker thread** precisely so the MCP event loop is not frozen — an admission that the blocking
shape is real and had to be worked around even there. Go has no equivalent escape: the handler's
return value is what the SDK sends back, so whoever waits, waits on the calling goroutine.
  </context>
  <options>
    <option id="decline-and-surface">
      <name>A — Decline, but make the ask visible (recommended)</name>
      <pros>
        - No turn is ever blocked; no row is written to `aura.paused_states`; no interaction with the resume machinery.
        - Strictly better than today: today the server gets `CodeInvalidParams` and the operator sees nothing at all. Here the operator sees, on their own surface, *which server asked for what* and can act on it deliberately.
        - Fully daemon-free testable; carries the 85% coverage floor without a live channel.
        - Reversible: option B remains available later as a pure addition behind the same `ElicitationConsent` seam.
        - Bounded by construction — there is nothing to time out.
      </pros>
      <cons>
        - A legitimate multi-round-trip tool still cannot **complete** in one turn. The operator must re-drive it after supplying whatever the server wanted, out of band.
        - Only partially satisfies MCPC-05's literal "reaches the operator through Aura's existing approval path": it reaches them through the notification path, not the approval path.
      </cons>
      <shape>`ElicitationConsent` implemented over `channels.Deliverer` (plain text, not `ApprovalDeliverer`): deliver one message naming the server, the elicitation's `Message`, and a rendered summary of the requested schema's top-level fields; log at WARN with the same content; emit an `obs` counter dimensioned by server and action; return `&ElicitResult{Action: "decline"}`.</shape>
    </option>
    <option id="mint-and-wait">
      <name>B — Mint a real approval pause and block, bounded</name>
      <pros>
        - Full hermes parity and the literal reading of MCPC-05: a real HITL prompt on the origin channel (Telegram Sì/No, WebUI in-thread) that the operator answers, and the tool call **completes** in the same turn.
        - Reuses machinery that already exists and is already proven: `Runner.MintApprovalPause` + `channels.ApprovalDeliverer` + `askuser.Store`.
      </pros>
      <cons>
        - **Blocks the in-flight agent turn for up to the timeout** (hermes' reference default is 300s). Every other tool in that turn waits.
        - Writes a row to `aura.paused_states` and a synthetic assistant turn into the conversation, from inside a turn that is itself mid-flight on that same conversation. The operator's answer drives a **resume**, i.e. a new Turn, while the old one is still blocked — an interleaving on one conversation that no existing code path produces and that needs its own correctness argument before it is written.
        - Resolution is observable only by polling `GetPausedStateByToken`; a poll loop is exactly the shape this phase spent its effort deleting.
        - Not daemon-free: meaningful tests need Postgres, so they land in a tier that feeds no coverage.
        - Hard to undo — persisted state and conversation history.
      </cons>
      <shape>`ElicitationConsent` implemented in `cmd/aura` over `Runner.MintApprovalPause` + `ApprovalDeliverer`, with a bounded `context.WithTimeout` and a `GetPausedStateByToken` poll; `accept`/`decline`/`cancel` mapped from the resolution, `cancel` on timeout.</shape>
    </option>
    <option id="seam-only">
      <name>C — Ship the seam, wire nothing</name>
      <pros>
        - Smallest surface; the handler, the timeout and the fail-closed default all exist and are tested.
        - Leaves the surface choice to Phase 46, which is already the trust-posture phase.
      </pros>
      <cons>
        - MCPC-05 does not close: nothing "reaches the operator". The requirement would have to be carried forward, and this phase's seal would be partial.
        - Setting `ElicitationHandler` non-nil still auto-advertises the capability, so servers start asking — and every ask is silently declined. That is worse than today's honest `CodeInvalidParams` refusal, because the server now believes the client supports elicitation.
      </cons>
      <shape>Handler + seam + fail-closed default; `ElicitationConsent` left nil at the composition root.</shape>
    </option>
  </options>
  <recommendation>
**Option A.** It is the only one that improves the operator's situation without inventing a
same-conversation turn interleaving that nothing in the codebase currently produces. Option B's
cost is not implementation difficulty — it is that a blocked turn plus a resume on the same
conversation is a correctness question that deserves its own phase and its own design note, not a
task at the tail of a client swap. Option C is worse than doing nothing, because advertising a
capability and then always declining it is a lie told to every mounted server.

If the answer is B, say so and plan 45.1-07 will carry a `checkpoint:human-verify` for the live
interleaving rather than shipping it on unit tests.
  </recommendation>
