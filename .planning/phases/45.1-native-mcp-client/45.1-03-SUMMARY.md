## What was built

Sixteen `cmd/aura` files plus `internal/config` now open MCP sessions through the SDK
seam plans 45.1-01/02 built (`mcp.OpenSDKSession`/`OpenSDKSessionForConfig`) instead of
the bespoke `mcp.Client`/`mcp.Transport`. Thirteen of those sixteen files needed **zero**
edits — they only touch `mcp.ManagedServer`/`ServerConfig`/`ProbeResult`, all unchanged
by the swap — confirmed by a clean `go build ./...`, not assumed from the plan's file
list. `mcp_tools.go` is the hub: `openManagedMCPSession` (renamed from
`openManagedMCPTransport`), `openAndListMCPTools`/`openAndListManagedMCPTools` (now
returning `*sdkmcp.ClientSession, []*sdkmcp.Tool`), and a new `callSessionText` helper
that is the single CLI-side domain-outcome decode call site, mirroring
`bridge_supervisor.go`'s `decodeResult`. `memory.go` and `memory_onboarding.go` route
through it; `scopeMemoryArgs` is deliberately unchanged (still stamps the
`user_identifier` argument — it moves to `_meta` in plan 45.1-05).

The bespoke MCP client is deleted outright: `client.go` (511 LOC), `http_client.go`
(411), `transport.go` (57), `protocol.go` (47), `tool_methods.go` (53), `lifecycle.go`
(90) — 1,169 LOC of hand-rolled JSON-RPC/stdio framing, streamable-HTTP framing,
handshake validation and the session-serialization gate — plus their 12-file, 2,655 LOC
test tier. `internal/mcp/darkcode_test.go`'s `TestNoHandRolledJSONRPCFraming` walks
`internal/` and `cmd/` for 12 deleted-symbol tokens (built by string concatenation so
the guard file cannot match itself) and was proven to bite: a deliberately-added file
defining `type sessionGate struct{}` was added, made the test fail, and was removed.
The guard scans non-test `.go` files with comments stripped via `go/scanner` — a design
decision, not the plan's literal bare-grep description, because this phase's own
SDK-era test fixtures legitimately construct `Mcp-Session-Id` headers and route on
`notifications/initialized` to emulate a pre-2026-07-28 third-party peer (exactly what
the SDK client must stay compatible with), and `sdkclient.go`/`result.go` legitimately
document the deleted symbols they replaced in prose. A bare substring scan across all
files, as literally described, produces guaranteed false positives against both; the
comment-stripped, non-test-only scan is the more correct reading of "dark code
reappearing in the shipped binary."

The three build-tagged live-sidecar tests (calendar/whatsapp/calculator_integration)
are re-pointed at `OpenSDKSession`/`OpenSDKSessionForConfig`, drain tools through a
shared `sdk_integration_helpers_test.go` (all three tags compile together under the
verification command, so per-file helpers would collide), decode through
`DecodeToolResult`, and now log `session.InitializeResult().ProtocolVersion` — the
mixed-fleet protocol question (RESEARCH Assumption A1) is answered by the next live run
instead of staying assumed. whatsapp/calculator's env-unset gates gained the same
`$CI`-fatal no-skip-as-green shape calendar's gate already had (both previously bare
`t.Skip` regardless of `$CI`, a pre-existing gap closed on touch).

Coverage: three new daemon-free test files close the gaps the coverage profile actually
named (measured first, per the plan — `httpAuthFromEnv`/`withAuthHeaders`/
`headerRoundTripper.RoundTrip` had no SDK-era test at all; `closeSession`/
`ReleaseSession` were genuinely unreached by the one existing test that touches
`BoundedCall`'s abandoned-goroutine path; `(*ToolCallError).Error()` was never invoked
by any existing test despite being the shape `bridge_supervisor.go` returns as an
error). `internal/mcp` measures 90.5%, `internal/agent/mcptools` 92.1% — both above the
85% floor.

**1. [Rule 1 - Bug] SDK-era memory HTTP test fixture never handled the standalone-SSE
GET, breaking once memory.go moved onto the SDK client**

## Issues Encountered — the mutation-testing incident and the gate re-run it required

Running `go-mutesting internal/agent/mcptools/bridge_supervisor.go` under WSL for the
Task 3 mutation spot-check left the source tree in a state where `git diff` initially
reported it as byte-identical to HEAD, but a subsequent orchestrator check found the
working tree DID diverge — two live, compile-legal no-op mutants
(`_ = s.mu.Lock` shapes) had survived the tool's own restore step. Because
`_ = expr` is legal Go, `go build`/`go vet` on that mutated file compiled and vetted
clean, meaning **the `go build ./...` / `go vet ./...` runs executed inside that window
proved less than they appeared to** — they exercised mutated, not real, source.

The orchestrator caught this, reverted `internal/agent/mcptools/bridge_supervisor.go`
to HEAD (confirmed via `git diff --stat` showing zero changes to that file), and every
gate cited in this SUMMARY and in the Task 3 commit message was **re-run after that
revert**, on the verified-clean tree:
- `go build ./...` — clean (repo-wide).
- `go vet ./...` — clean (repo-wide).
- `go test -race ./internal/mcp/ -count=1 -coverprofile=...` — pass, 90.5%.
- `go test -race ./internal/agent/mcptools/ -count=1 -coverprofile=...` — coverage
  92.1%, but the run itself still reports `FAIL` on
  `TestMCPRiskDefaultsAreConservativeWithoutOverridingReads/explicit_additive_write` —
  confirmed via `git diff --stat internal/agent/mcptools/bridge_risk.go` to be caused
  by that file's uncommitted, in-flight plan-45.1-04 change, not by anything in this
  plan or by the mutation-testing incident. `bridge_risk.go` is on this executor's
  explicit do-not-touch list.
- `go test -race ./cmd/aura/ ./internal/config/ -count=1` — pass.
- `TestNoHandRolledJSONRPCFraming` and
  `go vet -tags='calendar_integration whatsapp_integration calculator_integration'
  ./internal/mcp/` — both re-confirmed pass on the same verified-clean tree.

The 99/99-killed mutation score recorded in `45.1-VALIDATION.md` is the mutation tool's
own final summary line (`the mutation score is 1.000000`), produced by the run itself
before its restore step misbehaved — that number is the mutation *harness's* result,
not a `go build`/`go vet` claim made against the mutated tree, so it stands.

**Not run:** `bash scripts/coverage_docker.sh` (the full aggregate ≥85% owned-surface
gate across ALL of `internal/*`). It invokes `go test ./internal/...` against a live
Docker/Postgres stack; a concurrent, unrelated session held `compose.yaml` dirty and
`internal/agent/mcptools/bridge_risk.go` (plan 45.1-04) mid-edit in this exact checkout
for the whole duration of this plan's execution. Running the aggregate gate now would
fold in that in-flight state's own genuinely-failing test and risk colliding with a
concurrently-edited compose file. The per-package measurements above (90.5% / 92.1%,
both on the two packages this plan's ~3,750-LOC deletion actually affects) are the
honest substitute available in this environment; the aggregate gate should be re-run
once plan 45.1-04 lands and the tree is quiescent.

**Race detector on Windows:** not attempted directly; all `-race` runs above executed
in WSL (`CGO_ENABLED=1`) per CLAUDE.md's toolchain guidance, consistent with plans
45.1-01/02.
