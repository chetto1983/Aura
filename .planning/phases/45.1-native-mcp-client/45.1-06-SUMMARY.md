# Plan 45.1-06 — Elicitation surface: decided

This plan produces no code. It produces one recorded decision, consumed by plan 45.1-07.

## What was decided

**Option A — decline, but make the ask visible.** `ElicitationConsent` is implemented over
`channels.Deliverer` (plain text, **not** `ApprovalDeliverer`): on a server-initiated elicitation
Aura delivers one message naming the asking server, the elicitation's `Message`, and a rendered
summary of the requested schema's top-level fields; logs the same content at WARN; emits an `obs`
counter dimensioned by server and action; and returns `&ElicitResult{Action: "decline"}`.

## Blocking behaviour, stated before code

None. The SDK invokes `ElicitationHandler` synchronously inside the in-flight `CallTool`, which in
Aura sits inside `bridgedTool.Execute` → `runTool` → the agent turn. Option A does its work and
returns immediately: no turn is held, no row lands in `aura.paused_states`, no synthetic assistant
turn enters conversation history, and the resume machinery is not touched. There is nothing to poll
and nothing to interleave.

The 300-second timeout is therefore near-theoretical under this option — it bounds the handler's
own context, not a wait for a human. It is recorded now because it is the number option B would
inherit if the seam is later wired to `MintApprovalPause`, and settling it here means that upgrade
is a wiring change rather than a fresh product decision.

## Why not the alternatives

**B (mint-and-wait)** buys the literal reading of MCPC-05 — a real Telegram/WebUI prompt, and the
tool completes in the same turn — at a price this phase should not pay. It writes to
`aura.paused_states` and to conversation history *from inside a live turn on that same
conversation*, so the operator's answer drives a resume Turn while the original Turn is still
blocked. Nothing in the codebase currently produces that interleaving, and it needs its own
correctness argument, not a task at the tail of a client swap. It is also one-way: persisted state
and conversation history are hard to unwind.

**C (seam-only)** is worse than doing nothing. Setting `ElicitationHandler` non-nil auto-advertises
the elicitation capability, so mounted servers begin asking — and every ask is silently declined.
That is a lie told to every mounted server, strictly worse than today's honest
`CodeInvalidParams` refusal.

## What this changes for the operator

Today, with no handler registered, `c.elicit` returns
`&jsonrpc.Error{Code: CodeInvalidParams, Message: "client does not support elicitation"}`
(go-sdk v1.7.0 `client.go:862-864`). The SDK does **not** auto-fulfil. So Aura is already
fail-closed, and **registering a handler closes no security hole** — the ROADMAP's
"permissive-by-omission" premise was falsified by measurement and is already struck through in
REQUIREMENTS.md MCPC-05.

What changes is visibility. Today a server that needs input gets a flat refusal nobody sees, so a
legitimate multi-round-trip tool simply cannot work and no one learns why. After 45.1-07 the
operator sees which server asked and for what, and can act deliberately — re-driving the tool out
of band with the information supplied.

The honest cost: a multi-round-trip tool still cannot **complete** in one turn.

## Deviations from plan

**The recorded timeout source is not the one the operator asked for, because the thing they named
does not exist.** The instruction was 300 seconds reusing the gateway approval default. Grep over
`internal/gateway/approvals.go` (217 LOC — `Approve`, `Consume`, `Challenge`, `ApproveChallenge`,
`Evict`, `PendingCountForTool`), over `internal/config/config.go`'s full env catalog, and over
`internal/` + `cmd/` found **no approval timeout, TTL or expiry anywhere**.

That absence is structural rather than an oversight: gateway approvals are an asynchronous
cross-turn ledger — the gateway returns an approval-required result, the model relays it, the
operator resolves it, the model re-emits the call. Nothing is ever held waiting, so there is
nothing to bound. The only time-shaped thing nearby is `approval_reminded_at`, a cron throttle for
reminder spam, not a deadline.

The operator's value (300s) is honoured. The source became `AURA_MCP_ELICITATION_TIMEOUT_SEC`, the
env var the plan had already reserved — recorded here so plan 45.1-07 does not go hunting for a
constant that was never there.

## Carried into 45.1-07

Threats T-45.1-29 through T-45.1-31 apply to option A and must be mitigated in the implementation:

- **T-45.1-29 (spoofing/social).** The rendered message must always name the asking server and
  present the server's text as quoted, attributed, untrusted content — never as Aura speaking.
  Byte-cap both the message and the rendered schema summary. This is the phase's only path from a
  mounted server's text to a human.
- **T-45.1-30 (DoS).** Bounded timeout on every elicitation, fail closed to `cancel`. The
  per-conversation concurrency bound that option B would have required does not apply here, since
  nothing queues.
- **T-45.1-31 (EoP).** URL-mode elicitation stays OPT-OUT: declined cleanly, never opened. A
  server-supplied URL presented to an operator as an Aura-sanctioned link is a phishing primitive.

**T-45.1-32 does not apply** and is closed by this decision: it was the blocked-turn/resume
interleaving risk, which exists only under option B.
