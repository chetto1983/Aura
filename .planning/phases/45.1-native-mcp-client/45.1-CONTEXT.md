# Phase 45.1: Native MCP client - Context

**Gathered:** 2026-08-16
**Status:** Ready for planning

<domain>
## Phase Boundary

Aura speaks MCP through the official `github.com/modelcontextprotocol/go-sdk` client instead of a
hand-rolled one. The bespoke JSON-RPC/stdio client, the streamable-HTTP client, and the
reconnect/keepalive layer are **deleted**; Aura's own policy — SSRF resolve-then-pin, egress
allowlist, trust classification, managed-config and per-identity overlay — is **preserved on top of**
the SDK rather than reimplemented beside it.

Five requirements: MCPC-01, MCPC-02, MCPC-03, MCPC-04, MCPC-05 (already written into
`.planning/REQUIREMENTS.md` §"Native MCP client", all five carrying traceability rows — D-16 of
`46-CONTEXT.md` is therefore already satisfied).

**Not this phase:** Phase 46's trust ratification and fork-side curation; the tool-surface ceremony
strip and un-defer/merges (47/48); memory tiers (49). And **not** the deletion of Aura's
trust/untrust envelope (D-115) — that is Phase 46's posture question and needs its own PRD
amendment.

**The operator's governing directive for this phase**, given verbatim during area selection:
*"remove all shit bespoke and native mcp transport package."* Every decision below is downstream of
it. Where a measured fact collided with a clean deletion, the collision was put to the operator
explicitly rather than resolved by assumption; those four answers are D-103..D-106.

## Implementation Decisions

Standing directives carried in from the Phase 46 discussion and reaffirmed here:
**(1) research hermes first, adopt its shape, do not invent** (`D:/tmp/hermes-agent`);
**(2) use the native MCP client, no bespoke**; **(3) no ceremony**; **(4) every MCP server Aura
ships is a fork Aura controls.**

Decisions are numbered `D-1xx` to keep them distinct from `46-CONTEXT.md`'s `D-01..D-22`, several of
which this file inherits verbatim.

### Inherited and locked — do NOT re-open

These were decided during the Phase 46 discussion and recorded in
`.planning/phases/46-mcp-trust-and-facade/46-CONTEXT.md`. They are restated here so the planner does
not have to reconstruct them, and they are **not** open questions.

- **D-100 (= 46-CONTEXT D-11, measured):** `github.com/modelcontextprotocol/go-sdk v1.7.0` is
  **already a dependency** (`go.mod:27`), used **server-side only** today (`cmd/arcadedb-mcp/*`).
  It already ships the 2026-07-28 stateless core (`latestProtocolVersion`, `mcp/shared.go:50-51`)
  and negotiates down five protocol versions. **No dependency bump, no sidecar work.**
- **D-101 (= 46-CONTEXT D-12/D-13, MCPC-02/MCPC-03):** Scope is client + transport + reconnect +
  keepalive. **Deleted, not left dormant.** Preserved on top: `ssrf.go` + `transport_ssrf.go` +
  `egress_policy.go` (re-attached as a custom `http.RoundTripper`), `managed_config.go` +
  `managed_config_identity.go`, `classify.go`, `tool_error.go`, `domain_outcome.go`,
  `observability.go`, `redact.go`.
  — **Reversibility:** one-way — the bespoke transport and ~900 LOC of its tests are deleted and the
  bridge is re-pointed at a different client type; reverting means restoring a hand-rolled JSON-RPC
  client against a spec version that no longer has the session model it was built on.
- **D-102 (= 46-CONTEXT D-14/D-15, MCPC-04/MCPC-05):** `Client.AddSendingMiddleware`
  (`mcp/client.go:1131`) is the seam for host-side argument derivation — the SDK's own idiom, since
  MRTR ships as default-on client middleware (`mcp/mrtr.go:22-31`). Elicitation (SEP-2322) routes
  through Aura's existing approval path with a bounded timeout, naming the asking server (hermes
  parity, `tools/mcp_tool.py:1669-1758`); ~~the SDK auto-fulfills by default and Aura registers no
  handler today, so the current posture is permissive-by-omission~~.
  **Rationale corrected 2026-08-16 — the decision stands, its stated premise was falsified by
  measurement** (RESEARCH § Finding E). The SDK does **not** auto-fulfill: with no
  `ElicitationHandler`, `c.elicit` returns
  `&jsonrpc.Error{Code: CodeInvalidParams, Message: "client does not support elicitation"}`
  (`mcp/client.go:862-864`, v1.7.0). Aura is therefore already **fail-closed**, and registering a
  handler closes no hole. The real justification: SEP-2322 compliance and operator visibility — today
  a server that needs input gets a flat refusal nobody ever sees, so a legitimate multi-round-trip
  tool simply cannot work.

  `mcp_status.go`, `mcp_tools.go`, `memory.go`, `memory_onboarding.go`, `serve_governance.go`,
  `serve_governance_write.go`, `serve_memory_readiness.go`, `serve_provisioning.go`) plus
  `internal/agent/llm_agent_retry.go` and `internal/agent/mcptools/*`. The types crossing that
  boundary are `mcp.ToolDef`, `mcp.ServerConfig`, `mcp.ErrTransport`, `mcp.Client`.
  The 13 `main.go` files under `.claude/skills/spike-findings-Aura/sources/` also import it but are
  **not** in the build (the Go tool skips directories beginning with `.`) — they are historical

  — **Reversibility:** costly — undoing it means re-introducing a translation layer across ~16

### The four collisions, resolved

Each of these is a place where "delete all the bespoke code" met a measured fact that does not
travel with the transport. All four were put to the operator with the evidence.

- **D-104 — Tool-set drift on reconnect: mark the server dead.**
  **The measured collision:** `bridge_reconnect.go:238-259`'s `validateReconnectToolSet` is not
  transport bespoke — it enforces a **registry invariant that outlives the file**.
  `mount_retry.go:19-25` states it plainly: *"the agent's `tools.Registry` is immutable once a run
  starts (no lock; late `Register` would data-race the live dispatch)"*, and `tools.Registry` has
  `Register`/`Get`/`All`/`Validate` and **no `Unregister`** (`internal/agent/tools/spec.go:183-213`).
  **Decision:** keep the behaviour, re-expressed in the small on the SDK's own
  `ClientOptions.ToolListChangedHandler` (`mcp/client.go:178`, fired at `:337`) — when the advertised
  tool-name set differs from the set registered at mount, that server's tools fail with the existing
  `"tool set changed; restart required"` shape. In-place `refreshSpec` of an already-registered tool
  stays (it mutates the `bridgedTool`, not the registry map, so it is safe and it is what makes
  fork-side curation land without Aura-side code — 46-CONTEXT D-17).
  **Rejected:** refresh-in-place-and-ignore-add/remove (silent — a fork adding a tool would go
  unnoticed); making the registry mutable with a lock + `Unregister` (touches the hot dispatch path
  and reverses a deliberate design note).
  — **Reversibility:** reversible — ~30 LOC on an SDK handler.

- **D-105 — A stdio server that dies mid-run: fail and report.**
  **The measured collision:** the SDK's `CommandTransport` (`mcp/cmd.go:20-29`) has **only
  `Connect`** — no respawn, no restart. The roadmap's "the SDK ships equivalents … automatic
  reconnect with exponential backoff" is true for **streamable HTTP only**
  (`mcp/streamable_client.go:122-139`). All three built-in recipes are streamable-HTTP over loopback
  (`internal/mcp/manager/catalog.go:131,144,165`), so they are fully covered; `ServerConfig.Command`
  remains a live path for ad hoc and self-minted stdio servers, which are not.
  **Decision:** the mount goes down and calls return a clear transport error naming the server; the
  operator remounts. No bespoke respawn supervisor. `mount_retry.go`'s bounded **boot-time** retry is
  unaffected and stays — it solves a different problem (a sidecar still starting when Aura mounts it)
  and it cannot help a server that dies mid-run, because the registry is already frozen by then.
  **Accepted regression, stated plainly:** an ad hoc/self-minted **stdio** server that dies mid-run
  no longer self-heals. This is a behaviour change from today, taken deliberately.
  **Rejected:** re-running the whole mount under `MountWithRetry` on transport death (collides with
  the frozen registry — a remount would re-`Register`); dropping stdio entirely (changes the
  self-extension contract).

- **D-106 — The stdio command-safety validator: DELETE it.**
  (Operator decision, against the recommendation — recorded with its counter-argument, not as an
  oversight.)
  **What is being deleted:** `internal/mcp/client.go:140-172` refuses a launch command containing
  shell metacharacters, a relative executable path, or a shell interpreter, before `exec`.
  **The recommendation that was put and declined:** this is security policy rather than framing, it
  guards **servers Aura mints herself** through self-extension (an agent-authored command string is
  not the same trust class as an operator-typed one), MCPC-02 explicitly preserves Aura's policy on
  top of the SDK, and the SDK takes an `*exec.Cmd` and validates nothing. The operator's grounds are
  the same as the ratified trust posture (46-CONTEXT D-01): the operator controls what gets mounted,
  and mounting must cost no ceremony.
  **Decision as taken:** delete it; hand the `*exec.Cmd` straight to `CommandTransport`.
  **Consequence the planner must carry forward, not re-argue:** flag this for `/gsd-secure-phase` on
  this phase so the removal appears in the security record with its rationale.
  — **Reversibility:** reversible — the validator is a pure function over the config; restoring it is
  local.

- **D-107 — Adopt all four SDK tool annotations now.**
  **The measured gap:** `internal/mcp/client.go:88-91`'s `ToolAnnotations` carries only
  `ReadOnlyHint` and `DestructiveHint`; the SDK's `mcp/protocol.go:1967-1991` carries
  `IdempotentHint` and `OpenWorldHint` as well. Deleting the bespoke type removes the truncation for
  free, and `idempotentHint` is the spec's own signal for what `applyMCPOperationMetadata`
  currently hardcodes.
  **Invariant that MUST hold and must be proven by test:** `bridge_risk.go` lets `explicitDestructive`
  **escalate only, never de-escalate**. An adopted annotation may raise a tool's tier; it may never
  lower one. `mcpToolRisk`'s fail-closed default (unannotated → `true, true`) is unchanged.
  This closes 46-CONTEXT's deferred item *"Adopting the SDK's `IdempotentHint`/`OpenWorldHint` → the
  client-swap phase, or Phase 48"* in favour of this phase.

### `_meta` identity cutover (MCPC-04)

- **D-108 — Hard cut. No fallback, no accept-both window.** `cmd/arcadedb-mcp` reads the calling
  identity from stateless `_meta` and from nowhere else; the `user_identifier` field leaves every
  input struct.
  **The operator's reason, which is stronger than the one originally offered:** ArcadeDB is Aura's
  long-term memory with **one database per identity and server-enforced tenancy**. A dual-source
  identity path — `_meta` with an argument fallback — is a mechanism that can select the **wrong
  database**, and a wrong selection writes one identity's memory into another's. A safety valve on
  this particular parameter is itself the hazard. Recorded in the operator's own framing:
  *"arcade is a long term memory, if we put safety here we can trash all repo."*
  **Measured surface:** `user_identifier` is a declared field on **9 tool input structs** —
  `cmd/arcadedb-mcp/tool_memory.go:27,142,182,292`, `tool_browse.go:20,55,90`, `tool_forget.go:18`,
  `tool_graph_schema.go:17`, `tool_memory_maintenance.go:19`. Host-side it is filled by
  `withMemoryUserIdentifier` (`bridge_memory.go:45-58`), which overwrites whatever the model emitted
  from `identityctx`. `cmd/aura/memory.go:276-283` is a separate CLI path that passes one explicitly
  and must be migrated with the rest.
  — **Reversibility:** costly — `cmd/arcadedb-mcp`'s tool contract changes and the memory tool's
  schema shifts.

- **D-109 — The three PITFALLS §4 blast radii, sized against measurement rather than assumed.**
  1. **Rehydrated history — benign here.** A persisted `tool_calls` payload predating the cut may
     carry `user_identifier`; Go's `json.Unmarshal` ignores unknown fields, so the stale argument is
     inert rather than an error. It remains a conflicting few-shot exemplar in the model's own
     history, which is the generic §4 risk and not specific to this field.
  2. **Paused approvals — accepted, narrow, fail-closed.** `gatewayArgsFingerprint`
     (`internal/gateway/approvals.go:66`, called at `approve.go:114`) hashes the **model's** args,
     upstream of the host injection. Dropping the field from the schema changes what the model emits,
     so an approval withheld before the deploy and resumed after it will miss `Consume` and issue a
     fresh challenge — **fail-closed but silent**. §4's own cheap mitigation applies: log at INFO on
     a `Consume` miss with enough detail to tell "tool name changed" from "args changed", so this
     failure class is diagnosable rather than mistaken for a UI bug.
  3. **Scheduler — a non-issue, measured.** `internal/cron/handlers/agentjob.go` stores only
     `{"goal": "<free text>"}` and builds a fresh agent against the **current** registry at fire
     time. Nothing about this cut reaches it.

### Evidence and landing

- **D-110 — What proves the swap: SDK in-memory transports AND live sidecars.** Bridge-seam tests
  over the SDK's in-memory transports carry the **85% coverage floor** (daemon-free, so they feed the
  gate); the existing `internal/mcp/calendar_integration_test.go`,
  `whatsapp_integration_test.go` and `calculator_integration_test.go` re-point at the SDK client and
  prove the real wire. The phase still closes on a live scenario per ACC-01/ACC-02 — no new eval
  harness.
  **The constraint that makes this non-negotiable:** ≈900 LOC of tests covering hand-rolled framing
  and session recovery are deleted (`client_test.go`, `http_client_test.go`,
  `http_client_extra_test.go`, `http_client_session_recovery_test.go`, `client_frame_test.go`,
  `client_lifecycle_test.go`, `client_timeout_test.go`, `client_errors_test.go`, `client_open_test.go`,
  `transport_test.go`, `protocol_test.go`, `probe_test.go`, plus
  `bridge_reconnect_branches_test.go`, `bridge_reconnect_mutation_test.go`,
  `bridge_reconnect_realsubprocess_test.go`, `bridge_ping_test.go`). Integration tiers feed no
  coverage today (`AURA_COVERAGE_TAGS` defaults to `db_integration`), so the floor must be carried by
  the in-memory tier or the phase fails CI ~20 minutes after push.

- **D-111 — Landing shape: staged, each step tree-consistent.** Four steps, each compiling and
  passing the gates on its own, and **no commit leaves two MCP clients in the tree**:
  1. SDK client + transports + policy re-attach (`http.RoundTripper`) + the deletions (D-101, D-103,
     D-104, D-105, D-106);
  2. middleware seam — `withMemoryUserIdentifier` onto `AddSendingMiddleware` (D-102);
  3. `_meta` identity cutover in `cmd/arcadedb-mcp` + `cmd/aura/memory.go` (D-108, D-109);
  4. elicitation handler (D-102) and the four annotations (D-107).
  Ordering note: step 3 is the only one with persisted-state blast radius, so it lands after the swap
  is live-proven rather than entangled with it.

## Existing Code Insights

### Reusable Assets
- **The SDK itself, already vendored.** `go.mod:27` pins v1.7.0 and `cmd/arcadedb-mcp` already builds
  servers with it — the client half is simply unused. Nothing to add, nothing to bump.
- `mount_retry.go`'s `MountWithRetry` — boot-time transient-failure bound. Unaffected by the swap and
  explicitly **not** the answer to mid-run death (D-105).
- `bridge.go`'s narrow `Server` interface (`ListTools` / `CallTool` / `Ping` / `Close`) — the whole
  bridge already talks to an interface, so the client behind it is genuinely swappable. This is the
  seam that makes D-103 tractable across ~16 packages.
- `capSchemaDescriptions`, `boundedMCPError`, `refreshSpec` — bridge machinery that keeps working
  unchanged.
- `internal/mcp/ssrf.go` + `transport_ssrf.go` + `egress_policy.go` — already structured as transport
  decoration, which is exactly the shape a custom `http.RoundTripper` needs.

### Established Patterns
- **The tool registry is frozen once a run starts.** No lock, no `Unregister`. Everything about
  dynamic tool sets in this phase is downstream of that (D-104).
- **Fail closed on wiring, fail open on outages.** `Registry.Register` panics on duplicates,
  `ValidateClassifiable` panics on missing metadata, MCP mounts fail soft. D-104 sits on the wiring
  side; D-105 on the outage side.
- **Escalate-only risk classification.** `bridge_risk.go` never lets a server-declared annotation
  lower a tier. D-107 adopts two more hints under that ceiling.
- **No non-test Go file over 600 LOC** — `bridge.go` is 532 and is touched; refactor-on-touch is
  likely required in the same commit.
- **Deleted means deleted.** MCPC-03 forbids dark code: no hand-rolled JSON-RPC framing or reconnect
  loop may reappear anywhere else in the tree.

### Integration Points
- `bridge.go`'s `Server` interface — where the SDK client attaches.
- `ClientOptions.KeepAlive` + `KeepAliveFailureThreshold` — replaces `bridge_ping.go` wholesale.
- `ClientOptions.ToolListChangedHandler` — where D-104's drift check lands.
- `ClientOptions.ElicitationHandler` — where D-102's approval routing lands.
- A custom `http.RoundTripper` on the streamable transport's HTTP client — where SSRF + egress
  re-attach.
- `AddSendingMiddleware` — where `withMemoryUserIdentifier` moves, and where `_meta` gets stamped.
- `cmd/arcadedb-mcp`'s tool structs — the server half of the `_meta` cutover.

## Specific Ideas

- **"Remove all shit bespoke and native MCP transport package."** The organising directive. It
  settled the facade question outright (D-103) and set the default answer for every collision: prefer
  the SDK's affordance, and keep an Aura mechanism only where a measured invariant demands it.
- **Two of the roadmap's own claims were narrowed by measurement during this discussion**, in the

  cover stdio at all (`mcp/cmd.go` is `Connect` and nothing else), and the reconnect file's
  tool-set drift guard is a registry invariant rather than transport bespoke. Both are recorded as
  decisions with evidence rather than discovered during implementation.

  The counter-argument is preserved in full so a later reader does not mistake the removal for an
  oversight — the same treatment 46-CONTEXT D-01 gave the fencing decision.
- **The memory-identity cut is hard specifically because a fallback would be the hazard** (D-108).
  This inverts the usual instinct: on a parameter that selects which database a write lands in,
  a "safe" dual-source path is the thing that can cross a tenancy boundary.
- The operator declined to interrupt this phase for a frontend issue raised mid-discussion
  (*"not urgent — finish 45.1 first"*), so it is carried in Deferred Ideas rather than folded in.
