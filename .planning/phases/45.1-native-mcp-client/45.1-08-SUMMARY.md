# Plan 45.1-08 — The close-out, measured

## What this plan actually did

Nothing shipped to the runtime except one test. This plan is the phase's evidence, and the
evidence is in `45.1-VALIDATION.md`; what follows is only what was still missing when the
plan opened, and how each hole was closed.

**The mutation score STATE.md line 150 recorded as owed.** `bridge_risk.go` measured 33/36
killed (91.7%) — already past the ≥70% floor, and the temptation was to file the number and
move on. Reading the three survivors is what made it worth running. Two are the `slog.Debug`
call inside `logToolAnnotations` and the call to it: log-only, nothing to assert. The third
was real. Deleting `case mcpActionDestructive: return true, true` survived the entire suite,
because every curated case in `TestMCPToolRiskRecipeTablesUnchanged` was driven with either
nil `Annotations` or `allHints{ReadOnlyHint:false}` — and both of those reach `(true,true)`
down the fallback path as well, so neither could tell whether the curated `return` had fired.
`readOnlyHint:true` is the one declaration that diverts the fallback, to `(false,false)`.
In other words: nothing tested that a trusted-recipe server declaring itself read-only cannot
talk `send_message` out of the approval gate — which is precisely the "operator curation
outranks a server hint" decision plan 45.1-04 recorded. The assertion now runs over every
entry of all three recipe tables, and the file re-measures at 34/36 (94.4%) with only the two
logging mutants left.

**SC#5, which had been left to inference.** The sign-off listed protocol versions, SC#1, SC#3
and SC#4. The identity cutover was not listed, and the reason it felt covered is that SC#1's
`memory__memory_recall` succeeded — which does imply `_meta` carried the identity, since the
server refuses without it. That is an implication, not a measurement, and MCPC-04 has two
halves that an implication cannot separate. Driven live against `aura-arcadedb-mcp`: the tool
manifest carries no `user_identifier` anywhere; the same `memory_recall` without `_meta` comes
back `isError: true` with the model-readable refusal text (a tool error, not a protocol error —
the shape MCPC-04's second-pass correction insisted on); and with `_meta.aura.user_identifier`
it returns this identity's own graph content. Three legs, one session.

**The gate matrix.** Green in CI on `63b456f8e`: `CI`, `CodeQL`, `Skills (CAP-07/CAP-08)`.
Owned-surface coverage 86.2% (25,941/30,108) from the aggregate gate — the full-aggregate
re-run STATE.md line 149 recorded as owed, which could not run during 45.1-03 because a
concurrent session held the tree dirty.

## What this plan did NOT do

**No `prd.md` amendment**, and that is a decision rather than an omission. An amendment
records a measurement that contradicts the PRD; `prd.md` carries no claim about the MCP client
transport, the negotiated protocol version or the recovery mechanism, so these measurements
had nothing to correct there. The corrections this phase did produce were to its own RESEARCH
(Corrections 1–3, the third of them corrected again by SC#3) and they live next to the
evidence in `45.1-VALIDATION.md`.

**Nyquist per-task sampling is still owed.** `nyquist_compliant` stays `false` and the
Per-Task Verification Map is still TBD: it is populated from PLAN task IDs by
`/gsd-validate-phase 45.1`, which has not been run. Live evidence does not substitute for it —
a per-task map answers "is every task sampled", which no amount of end-to-end driving can
answer. Per `audit-milestone` §5.5 this phase is therefore PARTIAL (validated +
`nyquist_compliant: false`), not fully validated, and saying otherwise here would be the
easiest lie in the file.
