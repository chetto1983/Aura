## Manual-Only Verifications

### Live evidence — driven on the running stack 2026-08-16 (image built from `5b2f2a958`)

Every line below is a measurement taken through the real cockpit API against the live
deployment, not a unit test. The agent chose the tools itself; no call was hand-crafted.

**Negotiated protocol version — all three sidecars agree.** From the mount log:

```
mcp session open server=calendar transport=http protocol_version=2025-11-25 → mounted tools=14
mcp session open server=memory   transport=http protocol_version=2025-11-25 → mounted tools=4
mcp session open server=whatsapp transport=http protocol_version=2025-11-25 → mounted tools=14
```

The retention question this was meant to settle is therefore universal, not
per-server-conditional: there is no version split across the three forks to accommodate.

**SC#1 — live tool surface parity.** One conversation
(`01a00ca1-636a-7136-9d13-6be19169a9ca`), three prompts, `aura.tool_invocations`:

| tool | calls | outcome |
|---|---|---|
| `tool_search` | 6 | ok (5 ms) |
| `calendar__list_accounts` | 2 | ok (80 ms) |
| `calendar__get_calendar_events` | 2 | error — *no accounts configured*, reported as such |
| `memory__memory_recall` | 2 | ok (13 ms) |
| `whatsapp__list_chats` | 2 | ok (50 ms) |

All three sidecars answered through the SDK-backed client, and WhatsApp returned real data
(one private chat, last message 28 July 2026). The calendar error is the honest one: the
account is not connected, and the agent said so instead of inventing a schedule.

**SC#3 — kill and restart, and the phase's own hypothesis is corrected.** `docker kill
aura-whatsapp` mid-conversation, then the same question:

```
WARN mcp session closed  server=whatsapp  error="standalone SSE stream: failed to reconnect
     (session ID: d8d6841be…): connection failed after 5 attempts: ssrf: resolve "whatsapp":
     lookup whatsapp on 127.0.0.11:53: no such host"
WARN mcp redial failed   server=whatsapp  failures=1 backoff=500ms breaker_open_until=0001-01-01…
ERROR agent tool error   tool=whatsapp__list_messages err="redial mcp \"whatsapp\": …no such host"
```

The agent told the operator it was an infrastructure failure (DNS), not a data one. After
`docker compose up -d whatsapp`, the next question was answered with real data — and the log
shows a **new session id** (`a6e5aee4…`, against the dead `d8d6841b…`). So recovery is a
fresh session opened by the supervisor's bounded redial, not a silent reuse and not a
daemon restart. RESEARCH Correction 3 said the call would simply be a fresh POST with no
reconnect loop; the redial line above shows a supervisor with backoff and a breaker, which
is what actually ran.

**SC#4 — SSRF/egress refusal, both halves.** An HTTP server mounted at the cloud-metadata
address, then at a hostname that resolves to loopback:

```
mcp doctor ssrf-probe → mcp "ssrf-probe": ssrf: blocked target 169.254.169.254 (link_local)
mcp doctor ssrf-probe → mcp "ssrf-probe": ssrf: blocked target 127.0.0.1 (loopback)
```

The second is the one worth having: `localtest.me` is a public DNS name, so the refusal came
from resolving-then-classifying, not from pattern-matching a literal IP. The probe server was
removed afterwards and the three sidecars re-mount clean.

Also measured on the way in: the type↔trust matrix is enforced at config load —
`streamable_http server cannot have trust class "trusted_local"` — so an HTTP server cannot
be given a local server's trust even by hand-editing `servers.json`.
