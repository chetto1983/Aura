# Plan 45.1-07 — Elicitation, bounded and surfaced

## What shipped

Three pieces, in three commits.

**The handler** (`internal/agent/mcptools/elicitation.go`, 294 LOC). Bounded by
`AURA_MCP_ELICITATION_TIMEOUT_SEC` (default 300s, `<= 0` disables), fail-closed on every path, and
it never returns a non-nil error. A consent surface that ignores ctx runs on its own goroutine
behind a buffered channel, so it cannot hold the in-flight agent turn open and cannot leak when the
deadline wins.

**The wiring** (`mount.go`). `MountOptions` + `MountManagedServerWithOptions`; the four older
exported entry points delegate with a zero `Elicitation`, so this was additive rather than a
signature churn. `elicitationHandlerFor` returns a nil handler for a nil consent, which is what
keeps a consent-less mount from advertising a capability it cannot honour.

**The surface** (`cmd/aura/elicitation_consent.go`, 194 LOC). Late-bound `channels.Deliverer`
implementation that delivers the ask and declines. `renderElicitationPrompt` is the only place a
mounted server's text becomes operator text.

## What this does NOT do

It closes no security hole, and the code says so in three places. With no handler registered the
SDK already refuses on Aura's behalf — `c.elicit` returns `CodeInvalidParams` and does **not**
auto-fulfil (go-sdk@v1.7.0 `client.go:862-864`). What this buys is that a legitimate
multi-round-trip tool stops failing in silence, and that the operator learns which server asked
for what.

It also does not complete a multi-round-trip tool in one turn. The operator sees the ask and
re-drives the tool out of band. That was the accepted cost of option A.

## The thing the test found

The first draft of the in-memory test called `ServerSession.Elicit` and the SDK refused outright:

> `"elicitation/create" cannot be sent while serving a request on protocol version 2026-07-28: return an InputRequests map instead (multi round-trip requests, SEP-2322)`

On this protocol a server does not initiate `elicitation/create` mid-request at all. It returns an
`InputRequests` map in its `CallToolResult`, and `clientMultiRoundTripMiddleware` calls
`fulfillInputRequests` (`mrtr.go:233-268`), which dispatches `*ElicitParams` to the client's
handler. The test now drives a real `CallTool` through that path. Had the plan's assertion been
taken on trust, the handler would have shipped with a test that proved a path production never
takes.

## Deviations from plan

- **The obs counter is not a new instrument.** The plan asked for `MCPElicitationsID` /
  `aura.mcp.elicitation` dimensioned by server and by a seven-valued action attribute. `internal/obs`
  exposes emission ONLY through `Boundary`, whose outcome is derived from the error
  (`nil`→success, `context.Canceled`→canceled, `context.DeadlineExceeded`→timeout, else error) —
  there is no API for a counter with an arbitrary dimension. Adding one would be a bespoke widening
  of a shared package for a single call site. Instead the existing MCP call counter is reused with a
  new catalog-owned operation value `mcp_elicitation`, and the finer action (`url_declined`,
  `no_surface`, unrecognised) rides the structured log. Note also that `AttributeOperation` is a
  finite set with a `ValueOther` fallback, so the plan's "dimensioned by the server name" would have
  collapsed every server to `other` anyway — the catalog is deliberately the gate that keeps a
  server-supplied string out of a metric dimension.
- **The consent surface is late-bound**, which the plan did not anticipate. It could not be
  constructed-and-bound in `buildRegistryWithMCP` because the channels Registry does not exist yet
  at mount time. The existing `cron.ChannelDeliverer` late-binding pattern was followed rather than
  reordering boot.
- **This plan was completed inline by the orchestrator, not by a gsd-executor subagent**, at the
  operator's direction after six dispatches in this phase were killed by a 600-second stream
  watchdog — three of them before emitting a single tool call.

## Env catalog — a finding, not a task quietly skipped

The plan asked for `AURA_MCP_ELICITATION_TIMEOUT_SEC` to be added to the project's env catalog. It
was not, deliberately: `AURA_MCP_MOUNT_TIMEOUT` and `AURA_MCP_SHUTDOWN_TIMEOUT` — both real, both
in use — are absent from `prd.md` too, and `AURA_MCP_CALL_TIMEOUT_SEC` appears there only inside an
amendment's prose, not in an index. The whole `AURA_MCP_*` family is uncatalogued, so adding one
member would be inconsistent noise rather than coverage. The new var follows
`configuredMCPCallTimeout`'s package-local convention exactly. Cataloguing the family is a
PRD-amendment-shaped job, and it is recorded here rather than half-done.
