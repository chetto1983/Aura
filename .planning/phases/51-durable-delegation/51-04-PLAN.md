<objective>
Make concurrent worker memory writes correct by construction (**SWARM-07**, **SC#5**).

SWARM-07 reads *"durable facts (AUTO-03) **and reasoning traces (MEM-03)**"*, and the trace
clause is not dropped here: D-10's fix lands at the `cmd/arcadedb-mcp` boundary —
host-derived actor immediately before the `arcadedb.Fact{}` literal, exactly where
`canonicalSubject` already sits — and EVERY write that reaches the graph through the
memory MCP crosses that same boundary, facts and traces alike. There is no separate trace write
path to fix, which is precisely why the boundary was chosen over a per-call-site patch.

Three decisions, three very different amounts of work:
- **D-09 — duplicate suppression: NO WORK NEEDED.** `factIdentity(fact)` derives a content key
  and `attachFactSource` attaches an additional source to the existing fact BEFORE any create
  is attempted (`internal/arcadedb/memory.go` ~line 265). Two workers learning the same thing
  already produce one fact with two sources. This is recorded so no executor builds it again;
  the only new artifact is a test that PROVES the shipped behaviour under real concurrency.
- **D-10 — attribution becomes host-derived.** `RunID` is model-supplied today and marked
  `jsonschema:"required"`, so "no fact attributed to the parent" currently rests on the model
  telling the truth. Follow LibreChat's `createMemoryTool({userId, ...})`: close the actor at
  construction, so **the model gets no field to lie in** rather than a field the host corrects.
- **D-11 — workers do not supersede.** A worker ADDS facts; closing a still-valid fact stays
  with the parent and the operator. This removes the concurrency hazard by SCOPE rather than by
  locking (`UpsertFact` is a sequence of separate `Command` calls; only the create leg has race
  compensation, `closeSuperseded` has none). Accepted cost, stated plainly: a worker cannot
  rectify what it discovers to be wrong.

Purpose: SC#5. Output: a host-derived provenance path, an extracted authority check, and a
real goroutine fan-out test.
</objective>

  <decision>D-10 is ONE-WAY: it changes the published schema of a shipped MCP tool. `MemoryFactSource` is shared by THREE sites, not one. Decide which shape removes the model's ability to ASSERT provenance on the WRITE path while leaving `memory_forget`'s ability to QUERY BY a run id, and the read-back, intact.</decision>
  <context>
`51-CONTEXT.md` does not specify which, and `51-RESEARCH.md` §Risk Register requires the plan
to pick one and document it.

**Read this before choosing.** `MemoryFactSource` is documented in-tree as *"the single
provenance shape accepted and returned by the memory MCP"* (`cmd/arcadedb-mcp/tool_memory.go:17-21`).
It has THREE consumers, not one:

| Site | What it does with `RunID` |
|---|---|
| `tool_memory.go:124` (`memory_upsert_fact`) | **attribution** — `arcadedb.FactSource{RunID: in.Source.RunID, ...}`. This is the one D-10 removes |
| `tool_forget.go:20`, `:69-74` (`memory_forget`) | **filter** — `MemoryForgetInput.Source` is a `*MemoryFactSource`, and `in.Source.RunID` becomes `arcadedb.ForgetFilter{SourceRunID: ...}` |
| `tool_memory.go:354` (`toHits`) | **returned** on read-back, so a recall result can say which run supported a fact |

The distinction is load-bearing, not a nuance: **D-10's point is that the model may not ASSERT
provenance. Nothing in D-10 says it may not QUERY BY a run id.** `memory_forget`'s source-scoped
mode is that tool's whole reason for existing — its own doc comment says it is *"a filter rather
than an id because the thing most often worth removing is not one fact but everything a run
wrote — a probe, a bad extraction, a batch written under the wrong identity."* So a change that
deletes `RunID` from the shared struct destroys that mode, and a change that leaves the shared
struct alone but doc-comments it *"the host value always wins and the field is ignored"* prints a
statement that is FALSE on the forget path and on the read-back.

The WRITE-side caller set is the one MEM-04/D-19 already covers: the bridge, the CLI, and
host-driven writes — plus any external skill or script that passes `source.run_id` to
`memory_upsert_fact` today. Reversal is cheap in LOC but expensive in TRUST: facts written under
the host-derived scheme have a real, host-verified run id; facts written after a revert go back
to model-asserted provenance with no visible marker distinguishing the two eras.
