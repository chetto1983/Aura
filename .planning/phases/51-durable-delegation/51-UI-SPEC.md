# Phase 51 — UI Design Contract

> Visual and interaction contract for the SWARM-12 + SWARM-10 gap: the delegation delivery
> envelope (chip in chat, full report as a canvas artifact, one static Telegram message) and
> the cockpit's parallel read-only worker pane + `swarm_status` chip. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker. This is an EXTENSION of Aura's existing,
> shipped design system — every token, class and component named below already exists in
> `web/src`; nothing here introduces a new library, a new color, or a new type scale.

**Read before implementing:** `.planning/phases/51-durable-delegation/51-UX-ENVELOPE-RESEARCH.md`
(the reference study — hermes/LibreChat/open-claude-cowork/assistant-ui/codex/ADK) and
`.planning/phases/51-durable-delegation/51-CONTEXT.md` D-15 (the locked operator decisions).
This document turns that research into an implementable contract; it does not re-argue it.

## Spacing Scale

Declared values (Tailwind's default 4px unit, already in use project-wide):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps inside a status cell |
| sm | 8px | Chip row internal gaps (`gap-2`), stacked field spacing |
| md | 16px | Worker pane padding, panel header padding (matches `ArtifactsPanel`'s `px-3 pt-3` family scaled to the pane's own container) |
| lg | 24px | Section breaks inside the worker pane (parent-chat vs. picker vs. transcript) |
| xl | 32px | Not used by this gap |
| 2xl | 48px | Not used by this gap |
| 3xl | 64px | Not used by this gap |

**Exceptions:**
- **Density system** (`data-density="compact|operator|review"`, `theme.css:86-88`) scales
  `--space-unit`/`--row-h`/`--font-base` (3px/30px/14px → 4px/34px/15.5px → 6px/42px/16px). The
  chip row and worker-pane tab MUST use `--row-h` for their minimum row height, not a hardcoded
  value, so they respect the operator's chosen density like every other list row in the cockpit.
- **44px touch-target floor is a literal px minimum, never `rem`.** The root font is
  density-driven (14/15.5/16px), so a `rem`-based target silently shrinks below 44px at compact
  density. Every interactive element this gap adds (chip's "watch worker" control, worker-pane
  tab, artifact pointer) uses the SAME class fragment already shipped for this purpose:
  `min-h-[44px] min-w-[44px]` (see `ExternalStoreChat_messages.tsx` `MESSAGE_ACTION_CLASS`,
  `data-required-touch-target`).

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--color-bg` | Page/pane background |
| Secondary (30%) | `--color-surface` / `--color-surface-2` | Chip row container, worker-pane background, panel header bar |
| Accent (10%) | `--color-accent-text` (dark `#D3E3FD` / light `#07346F`), ring `--color-ring` | See reserved-for list below — nothing else |
| Destructive | `--color-danger` | `failed` status dot/label/icon only. No new destructive action is introduced by this gap (kill/pause per worker is explicitly out of perimeter, see UX-ENVELOPE-RESEARCH §Perimeter) |

**Accent reserved for (exhaustive):**
1. The "watch worker" pointer control on each chip row (icon + focus state).
2. The active tab's underline/indicator in the worker picker (codex `/agent` pattern).
3. Focus rings on every new interactive element (`--color-ring`, `focus-visible:ring-2
   focus-visible:ring-accent` — the exact class already used by `ArtifactsPanel`'s buttons).
4. The report-artifact pointer icon/link on a terminal chip row.

Accent is never used for a status dot, a background fill, or as a generic "important" highlight.

**New semantic status colors** (extends the existing `success`/`warning`/`danger` triad in
`swarmRow.ts` — same tokens, no new hex values):
- `running` → `--color-info` (new use of an existing, previously-unused-in-swarm token)
- `ok` → `--color-success` (unchanged)
- `failed` → `--color-danger` (unchanged)
- `awaiting_input` (the SWARM-06 pause, today's `needs_user_input`) → `--color-warning`
- `stalled` (D-03's inactivity signal) → `--color-warning` — **same color as `awaiting_input` by
  design**, differentiated by icon and label text per the rule already stated in
  `SwarmReportTable.tsx`'s own header comment: *"color is never the only signal"*.

## Delegation Delivery Envelope Contract

This section is additive to the template — it is the load-bearing part of this gap's contract
and is what `gsd-planner`/`gsd-executor` implement against directly.

### 1. The chat chip (extends `SwarmReportTable.tsx` / `swarmRow.ts` — do not build a new component)

The existing `SwarmReportTable` already renders exactly this row shape for the SYNCHRONOUS case:
`# index · child_id (mono) · status dot+label · summary`, expandable in place. This gap extends
it, it does not replace it:

- **New statuses added to `SwarmStatus`:** `running`, `stalled` (alongside the existing `ok`,
  `failed`, `needs_user_input`). `SWARM_DOT_CLASS`/`SWARM_STATUS_KEY` in `swarmRow.ts` gain two
  entries; `isSwarmStatus` gains the two new literals.
- **Running dot:** `bg-info` with Tailwind's built-in `animate-pulse` (no new animation is
  authored; the existing `--motion-*` CSS vars govern nothing here because `animate-pulse` is a
  Tailwind utility, not a custom keyframe).
- **Stalled vs. awaiting_input:** both `bg-warning`, differentiated by a 16px lucide icon next to
  the label — `Clock` for `stalled`, `HelpCircle` for `awaiting_input` — plus distinct label text
  ("Stalled"/"Bloccato" vs. "Needs input"/"Richiede input").
- **Duration column (new):** reuses `useElapsed`/`formatElapsed` from `durationFormat.ts`
  verbatim — live-ticking while `running`, frozen once a terminal status lands, `tabular-nums`
  mono, exactly the convention `ToolActivityCard` already uses. Rendered as a 5th cell in the
  row's collapsed grid (extend the existing `grid-cols-[3rem_1fr_8rem_2fr]` template).
- **Pointer affordances (two separate 44px-min controls per row, never one ambiguous click
  target):**
  1. **"Watch worker" / "Osserva worker"** — always present once the job is claimed
     (`running`/`stalled`/`awaiting_input`/terminal) — opens the worker pane (§2) focused on this
     `child_id`.
  2. **"View report" / "Vedi report"** — present ONLY on terminal rows (`ok`/`failed`) once the
     consolidated report artifact exists — opens the `ArtifactsPanel`/`PreviewModal` for that
     asset, reusing the existing `onArtifact` auto-open wiring in `AppShell.tsx` (an `aura.artifact`
     frame for a delegation report auto-opens the panel once per thread, exactly like `send_file`
     does today — no new auto-open rule).
- **What is explicitly NOT added to the chip:** no raw JSON, no full report body, no kill/pause
  control (perimeter, see UX-ENVELOPE-RESEARCH §Perimeter).

### 2. The full report artifact (canvas)

- Persisted as a `text/markdown` asset through the existing `aura.artifact` seam (`send_file`'s
  seam — `internal/agui/translator.go:19`, `Actions.ArtifactDelta`). No new frame type, no new
  artifact renderer: `ArtifactsPanel` + `ArtifactRow` + `PreviewModal` render it exactly like any
  other markdown asset already does (`artifactMeta.ts`'s existing renderer gate).
- Title convention: the worker's goal, one line, capped — matching the chip's own goal-line cap
  (§4 below) so the artifact list and the chip agree on what the delegation was "about."

### 3. The worker pane — DECIDED by UI research (operator may override)

**Decision A — placement: a third resizable panel, not a tab inside the Artifacts panel.**

Rationale, grounded in the references and the existing `AppShell.tsx` layout:
- `ArtifactsPanel` is architected around discrete, static, previewable **rows**
  (`useThreadArtifacts`, lazy `PreviewModal` with six lazy renderer chunks for docx/xlsx/etc.).
  A live, auto-scrolling, append-only agent thread does not fit that "list of finished documents"
  mental model or its lazy-mount contract — nesting it as a tab would either break that contract
  or force the panel to hold two unrelated data-fetching strategies (`useThreadArtifacts` polling
  vs. an SSE/tail stream).
- assistant-ui's own primitive for this — `ReadonlyThreadProvider` — is documented and shipped as
  a **side-panel** primitive, independent of any artifact/document viewer; it is the direct
  mechanism for "a second `Thread` beside the main one," not a tab inside a file browser.
- codex TUI, the closest reference in `51-UX-ENVELOPE-RESEARCH.md`'s table, models a watched
  sub-agent as its own addressable thread with a picker (`/agent`), never as a tab under a
  file/artifact view.
- `AppShell.tsx` already generalizes its right rail into a **dynamic panel-id set**
  (`useArtifactsPanel`'s `panelIds`, namespaced `react-resizable-panels` layout persistence) —
  the exact mechanism a worker-pane panel reuses, not a new one.
- **Desktop concurrency rule:** the worker pane and the Artifacts panel occupy the SAME right-rail
  slot and are mutually exclusive by default (one at a time), matching `chat-workspace`'s
  `minSize: 380px` floor — a simultaneous 4-column layout (nav + chat + artifacts + pane) is not
  designed and is explicitly out of scope. Opening one while the other is open closes the other,
  the same "one heavy surface" discipline `useSurfaceRestore` already enforces for overlays.
- **Mobile:** the worker pane collapses into the SAME `Drawer`/overlay slot `ArtifactsDrawer`
  already uses (`useSurfaceRestore().overlayOpen`), governed by the same "one heavy overlay at a
  time" rule against the nav drawer. No new overlay mechanism.

**Decision B — content: tool calls + text only, no reasoning deltas.**

Rationale:
- ADK's `is_final_response()` rule (the closest documented precedent, `adk-subagent-visibility
  -2026-08-29.md`) treats only final text as chat-worthy; codex's own sub-agent tree view shows
  tool-call lines and completion lines, never raw chain-of-thought.
- The operator's own words on 2026-08-29 were *"vedere l'agente lavorare"* (watch it work) — tool
  calls and their outcomes ARE the work; raw reasoning deltas are the most token-heavy, least
  legible part of a stream and were not asked for.
- Worker output rides under the untrusted-tool-output envelope (D-04's spike-098 fix); giving a
  worker's raw reasoning stream the same visual prominence as the operator's own agent's curated
  `ReasoningPill` would blur a trust boundary that the delivery envelope was deliberately built to
  keep visible.
- **Reversibility is cheap either way:** `MessagePartPrimitive.Messages` inherits the parent's
  toolkit renderers by construction, so if this is revisited, wiring `Reasoning` into the nested
  render is additive, not a redesign.

**Mechanics (both decisions, together — nothing here is new protocol):**
- The worker pane is `ReadonlyThreadProvider` fed by `<conv>-swarm-<childID>`'s message array —
  the SAME `agent.Event → ThreadMessage` conversion `sseAdapter.ts` already does for the main
  thread, applied to the transcript's events (per `51-UX-ENVELOPE-RESEARCH.md`'s consequence for
  G2). Tool-call rendering inherits `ToolFallback`/`toolSummary.ts` for free — the pane's tool
  cards look and behave exactly like the main thread's.
- **Picker:** a horizontal `role="tablist"` of workers above the pane content, one tab per
  `child_id`, each a `min-h-[44px] min-w-[44px]` target. Keyboard: `ArrowLeft`/`ArrowRight` moves
  focus between tabs (native tablist roving-tabindex pattern), `Home`/`End` jump to first/last,
  `Enter`/`Space` activates. The active tab carries the accent underline (Color § Accent, item 2)
  and `aria-selected="true"`; every tab's status dot mirrors the chip's own dot (§1) so the
  picker and the chip never disagree about a worker's state.
- **Header:** reuses `ArtifactsPanel`'s exact `<h2>` treatment (Typography § Panel heading) with
  an `X` close button in the same position/size (`size-7`, `hover:bg-surface-3`).
- **Live updates:** push only (SSE tail of the transcript, per the research doc's explicit
  perimeter note: *"No cockpit-side polling loop for delegation status"*). The pane and the chip
  read the same stream; no separate poll for either.

### 4. Telegram — locked by D-15, specified exactly here

**Exactly one message per terminal outcome. No edited-in-place status message, no narration, no
report body, no progress relay.** Italian, per the operator's stated channel language.

Message shape (status glyph line, goal one line ≤80 runes, blank line, summary ≤300 runes, blank
line, fixed closing line):

```
✅ Worker completato: <goal, ≤80 rune, one line>

<summary, ≤300 rune>

Dettagli nel cockpit.
```

```
❌ Worker fallito: <goal, ≤80 rune, one line>

<summary or error, ≤300 rune>

Dettagli nel cockpit.
```

```
⚠️ Worker non consegnato dopo 8 tentativi: <goal, ≤80 rune, one line>

Dettagli nel cockpit.
```

- **Glyphs:** ✅ `ok`, ❌ `failed`, ⚠️ `dead_letter` (delivery exhausted its retry budget —
  `attempt_count == max_attempts`, D-01's measured terminal case). No glyph exists for
  `running`/`stalled`/`awaiting_input` — those never reach Telegram (no progress relay, per D-15;
  a worker's own `ask_user` pause reaches the operator through the EXISTING separate HITL relay,
  unchanged by this gap, not through this delivery envelope).
- **Goal cap (≤80 runes):** not explicitly numbered in D-15 (only "one line" is locked); 80 runes
  is this research's default, chosen to fit one Telegram preview line without wrapping on a phone
  screen. **Operator may override this number**; the "one line, no wrapping" requirement itself
  is locked.
- **Summary cap (≤300 runes):** locked by D-15 verbatim.
- **Closing line ("Dettagli nel cockpit."):** locked by D-15 verbatim, always present, always the
  last line, never varied per outcome.
- **Truncation rule:** both caps truncate on a rune boundary (never mid-multibyte-character) with
  a trailing `…`; truncation happens server-side before send, not client-displayed.
