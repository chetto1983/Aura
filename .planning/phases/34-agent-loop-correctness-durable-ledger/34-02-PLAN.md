<objective>
Enforce terminal `text_response` exclusivity (LOOP-01 / F-003, D-01) and lock the already-shipped mutating-panic classification (LOOP-08 / F-031) with a regression test.

**LOOP-01:** In `dispatch()`, when the partition finds a terminal `text_response` alongside ANY runnable sibling — OR more than one terminal — reject the whole step atomically before any sibling hook/exec runs, by reusing the existing dedup-trip path (`appendSyntheticToolResults(calls, ...)` + `maybeRecover`→`finalize`). This matches native tool-use semantics (any tool call present ⇒ not final) and needs zero reliance on the untrustworthy `Mutating` flag. It also fixes the latent bug where a second `text_response` in a step is silently `continue`-skipped today.

**LOOP-08 / D-13:** `runToolRecovering` already resolves `tool.Spec().Mutating` before executing and copies it into the panic-recovery `toolRunResult` (verified `internal/agent/llm_agent_parallel.go:66-96`, wired to `a.sideEffected`/`gateCompletion`). The requirement box stays `[ ]` because it lacks a test — add the regression test that a mutating tool panicking AFTER its side effect still arms `a.sideEffected`.

Purpose: close the "final answer executed beside a mutating sibling" hole and prove the post-mutation gate survives a panic. Both are internal-agent concerns with no DB/composition-root touch, so this plan runs in Wave 1 fully parallel to the DB/HITL work.

Output: the exclusivity short-circuit in `dispatch()`, a table reject test, and the mutating-panic regression test.
</objective>
