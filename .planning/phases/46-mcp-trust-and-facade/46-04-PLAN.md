<objective>
Replace `bridgePolicy.defaultDeferred()`'s unconditional `true` with D-27's arithmetic: a server
exposing <= 3 model-facing tools earns an always-loaded slot, capped at 2 slots globally, granted in
mount order, overflow deferred.

Purpose: MCP-04 needs the two curated tools always loaded, and D-17 forbids that being a list of
names. Counting needs no declaration anywhere, so a self-minted or ad hoc server with one good tool
is loaded by the same arithmetic that defers a 28-tool raw surface — which is exactly what Success
Criterion 6 promises.

Output: `bridge_deferral.go` plus its daemon-free unit test (VALIDATION.md Wave 0 gap 2), with the
freeze-at-mount answer to `refreshSpec` churn.

**This lands before either fork curates, and is a no-op on today's surface:** memory exposes 4
model-facing tools, calendar and WhatsApp expose 14 each, so every mounted server still comes out
deferred. That is deliberate — it lets the arithmetic be proven in isolation before the tracer
depends on it.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-46-11 | Elevation of Privilege | `grantLoadedSlot` — a mounted server promoting itself into the always-loaded manifest | mitigate | Promotion is earned only by exposing <= 3 model-facing tools AND by the global 2-slot budget being unspent; overflow fails closed to deferred. | T-46-SC | Tampering | package installs | mitigate | No package installs in this phase; nothing to gate. |
