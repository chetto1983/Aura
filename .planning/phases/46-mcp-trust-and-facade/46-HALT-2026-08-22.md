## 4. The MCP Apps views are live, and the 14→1 collapse breaks them twice

The views are not aspirational. The whole path exists and is reachable today:
`hydrateViews` (bridge_views.go:82) → `viewDescriptor` (:57) → `Actions.ViewDelta`
(llm_agent_events.go:151) → `aura.mcp_view` CUSTOM event (agui/translator.go:389) →
`DisplayRouter.tsx:64` → `McpViewFrame`. The gate `policy.views = mcp.TrustMayRenderViews(trust)`
(bridge_risk.go:93) is **true** for `recipe:whatsapp` (trusted_recipe), and `viewRefFor`
(bridge_views.go:46) reads the tool's `_meta.ui` with no capability check — so the bindings above
are picked up.

Collapsing all 14 into one multiplexed `messages(action=…)` tool breaks this in two independent
ways:

1. **One tool carries one view.** `ViewRef` is per-tool, frozen at mount, and `viewDescriptor`
   emits the fixed `b.view.ResourceURI`. There is no per-result view selection. A single curated
   tool can bind at most one `resourceUri`, so `thread.html` and `chats.html` cannot both survive.
2. **The surviving view goes inert.** `CallReadOnlyTool` (bridge_views.go:177) gates every view
   callback — paging, refresh, drill-down — on `toolIsReadOnly`, which is
   `advertised && !bt.Spec().Mutating` (bridge_supervisor.go:339-344). A multiplexed tool covering
   `send_message` must be Mutating (46-06 requires it classify Destructive), so every callback is
   refused. D-26 deletes the raw `list_messages`/`list_chats`, leaving nothing read-only to call.

Nothing in 46-CONTEXT.md, 46-RESEARCH.md or the plans mentions this — the phase was scoped against
the pre-2026-08-17 branch, which had no views at all.

`sha-e0b8345` = main `e0b83459`, digest `sha256:7d557d462994dca468cf19f69931743cb99e34a2ca5c47969aa77eba7df04568`.

**Why a `sha-` tag and not `:sidecar`.** Two workflows on the fork write `:sidecar` —
`aura-publish-image.yml` (branches `aura/cockpit-connect`, `aura/verygoodplugins-fusion`) and
`publish-image.yml` (`main`, via `type=raw,enable={{is_default_branch}}`). Which build it names
depends on which ran last, so it was never a safe pin. It happens to point at main today
(run 2026-08-22T09:47:59); that is luck, not a guarantee.

**A convention correction for the plans.** 46-06 and 46-08 both require an immutable
`ghcr.io/…:<40-hex-sha>` tag. That format is **unavailable on the WhatsApp fork**: `publish-image.yml`
uses `type=sha`, which mints `sha-<7hex>`. The 40-hex form only exists where a workflow passes
`${{ github.sha }}` verbatim — which the **PIM** fork's `aura-publish-image.yml` does. So the
must_have holds for calendar and must be reworded for WhatsApp.

## The views RENDER today — measured, not inferred (2026-08-22)

The earlier `sandbox_origin=""` reading was a **stale log line**, emitted by a process instance that
started before `AURA_MCP_SANDBOX_ORIGIN` was in place. The current process logs
`sandbox_origin=https://views.pmsyncaura.dedyn.io`, and `/proc/1/environ` confirms it. Measured
against the live cockpit on an authenticated authula session:

- `GET /api/mcp/view?server=whatsapp&uri=ui://whatsapp/thread.html` → **HTTP 200**, 27,733 bytes of
  armed HTML, `sandbox_origin: https://views.pmsyncaura.dedyn.io`, `declared.sealed: true`, applied
  CSP `default-src 'none'; connect-src 'none'; frame-src 'none'; base-uri 'none'; …`.
- `POST /api/mcp/view/call {server:whatsapp, tool:list_chats}` → **200**, returning real live chat
  rows. The view-initiated read path works.
- `POST /api/mcp/view/call {server:whatsapp, tool:send_message}` → **`tool call refused`, HTTP 403**.

**That 403 is the measurement that settles §4.** The read/mutate split at `CallReadOnlyTool` is not
a code-reading inference — it is live behaviour. A merged `messages(action=…)` tool is necessarily
Mutating (46-06 requires `send_message` classify Destructive), so it lands on the 403 side of the
gate that `list_chats` currently passes. Collapsing 14→1 does not degrade the views; it takes a
working, in-use capability to a hard refusal.

This raises the cost of "curate all 14 and drop the views" and lowers the cost of exempting the two
view-bound tools: the exemption protects something the operator can use right now.
