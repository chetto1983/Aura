<objective>
**The tracer slice.** Wire the curated calendar tool through Aura end to end in one atomic commit:
re-key the risk table to action names, set `Multiplexed` only where a classifier already exists,
register the per-action classifier, reconcile the fork's action enum at mount, and pin the sidecar
image — then prove a read and a destructive action of the SAME tool classify differently.

Purpose: D-21 is the phase's real code and it fails SILENTLY. A bridged tool never sets
`Multiplexed`, so `ValidateClassifiable`'s per-action assertion skips it and `classify` gives ONE
flat tier to the whole merged tool: `calendar(action=list_calendars)` and
`calendar(action=send_email)` classify identically, so either every read demands approval or
`send_email` is un-gated. No panic warns you.

**Why this is the tracer and why it comes after the amendments.** The PRD amendments gate the code
(CLAUDE.md), so they are wave 1 and are the phase's actual first deliverable, not overhead. Only
then does ONE thin vertical slice — a single curated tool, one read action and one destructive
action, classified per-action, mounted, dispatched in a real turn — get built and verified (plan
46-07) BEFORE the second sidecar, the remaining actions, or any further expansion. The WhatsApp half
(plan 46-08) is a repeat of a proven pattern, not a parallel experiment.

**Landing order (D-32, scoped honestly):** the fork publishes first (46-05), then ONE Aura commit.
D-32's atomicity is per-SOURCE, not phase-wide: the invariant is that a source's table re-key and its
image pin land together. Calendar's do here; WhatsApp's do in 46-08. Splitting either pair across
commits produces a live window in which every calendar read demands approval (table re-keyed, fork
not yet pinned) or the merged tool classifies flat (fork pinned, table not yet re-keyed).
</objective>
