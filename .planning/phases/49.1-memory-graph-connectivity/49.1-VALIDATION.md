> `"CocoIndex con Garage S3"` — depth 1 returned **1** fact, depth 2 returned **15**.

That is the phase in one line. At depth 1 an entity answers only with what is stated
about it directly; at depth 2 it answers with what it is connected to.

- `depth: 1` and an absent `depth` emit a **byte-identical statement**, and that statement

  (`TestFactsAboutDepthOneEmitsTheStatementThatShipped`).
- `depth: 0`, `3`, `-1` and `99` are **refused with a model-readable error** and never

- `depth: 2` keeps the valid-time condition, keeps `LIMIT`, and reports
  `retrieval.path: "mentions"` so a widened answer is distinguishable from a lucky one.
- Ordering is deterministic across two identical calls
  (`TestMemoryMentionsSecondHopIsDeterministic`).

## What these numbers do NOT establish

- **One identity, one corpus.** All figures come from a memory imported mechanically from
  a file-based note collection, one note per fact, each with a bespoke subject. Organically
  captured memory may have a different entity-reuse profile, and the plateau's width is a
  property of this corpus.
- **Nothing about scale.** 107 facts and 209 entities. The sweep is one corpus scan plus one
  command per changed edge; neither the linking cost nor the traversal cost has been measured
  on a corpus an order of magnitude larger.
- **Nothing about conversation turns or document passages.** They were out of scope and have
  no `Entity` edge at all, so no connectivity figure exists for them.
- **Nothing about retrieval quality.** This phase makes facts *reachable*; whether the second
  hop makes answers *better* is a separate measurement against a question set, not run here.

## Inventory performed before writing code

Required by CLAUDE.md, and it changed the implementation twice.

- **ArcadeDB `MATCHES`** is a full Java-regex operator and *can* do case-insensitive
  word-boundary matching in SQL — verified live (`mitigate` vs `(?i).*\bgate\b.*` → 0,
  `neo4j` vs `(?i).*\bNeo4j\b.*` → 1). It is **not** used, because the docs state that
  "LIKE, ILIKE, MATCHES are not using full-text indexes" and no engine function accepts a
  *list* of needles (the whole `text.*` namespace and `sql-functions.adoc` were enumerated).
  Finding which names occur would therefore cost one unindexed scan per candidate name.
  The engine has the capability; it does not fit the access pattern.
- **`DELETE EDGE MENTIONS …` does not parse** — `CommandSQLParsingException`. The working
  form is `DELETE FROM MENTIONS WHERE …`. This was found by probing a throwaway database
  before the code ran, not by a failure in production.
- **`CREATE EDGE … IF NOT EXISTS`** is supported and is a true no-op on replay (same `@rid`,
  no second row), so a sweep racing another writer cannot double an edge.
- **The two-hop shape returns each fact exactly once without `DISTINCT`.** The `MATCH` and
  Cypher forms of the same question both duplicate — nine rows where four were due — and
  would have needed a `DISTINCT` whose absence nothing would have caught.
- **Java's default `\b` uses ASCII `\w`**, so `società` fails its own boundary test without
  `(?U)`. Comparing bytes rather than runes gives the correct behaviour for free.
