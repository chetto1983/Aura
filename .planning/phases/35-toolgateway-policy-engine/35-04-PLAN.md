<objective>
Deliver D-01a, D-01b, D-01c (GATE-03 + GATE-04) — D-01c specifically: the reserve `start` insert is SYNCHRONOUS and committed BEFORE `Execute()` on the mutating path (the async `persistToolInvocationLedger` stays as-is for read-only/observability). This is: the synchronous, fatal-on-failure durable pre-execution reservation and the idempotency-key replay, by promoting the append-only `aura.tool_invocations` ledger — ZERO migration, ZERO new table. Flip `InsertToolInvocation` from `:exec`/`DO NOTHING` to `:execrows` (keep `DO NOTHING`), add the `GetToolInvocationEnd :one` replay query and the `ListInFlightToolInvocationsBefore :many` query (consumed by the 35-05 reconciler), regenerate sqlc, add `Store.Reserve`/`GetEnd`/`ListInFlightBefore`, and wire the reserve→execute→replay gate into the gateway's mutating path inside `execTool`.

**Unified reserve (checker blocker fix):** the reserve gate covers EVERY mutating-Allow outcome — decide.go's plain not-GateRecommended auto-allow AND routeApprove's post-resume `Verdict{Allow, OperatorID}` — through the SAME single `store.Reserve` call before `Decide` returns Allow. The operator_id rides that ONE reservation start's Meta (the executed marker); the approve branch writes NO separate row (35-03 already returns `Verdict{Allow, OperatorID}`, no bare Insert). So an operator-approved, resumed mutating call (the highest-risk category — `skill create/update/delete` at high tier) takes its GATE-03 reservation and GATE-04 idempotency key identically to the auto-allow path, per LOCKED CONTEXT.md D-03 point 2 ("the resume MUST re-enter the gateway so the now-approved call still takes its GATE-03 reservation + GATE-04 idempotency key").

Purpose: GATE-03 requires the reservation durable in Postgres BEFORE the mutating `Execute()`; the current write is async/best-effort/non-fatal and absent on headless paths (RESEARCH CV-3). GATE-04's idempotency key is the EXISTING UNIQUE index `(conversation_id, request_id, tool_call_id, event_kind)` — the conditional-write IS the key (Phase-34 D-06). `rows==1` ⇒ reserve acquired → Execute; `rows==0` ⇒ already held → replay the recorded outcome instead of re-invoking. Unifying the approve branch into this ONE reserve call closes the slot-collision the checker flagged (a separate executed Insert would race the reservation's own start/end into ON CONFLICT DO NOTHING).

Output: the `:execrows` + replay query changes, `Store.Reserve`, `internal/gateway/reserve.go`, the decide.go/execTool replay wiring (covering the approve branch), and the `db_integration` proof tier including `ApprovedCallReservedAndIdempotent`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| gateway → Postgres ledger | The reservation INSERT is the fail-closed gate; a write failure must block, never allow. |
| retried/duplicate tool_call → ledger | A retry (including a retried operator-approved call) must not double-apply a mutating side effect. |
| approve branch → ledger slot | The approved call's executed marker must ride the ONE reservation start Meta, never a second row competing for the same (triple, event_kind) slot. |
| secret in tool args → durable append-only ledger | The reservation row is un-deletable; a secret must be redacted before it lands. |
