<objective>
Close the ONE escalated gap in Phase 35 (35-VERIFICATION.md, human-verification item 1): the interactive `approve` verdict has no working pause/resume UX, so under `single_user_hardened` every Risky/Destructive mutating tool call (swarm_spawn, skill create/update/delete, task run_now/schedule[agent_job]) renders as a permanent, unresolvable `error: awaiting user input`. The fail-closed guarantee holds (the tool is withheld), but CONTEXT.md's LOCKED decision **D-03 point 2** ("reuse the Phase-25 approval center … persist-before-act; the resume MUST re-enter the gateway") is not realised end-to-end: `internal/gateway.WithResolvedApproval` has zero production callers, the `gateway_approval` ResumeContext is never read by `internal/agui/approvals_api.go` or `internal/runner/runner_resume.go`, and the non-`ask_user` pause path is name-gated in `internal/agent/llm_agent_pause.go`.

This plan wires the three seams the verifier named so an operator can actually resolve a `gateway_approval` pause and the resumed turn RE-ENTERS `gateway.Decide` — which then takes the single reservation via 35-04's funnel and returns `Verdict{Allow, OperatorID}` (D-03 / GATE-01). It closes GATE-01's `approve` verdict path end-to-end.

**Design — mirror two proven in-repo precedents, add no new subsystem:**
1. **ask_user pre-dispatch pause detection** (`internal/agent/llm_agent_pause.go` `pauseCalls`) — the widened detector surfaces a gateway approve as a first-class `Actions.AwaitingInput` Event.
2. **shell_exec session-approval ledger** (`internal/agent/tools/shell_approval.go` `ShellApprovals`) — a mutating tool that needs operator approval is gated, the operator approves via the approval center, a resume hook records the approval in a session ledger keyed by a stable (conv, tool, canonical-args) fingerprint, the model re-issues the exact call, and the gate consults the ledger and executes exactly once. `GatewayApprovals` is the byte-for-byte analog for the gateway; the resume re-enters `gateway.Decide` and rides 35-04's unified reserve.

The `WithResolvedApproval`/`resolvedApproval(ctx)` ctx carrier that 35-03 built stays as the in-process representation of a resolved approval (unit-test seam + same-ctx fast path); `GatewayApprovals` is its cross-turn store, because — verified in the code — an operator resolve (`POST /resolve` → `SubmitAnswers`) and the re-drive (`Turn(convID, nil)`) are SEPARATE Turn calls in BOTH the REPL (`cmd/aura/chat_repl.go`) and the cockpit (`internal/agui`), so a ctx value cannot span them. The ledger is the honest carrier; the resume hook is the sole production writer.

Purpose: realise D-03 point 2 without violating the 35-04 single-reservation invariant or the 35-05 reconciler's uniform start∧¬end candidate set, and without touching Phase-36 identity work.
Output: `internal/gateway/approvals.go` (the ledger), the `WouldApprovePause` peek + `routeApprove` Consume branch, the `llm_agent_pause.go` surfacing, `newGatewayResumeHook` in `cmd/aura`, and a live `db_integration` proof of the end-to-end resume→re-enter→execute-once path.
</objective>

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-35-06-01 | Elevation of Privilege | model self-approving a gated tool | mitigate | The ledger is written ONLY by the host-side resume hook (behind the approval center); `WouldApprovePause`/`routeApprove` only READ/Consume it.
