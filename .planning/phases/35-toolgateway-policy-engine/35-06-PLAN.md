<objective>
Close the ONE escalated gap in Phase 35 (35-VERIFICATION.md, human-verification item 1): the interactive `approve` verdict has no working pause/resume UX, so under `single_user_hardened` every Risky/Destructive mutating tool call (swarm_spawn, skill create/update/delete, task run_now/schedule[agent_job]) renders as a permanent, unresolvable `error: awaiting user input`. The fail-closed guarantee holds (the tool is withheld), but CONTEXT.md's LOCKED decision **D-03 point 2** ("reuse the Phase-25 approval center … persist-before-act; the resume MUST re-enter the gateway") is not realised end-to-end: the `gateway_approval` ResumeContext is never read by `internal/agui/approvals_api.go` or `internal/runner/runner_resume.go`, and the non-`ask_user` pause path is a dead end.

**Design correction (this revision) — mirror the shipped shell_exec approval precedent EXACTLY (checker fix option (a)):**

The prior draft of this plan intercepted the mutating call PRE-DISPATCH (`WouldApprovePause`) and surfaced it as a pause using the original `llm.ToolCall`. That mechanism does NOT survive the persist→resume round-trip: `internal/runner/runner_persist.go`'s `assistantAskUserToolCalls` UNCONDITIONALLY rewrites every `Kind=approval` pause's persisted assistant turn to `ask_user` with synthesized args, so the real tool name (`swarm_spawn`) and real arguments (the `goals` list) are NEVER written to `conversation_turns`. The resume `Turn(convID, nil)` rehydrates strictly from persisted rows (`loadTurnHistory`→`LoadManagedHistory`), so the model would see only `ask_user(resume_context={...,"args_sha256":"<hash>"})` — a hash, not the args — and could never reproduce a matching canonical fingerprint for the ledger key `(conversationID, toolName, argsFingerprint)`. The gap would re-open silently.

The fix mirrors `internal/agent/tools/shell_approval.go` `requireShellApproval` byte-for-byte, but hoisted from inside a tool's `Execute` up into the gateway PEP (which sits ABOVE `tool.Execute` in `execTool`):

1. On a mutating GateRecommended call under `single_user_hardened` + a live responder with **no ledger hit**, `gateway.Decide` returns `Verdict{Decision: Approve, ApprovalRequest: <tools.ToolResult>}`. `execTool` returns that ToolResult **with no error and WITHOUT calling `tool.Execute`** — the mutating side effect is withheld (strictly stronger than shell_exec, whose gate runs inside `Execute`).
2. Because `execTool` returns a normal ToolResult, `runTool`→`toolResultEvent` persists the **REAL** `swarm_spawn(goals=[…])` assistant tool_call turn (verbatim name + args) plus the approval-required message as the RoleTool result. **The real args are now in `conversation_turns`.**
3. The ToolResult (mirroring `shellApprovalRequiredResult`) instructs the model to call `ask_user` with `kind=approval`, a descriptive `question`, and `resume_context={"type":"gateway_approval","tool":…,"conversation_id":…,"args_sha256":…}`, and to "retry the exact call only after the user accepts." The model relays via `ask_user` — the EXISTING name-gated pause path (`llm_agent_pause.go` UNCHANGED) — producing a first-class `Actions.AwaitingInput` Event resolvable in the Phase-25 approval center. The descriptive question renders in `handleListApprovals` (fixes the checker's WARNING; **no `approvals_api.go` change**).
4. Operator accepts → `Runner.SubmitAnswers` → `applyResumeHook` → the production `newGatewayResumeHook` decodes `gateway_approval`+accept and records `GatewayApprovals.Approve(conv, tool, args_sha256, {Approved:true, OperatorID:"local"})` — the byte-for-byte analog of `newShellResumeHook`.
5. Resume `Turn(convID, nil)` → `LoadManagedHistory` rehydrates the verbatim `swarm_spawn(goals=[…])` call → the model re-emits the EXACT same call → `execTool`→`Decide`→`routeApprove` computes `gatewayArgsFingerprint(rawArgs)`, `Consume`s the ledger → `Verdict{Allow, OperatorID}` → the SINGLE 35-04 reservation → `tool.Execute` runs exactly once.

**Two proven in-repo precedents, no new subsystem, no pre-dispatch interception:**
- **shell_exec session-approval ledger** (`internal/agent/tools/shell_approval.go`) — the ledger + resume-hook + model-relayed-ask_user + retry-exact-call shape, replicated as `GatewayApprovals` + `newGatewayResumeHook`.
- **the shipped ask_user pause path** (`llm_agent_pause.go`, UNCHANGED) — the model relays the approval request through it, so the pause detector is not touched.

The `WithResolvedApproval`/`resolvedApproval(ctx)` ctx carrier that 35-03 built stays as the in-process representation of a resolved approval (unit-test seam + same-ctx fast path); `GatewayApprovals` is its cross-turn store, because — verified in the code — an operator resolve (`POST /resolve` → `SubmitAnswers`) and the re-drive (`Turn(convID, nil)`) are SEPARATE Turn calls, so a ctx value cannot span them. The ledger is the honest carrier; the resume hook is the sole production writer.
