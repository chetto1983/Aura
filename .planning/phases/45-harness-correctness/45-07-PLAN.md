<objective>
Expose, at the model-facing MCP boundary, everything plan 45-06 made possible in the client: the
fact identifier on recall, `supersedes_fact_key` on write, and a refusal that comes back as a
successful call carrying its candidate set. Then canonicalize the operator's subject at the one
place every fact is built, so the operator's profile stops splitting across a name and a UUID.

Purpose: HARN-04's guarantee only means something if the model can name a fact — which requires the
identifier to appear on recall and to be accepted on write. And "exactly the fact it names" cannot
be reliably kept if the subject cannot be reliably identified, which is why MEM-04 is bundled into
this phase rather than the later memory-tiers one.

Output: three input/output shape changes on the MCP tool, a host-side canonicalization at
`memoryUpsertFactHandler`, and a decision checkpoint on the published-contract change before it is
written.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model → MCP tool arguments | `subject`, `supersedes`, `supersedes_fact_key` are model-generated; a wrong `fact_key` must fail visibly, never fall back to the broad close |
| MCP handler → idempotency ledger | Whether a refusal is an error or a success determines whether a failed mutation is durably recorded, and therefore whether the corrected retry is deniable |
| identity resolution → subject rewriting | Canonicalization reads the resolved tenant identity; rewriting a subject on a mis-resolved identity would attribute a fact to the wrong operator |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-45-29 | Tampering | a wrong `supersedes_fact_key` silently falling back to the broad subject+predicate close | mitigate | The explicit-key path never falls back: 0 still-valid matches is the refusal case, asserted in Task 2's behaviors and in plan 45-06's client-side test |
| T-45-30 | Repudiation | a refusal recorded as a durable failed mutation, making the corrected retry deniable | mitigate | Refusal is a successful call with a nil error (D-17); Task 2 asserts the nil error explicitly before the implementation exists, so the assertion cannot be retro-fitted to whatever was built |
| T-45-31 | Tampering | canonicalization rewriting a subject that is not the operator | mitigate | Exact `TrimSpace` + case-insensitive equality against two known identifiers only; a negative test asserts a subject merely CONTAINING the operator's name is untouched (ASVS V5) |
| T-45-32 | Information Disclosure | candidate previews on a refusal crossing an identity boundary | accept | ArcadeDB isolation is one database per identity with a tenant-derived credential enforced by the server, and the tenant is resolved from `user_identifier` before the read; a refusal returns only facts the caller could already recall |
| T-45-33 | Spoofing | a caller supplying a `user_identifier` for another operator to canonicalize into their namespace | mitigate | Not introduced by this plan — the handler resolves the tenant exactly as it does today, and canonicalization consumes that resolution rather than any new input. Confirm during Task 3's read that no new caller-controlled path into identity resolution is opened; if one is, stop and report |
| T-45-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs in this plan; the Package Legitimacy Gate is not applicable |
</threat_model>
