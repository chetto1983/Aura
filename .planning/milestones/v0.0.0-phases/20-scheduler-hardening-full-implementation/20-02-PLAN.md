<objective>
Capture the origin of a scheduled task and snapshot the stable owning identity at schedule time (R1, Fork 1). The agent `task` tool reads the conversation id from the tool-call ctx (the `sessionID` set at `llm_agent.go:470`) and forwards it as `CreateTaskInput.OriginConversationID`. The composition-root `cronTaskStore.CreateScheduledTask` adapter resolves that conversation id → `identity_id` ONCE via `conversations.Store.Get` and threads BOTH columns into `cron.CreateTaskParams` (both already exist, migration 0009). Snapshotting identity at enqueue (transactional-outbox / Klaviyo pattern) means a later-deleted origin conversation still resolves the owning channel, and it lets the dispatcher (20-03) read `task.IdentityID` directly with zero lookup.

Purpose: without origin+identity capture there is nothing for the dispatcher to route on — this is the data-population half of the headline fix.
Output: `CreateTaskInput.OriginConversationID`, bare-ctx-safe capture in `actionSchedule`, the adapter's `*conversations.Store` field + resolution, and the tool-level unit test.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent tool ctx → scheduled task row | the conversation id the tool reads from ctx becomes the origin key; it must be the REAL active conversation, not attacker-supplied |
| schedule-time conv→identity resolution | the resolved `identity_id` is the durable delivery key (authorization boundary for who later receives the notification) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-20-04 | Spoofing / wrong-recipient | conv→identity snapshot at schedule time | mitigate | The identity is read from `conversations.Store.Get(originConvID).IdentityID` where `originConvID` comes from the trusted tool-call ctx (`a.sessionID`, set by the agent runtime at llm_agent.go:470), NOT from LLM-supplied tool args. The model cannot inject an arbitrary origin/identity — it only triggers `action=schedule`; the ctx is server-set. |
| T-20-05 | Elevation / stale-identity | snapshot survives a deleted origin conversation (Fork 1) | mitigate | Snapshotting identity at enqueue (no FK on identity) is deliberate: a deleted conversation (`ON DELETE SET NULL` on origin) leaves `identity_id` intact so delivery still resolves the SAME owning user — it cannot silently re-route to another user. Orphaned identity rows (un-onboarded / 'local') resolve to `pgx.ErrNoRows` at delivery → not-my-user fall-through (20-01), never a cross-user leak. |
| T-20-06 | Denial of Service | a real DB error during resolution | mitigate | A non-`ErrConversationNotFound` error hard-fails the schedule (`%w`-wrapped) rather than silently persisting a wrong/empty identity — the operator sees the failure instead of a misrouted reminder. `ErrConversationNotFound` is the only soft path (→ 'local'). |
| T-20-SC | Tampering | npm/pip/cargo installs | accept | No package installs — zero new deps (20-RESEARCH §Package Legitimacy Audit). No checkpoint needed. |
</threat_model>
