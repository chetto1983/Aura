## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| scheduler → channels (Registry.DeliverToIdentity) | the scheduler hands an `identityID` it trusts (snapshot at schedule time, 20-02); the Registry must deliver ONLY to the channel that owns that exact identity |
| channels/telegram → DB (telegram_accounts) | the `identity_id → telegram_user_id` lookup is the authorization decision: the resolved chat id determines WHO receives the message |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-20-01 | Information Disclosure | `Telegram.Deliver` identity→chat resolution | mitigate | Deliver sends ONLY to `tele.ChatID(acct.TelegramUserID)` resolved from the exact `identity_id` via `GetTelegramAccountByIdentity`; a missing/mismatched identity → `pgx.ErrNoRows` → `(false,nil)` (delivers to NObody, falls through) — never a default/last chat. Unit test pins ErrNoRows→(false,nil). |
| T-20-02 | Spoofing / wrong-recipient | non-UUID / `'local'` identity reaching `GetAccountByIdentity` | mitigate | `parseUUID` failure on a non-UUID identity maps to wrapped `pgx.ErrNoRows` → not-my-user → no delivery to any account (Pitfall 6). Test with `identityID="local"` asserts `(false,nil)`, never a stray send. |
| T-20-03 | Tampering / double-delivery | tri-state `(false,err)` misread as "try next channel" | mitigate | The `Deliverer` doc contract + `DeliverToIdentity` return `(false,err)` immediately stops fan-out (no sibling attempt); owns-but-fails unit case asserts the sibling Deliver is never called. Prevents one identity's message leaking to a second channel on a transient error. |
| T-20-SC | Tampering | npm/pip/cargo installs | accept | No package installs in this plan — all deps (`telebot.v4`, `pgx/v5`) already vendored (20-RESEARCH §Package Legitimacy Audit: zero new installs). No slopcheck checkpoint needed. |
