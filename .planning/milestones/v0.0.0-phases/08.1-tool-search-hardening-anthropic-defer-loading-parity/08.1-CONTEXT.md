# Phase 08.1: Tool Search hardening — Anthropic defer_loading parity - Context

**Gathered:** 2026-06-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Harden Aura's in-process `tool_search` hook tool to **Anthropic `defer_loading` parity** (the official Tool Search Tool contract, header `advanced-tool-use-2025-11-20`). This is a HOW-phase: the deferred-tool mechanism already exists (`Spec.Deferred`, `tool_search` non-deferred hook, `Registry.Render` manifest). 08.1 upgrades its *quality* so tool-selection accuracy stays high as the tool count grows toward — and past — the 30–50-tool degradation threshold (Phase 11 skills/7e snippets + future stdio MCP mounts via the retained `internal/agent/mcptools` seam).

**In scope (4 decisions, all locked below):**
1. Replace substring matching with in-process **BM25 ranking over expanded index fields** (name + description + argument names + argument descriptions).
2. **Top-K result cap** with a `max_results` param (default 5).
3. **MCP tool namespacing** (`<server>__<tool>`) in the `mcptools` bridge.
4. Two parity extras: **tool-categories orientation** (inside the `tool_search` Description) + **≥1-non-deferred fail-closed guard**.

**Out of scope (explicit — belong elsewhere):**
- Embedding-semantic / hybrid tool ranking (deferred to a future phase if the catalog crosses ~100–200 tools and paraphrase-recall misses appear).
- PG-FTS-backed tool search (rejected — couples a hot, always-on, offline-sensitive path to Postgres).
- Mounting any real stdio MCP server in production (the `mcptools` seam stays retained-but-unmounted; 08.1 only makes its naming correct for when it *is* mounted).
- Any change to the byte-stable `SystemPrompt` in `internal/agent/prompt.go` (cache-load-bearing — categories ride in the `tool_search` Description instead).
</domain>

<decisions>
## Implementation Decisions

### Ranking engine
- **D-01:** Ranking is **in-process pure-Go BM25/TF-IDF** over the registry. **No DB, no embedding sidecar, no new infra dependency.** Rationale: Codex (most mature peer) uses an in-process `bm25` crate and advertises "BM25" to the model; tool-retrieval research shows BM25 ≥ dense embeddings *for tools specifically* (term-overlap matters; embeddings reward surface similarity over functional relevance — arxiv 2503.01763; ToolBench BM25 nDCG@5 ≈0.853 > dense ≈0.834); Anthropic ships a BM25 variant and **no** managed embedding variant; on the CPU-bound mini-PC BM25 is sub-ms and offline-resilient (memory: `feedback_gpu_not_for_embedding_workload`, `feedback_minipc_cpu_budget`).
- **D-02:** **Index-field expansion is the highest-leverage change**, more than the substring→BM25 axis. Build a per-tool "search document" = tool `Name` + name-with-`_`-as-spaces + full `Description` + **every parameter name + parameter description, extracted recursively from the `Parameters` JSON-Schema** (mirror Codex `default_tool_search_text` / `append_schema_search_text`). The current Name+Summary-only index (`search.go:91`) is the real weakness; research confirms description/arg expansion beats swapping rankers (arxiv 2510.22670).
- **D-03:** Search still operates over **deferred tools only** (preserve the `!s.Deferred` filter at `search.go:88`); the `select:Name1,Name2` exact-by-name path stays and resolves **any** registered tool by name (unchanged contract).
- **D-04 (research-it):** Pick the BM25 implementation in `plan-phase`/`research` — a small vetted Go BM25 lib vs a compact in-house ranker (tool set is tiny; a self-contained tokenizer + BM25 scorer is plausible within the ≤600-LOC/file rule and avoids a dependency). This is an implementation choice, not a user decision.

### Result cap
- **D-05:** **Top-K cap** via a new optional `max_results` arg on `tool_search` (default **5**, Anthropic/Claude-Code parity). Reject `max_results == 0`. BM25 rank selects the top-K. Keyword/free-text queries are capped; **`select:` stays uncapped** (explicit direct-load by name).

### MCP namespacing
- **D-06:** Bridged MCP tools are namespaced **`<server>__<tool>`** (double-underscore), e.g. `github__create_issue`. Convergent standard: MCP SEP-993, Claude Code SDK (`mcp__github__list_issues`), MetaMCP. `__` is the delimiter precisely because `/` and `.` are invalid in LLM tool-names and single-underscore is ambiguous when a server name contains `_` (nanobot's footgun). `Mount`/`Bridge` take the **server/namespace name** as input and apply the prefix.
- **D-07:** Apply Codex-style hardening to the namespaced name: **sanitize to `[a-zA-Z0-9_-]`**, **64-byte cap**, and on collision append a short hash suffix (namespace-first, then tool-name). Keep the existing all-or-nothing `Mount` collision refusal as the outer guard; namespacing is also a malicious-shadowing mitigation (vulnerablemcp.info tool-name-collisions).
- **D-08:** Low blast radius — no production caller mounts MCP yet, so only `internal/agent/mcptools/bridge_test.go` assertions change (legitimately, behavior changed). Native built-in tool names are NOT renamed in 08.1.

### Scope extras (both in)
- **D-09:** **Tool-categories orientation** is generated **dynamically inside the `tool_search` tool's `Description`** (Codex `tool_search_spec.rs` pattern: "You have access to tools from the following sources: …"), auto-derived from the mounted tools/servers. It does **NOT** go in `SystemPrompt` (`prompt.go` stays byte-stable). The `tool_search` Description becomes registry-derived; since the Registry is immutable for an agent run (`spec.go:48-53`), this stays turn-stable and cache-safe — it only changes when the mounted set changes.
- **D-10:** **≥1-non-deferred fail-closed guard.** Add a registry validation (run at build/boot) that errors if zero non-deferred tools exist (excluding `tool_search` itself), mirroring Anthropic's hard 400 (`"At least one tool must be non-deferred"`). Encode structurally that `tool_search` can never defer itself (Codex excludes its search tool from deferral by construction). De-facto already true today (`text_response`/`ask_user`/`current_time`/`tool_search`); 08.1 makes it enforced.

### Claude's Discretion
- BM25 hyperparameters (k1/b), tokenizer details, exact field weighting (name > description > args), and whether to memoize the per-tool search documents at registry-build time.
- Exact signature shape for passing the namespace into `Bridge`/`Mount`.
- Where the ≥1-non-deferred guard is invoked from (registry constructor vs an explicit `Validate()` called at boot in `cmd/aura`).
</decisions>

## Existing Code Insights

### Reusable Assets
- `tools.Registry` (`spec.go:48`) — immutable for an agent run; iterate `All()`/`Get()` for both indexing and `select:` resolution. Immutability is what makes the dynamic `tool_search` Description cache-safe (D-09).
- `tools.NewResult(ctx, ...)` — already used by `Execute` (`search.go:68`) for spill/preview; the BM25 result rendering keeps routing through it (large multi-spec selects page via the sidecar).
- `Registry.Render()` alphabetical-by-Name ordering (`manifest.go:39`) — keep as the cache-stability invariant after namespacing renames.
- `firstLine()` (`bridge.go:126`) — MCP summary extraction; reuse when building namespaced bridged specs.

### Established Patterns
- Deferred-tool pattern (`spec.go` package doc): big tools `Deferred:true` show Name+Summary only; `tool_search` is the always-visible hook. 08.1 must NOT change which tools are deferred — only how they're searched/named.
- Manifest ordering is cache-poisoning-sensitive (memory `reference_aura_cache_poisoning_sites_2026-05-27`): any reshuffle busts the OpenRouter implicit cache. BM25 ranking affects only `tool_search` *output*, never `Render()` manifest order — keep that separation.
- `Mount` is all-or-nothing on collision (`bridge.go:99-121`) — namespacing slots in *before* the collision check (prefix first, then detect residual collisions, then hash-suffix per D-07).

### Integration Points
- `tool_search` is registered non-deferred in the registry wiring (`cmd/aura/main.go` / `chat.go`) — the ≥1-non-deferred guard (D-10) hooks in at registry build / boot there.
- `mcptools.Mount` callers: currently none in production (seam retained-unmounted) → namespacing change is low-risk; only `bridge_test.go` assertions update.
</code_context>
