## Adopted Decisions

- Phase07F will not introduce a new canonical store. The canonical wiki
  metadata remains the Markdown frontmatter parsed by `internal/wiki`.
- The first implementation slice is metadata promotion through existing
  retrieval paths: `wiki.Page` -> `loadWikiDocuments` metadata -> SQLite/Qdrant
  result -> `search_memory` output.
- `wiki_documents` can keep its current FTS5 schema because the `metadata`
  column already stores a JSON object and the Qdrant payload already accepts
  string metadata.
- LLM-visible output should stay compact. The tool should emit trust tokens,
  not raw frontmatter blocks.
- Single-page wiki reindex must not call the full rebuild path when the Qdrant
  collection is warm. The live write path needs direct page upsert semantics.

## Rejected Or Deferred Decisions

- No wiki write-governance redesign, destructive approval policy, or memory
  promotion flow in Phase07F. Those remain Phase05/Phase06/Phase09 concerns.
- No GraphRAG algorithm/ranking/community-report implementation in Phase07F.
  This slice only gives later graph retrieval the metadata it needs.
- No migration that rewrites all wiki pages. Existing pages are parsed on index
  rebuild and validated by current wiki code.
- No new graph database or Qdrant metadata authority.
- No live mutation of user wiki pages for the benchmark; fixtures must use
  disposable temp wiki directories or live probe cleanup.
- No collection-wide Qdrant delete/recreate for ordinary page writes. Full
  rebuild remains an operator/startup path.

## Missing Source Questions

- Whether a later GraphRAG slice should use frontmatter trust metadata for
  ranking, filtering, or warnings is deferred. Phase07F only makes those fields
  available.
- Whether prompt-version drift should trigger automatic page repair or a
  proposal queue item is deferred to a later wiki maintenance/governance slice.
