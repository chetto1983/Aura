* Swarm uses PER-ROLE MaxToolCalls (1-5 range, see internal/swarm/plan.go:245
  roleMaxToolCalls and internal/swarmtools/tools.go:427 roleMaxToolCalls).

  {"reply": str, "elapsed_ms": int, "llm_calls": int, "tool_calls": int, "tokens": int}
  cmd/probe_chat + cmd/chat depend on it. Diff against current shape before
  committing.

  (today via agent.Task.CompleteOnDeadline). Find the analog in agentruntime
  or add it.

* No new dependencies. No protocol changes. agentruntime.Run today emits
  streaming events but accepts a non-streaming ChatClient; the
  no_stream_client.go wrapper (~30 LOC) lets non-streaming callers reuse it
  without forcing streaming where it wasn't before.

Real root cause of the "3 reduce.go bugs" identified during post-mortem: **none of Ralph's reduce.go logic was actually broken.** The 3 test failures were all symptoms of a single typo in the test helper.

`bigText(n)` was supposed to produce n distinct lines for elision tests but the format string had a literal `XXXX` placeholder instead of `%04d`/`%d`:
- Before (buggy): `b.WriteString("this is test line number XXXX in the output\n")` — produces n IDENTICAL lines
- After (fixed):  `fmt.Fprintf(&b, "this is test line number %04d in the output\n", i)` — n unique lines

With identical lines, `dedupeAdjacent` (correctly) collapsed 20→1 BEFORE `headTail` could elide → no "omitted" marker, no "90 lines omitted", and ratio became 0.05 (massive collapse) instead of ≈1.0 (no truncation possible at head=1000). All three test failures were the same defect surfacing in different shapes.

`TestReduceDedupeAdjacent` correctly used its own builder with identical lines (it WANTS dedupe to fold), so that test always passed — confirming the rest of the pipeline was sound.

Verdict: this is a test infrastructure typo fix, not a test relaxation. `bigText`'s docstring says "n lines of fixed content" — the spirit was n distinct lines per the test designs that depend on it. No production code changed.
