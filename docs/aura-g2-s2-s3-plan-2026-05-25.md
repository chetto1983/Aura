## G2-S2 — `search(action=suggest_questions)` (~180 LOC, SMALL, Codex)

### Purpose

Cold-start UX: when the user opens Telegram with no specific request,
Aura today replies "posso aiutarti con…". With this story she can call
`search(action=suggest_questions)` and return 4–7 pointed questions
that cite specific slugs and explain the signal that surfaced them.
Mirror of graphify `analyze.py::suggest_questions` (`:402-524`), adapted
to Aura's data model.

### Buckets (4 of graphify's 5; bucket 5 deferred to Wave G3)

| # | Bucket | Aura signal | Question template |
|---|---|---|---|
| 1 | AMBIGUOUS edges | `Page.Related[].Confidence == "AMBIGUOUS"` (from G1-S1) OR `proposed_updates` rows with `confidence < 0.55` | "What is the exact relationship between [[A]] and [[B]]?" |
| 2 | Bridge nodes | `Degree(slug)` close to `P99Degree()` AND outbound neighbours span ≥ 2 distinct `NodeMeta.Category` values | "Why does [[X]] connect `<cat-A>` to `<cat-B>`?" |
| 3 | God-nodes with many INFERRED edges | `Store.TopNodes(10)` ∩ count of `Related[].Confidence == "INFERRED"` ≥ 2 | "Are the N inferred relationships involving [[X]] (e.g. with [[Y]] and [[Z]]) actually correct?" |
| 4 | Isolated / under-linked | reuse `internal/wiki/gaps.go::FindGaps()` from G1-S3, take top 3 slugs | "What connects [[A]], [[B]], [[C]] to the rest of the system?" |
| 5 | Low-cohesion communities | gated on Wave G3 clustering — emit only when `Store.Clusters()` exists | (deferred) |

Top-K=7 cap. Deterministic ordering: bucket priority (1 → 4), then
score descending within bucket, then slug alphabetical for stable
output across runs.

### LLM-facing output (markdown capsule, NOT JSON)

Following the slim format convention from commit `0bb00697` and the
markdown capsule from `wiki_subgraph`:

```
4 suggested question(s) for the current wiki:

- [ambiguous_edge] What is the exact relationship between [[davide-marchetto]] and [[albatech]]?
  why: edge tagged AMBIGUOUS in [[davide-marchetto]] frontmatter (confidence < 0.55)
- [bridge_node] Why does [[robot]] connect concept to entity?
  why: degree=8 (P99=7); outbound spans 2 distinct categories
- [verify_inferred] Are the 3 inferred relationships involving [[main-motor]] (e.g. with [[calandra]] and [[stenditore]]) actually correct?
  why: top-degree page with 3 INFERRED-confidence outbound edges
- [isolated_nodes] What connects [[probe-test-012022]], [[probe-v2-012823]] to the rest?
  why: 2 wiki pages with InDegree+OutDegree <= 1
```

This shape is what `wiki_suggest_questions.go::Execute` returns. The
underlying `[]Question` slice stays JSON-marshalable for any internal
caller that wants structured access (e.g. a future dashboard widget).

## G2-S3 — IDF exact-match boost in RRF (~80 LOC, SMALL, Codex)

### Purpose

When the user types literally a slug (e.g. `davide-marchetto`), the
current RRF returns it but NOT always at position 1 — other pages that
mention "davide" in body can outrank the literal slug because the
hybrid fuses three signals each capped at ~0.42. Mirror of graphify
`serve.py::_score_nodes` (`:98-121`) with its 1000 / 100 / 1 three-tier
weighting, IDF-scaled per term.

### Current state (audited)

`internal/storage/search/qdrant_hybrid.go::exactMatchDB` does a
title substring match with diacritic strip and emits Score=1.0,
ScoreExact=1.0 for hits. There is no tier differentiation — a page
whose title is literally the query gets the same exact-channel score
as a page that merely contains the query as a substring. After RRF
normalisation, exact-channel rank-1 → 0.4167 of total, which can lose
to a vector rank-1 + FTS rank-1 combination on a different page.

graphify's pattern: separate the three tiers BEFORE fusion and weight
them by IDF so common terms (e.g. "robot" in a robotics wiki) cannot
beat a rare exact identifier.

### Algorithm (port of `serve.py:98-121`)

1. **Term tokenisation**: split the query into terms via the existing
   `significantSearchTerms()` helper (already strips stopwords +
   normalises diacritics).
2. **IDF per term**, cached in a struct keyed by GraphIndex generation
   count (invalidate on `RefreshPage` / `RemoveNode`):
   ```
   idf(term) = ln(1 + N / (1 + df(term)))
   ```
   where `df(term)` is the count of pages whose normalised slug or
   title contains the term, and `N` is the total page count.
3. **Per-page score** = max-tier contribution per term, summed across
   terms:
   - tier 1 — **exact**: `slug == normalised_term OR title == normalised_term` → `1000 × idf(term)`
   - tier 2 — **prefix**: `slug.startswith(term) OR title.startswith(term)` → `100 × idf(term)`
   - tier 3 — **substring**: `term ∈ slug OR term ∈ title` → `1 × idf(term)`
   - take the strongest tier per term (no double-count).
4. **Replace `exactMatchDB`** with the new scorer. Returns ranked
   results with `Score = tier_score / max_tier_score` (normalised
   to [0,1] so the RRF fuser sees a comparable magnitude).

### Why this beats the current substring match

The literal-slug query case:
- query `davide-marchetto` → exact tier fires → 1000 × idf("davide-marchetto")
- a page that merely mentions "davide" in body → substring tier → 1 × idf("davide")
- Ratio is ~1000× regardless of how strong vector or FTS get → exact-channel rank-1 is always the literal slug.

The non-literal query case (`tell me about davide`):
- All three pages with "davide" in title → substring tier → comparable scores → RRF still does the heavy lifting via vector + FTS as today.

So the change is conservative: it only changes ranking when the user
typed a literal identifier; broader queries behave identically.

### Acceptance criteria

1. **Tier tests** (all on synthetic 5-page fixture):
   - `TestExactMatchTier_ExactSlugWins`: query `davide-marchetto`
     against `{davide-marchetto, davide-notes, work-davide, ...}` →
     `davide-marchetto` is at position 0 with score ≥ 0.9.
   - `TestExactMatchTier_PrefixBeatsSubstring`: query `robot` →
     `robot-*` slugs at top, pages mentioning "robot" in title-mid
     position below.
   - `TestExactMatchTier_IDFDownweightsCommonTerms`: query
     `robot collaborative` on a wiki where every page mentions
     "robot" → the page literally named `collaborative-robot` wins
     by IDF on the rare term.
2. **IDF cache**:
   - `TestIDFCache_InvalidatesOnPageWrite`: precompute IDF, add a
     new page, query again → cache miss + recompute.
   - `TestIDFCache_StableAcrossReads`: two queries with same terms →
     second call uses cached IDF (assert via instrumentation counter).
3. **Back-compat**: existing `TestSearchHybrid_*` tests in
   `wiki_hybrid_test.go` stay green. The exact-channel score is
   still ≥ 0 for substring hits, only the relative magnitude changes.
4. **RRF normalisation invariant**: the per-channel `ScoreExact`
   value reported on each `Result` is now the tier-derived score
   normalised to [0,1] — the normalisation constant from commit
   `13d004d3` still applies, so the fused total Score still maxes
   at 1.0.
5. **No regression on `TestMergeHybridResultsNormalisesScoreToUnit`**
   (commit `13d004d3`): the test asserts a synthetic top-1-everywhere
   hit produces Score=1.0; this still holds because the tier scorer
   feeds rank-1 to the RRF fuser exactly as before.
6. **Live probe**: ask Telegram exactly `davide-marchetto`; the
   `search(action=search, query="davide-marchetto")` underlying call
   returns `[[davide-marchetto]]` at position 0 with score ≥ 0.85.

### Risks

- **IDF on 45 pages is low-signal**. The cache and machinery are
  ready for scale but the immediate impact is on the EXACT-tier
  (1000×) win, not the IDF weighting nuance. That's fine — the

  pin the counter behaviour explicitly.
- **Test fixture explosion**. The 4 new tier tests are small (≤30
  LOC each) and reuse the existing `writeTestMDPage` helper from

- Deep-refactor on touch (lefthook gates per commit).

  surfaces (G2-S2 returns markdown; G2-S3 is internal to the search

  bridge-nodes / isolated-node detection runs (G2-S2). G2-S3 doesn't
  apply god-node filtering — it ranks every wiki page on its title
  match.

  `CLAUDE.md`) for live-probe acceptance, not just unit tests.

  `SuggestQuestionsCallsTotal` and an `ExactMatchTierHitsTotal{tier}`
  histogram-like counter so the dashboard can show whether the
  new surface is being used.
