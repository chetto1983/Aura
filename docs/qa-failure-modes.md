# Failure Modes — 2026-05-18 — git_head: 3652fdf2

Aura is a single Go binary with seven first-class network/runtime dependencies and a per-turn agent loop with its own internal failure surface. This document is a static-analysis inventory: every external dep is mapped to its transport, health-probe code path, what happens on failure, and the user-facing impact on Telegram or web chat. The internal modes are the per-turn loop conditions in `internal/agent/loop.go` plus the few sentinel paths Aura explicitly classifies (`internal/llm/classify.go`, `internal/agent/phantom_guard.go`). Cells flagged `STATIC-ANALYSIS-INSUFFICIENT` are ones a code read cannot prove without a live probe of the running container.

Code references use `file:line` and reflect the tree at `3652fdf2`.

## Internal failure modes

| internal mode | trigger | code path | user-visible impact |
|---------------|---------|-----------|---------------------|
| `context.DeadlineExceeded` mid-turn (`MaxElapsed`) | Per-turn wall clock exceeds `opts.MaxElapsed` (default `5 * time.Minute`, `loop.go:211`). The `time.Since(start) >= MaxElapsed` check fires at the top of the next iteration. | `loop.go:262-274`: sets `stats.MaxElapsedHit`, `StopReason = "max_elapsed_hit"`, calls `finalAnswerOnBudget(lastToolResult)`, appends as assistant message, returns. The deadline-mid-Chat path is at `loop.go:323-335`: if `CompleteOnDeadline && globalToolCallsExecuted > 0`, returns `interruptedAssistantContent` instead. | Telegram user gets a short canned recap built from the last tool result, or `"Agent interrupted before a final answer: context deadline exceeded. Last tool result: ..."` — both expose internal scaffolding. STATIC-ANALYSIS-INSUFFICIENT: live probe needed to gauge how often this actually fires for real users at the 5-min cap. |
| MaxIterations hit (per-turn cap, NOT MaxToolCalls) | `iteration >= opts.MaxIterations` falls out of the `for` loop. Default raised from 50→100 ceiling (`loop.go:207`, `MaxIterationsCeiling`). Compose sets `AURA_AGENT_LOOP_MAX_STEPS=50` per turn. | `loop.go:261,629-647`: sets `stats.MaxIterationsHit`, `StopReason = "max_iterations_hit"`, logs warning, optionally tries `finalizeAnswerAfterBudget` (one final tool-less LLM call, `loop.go:649-679`) when `AllowNoToolFinalization`, otherwise falls back to `finalAnswerOnBudget(lastToolResult)`. | User receives a wrap-up answer that may be a summary of the last tool result. The LLM is forced to stop calling tools, so a multi-step research workflow stops mid-task. STATIC-ANALYSIS-INSUFFICIENT: live probe to confirm whether the wrap-up message acknowledges the cap or pretends to be complete. |
| empty LLM response after a tool call | LLM returns `HasToolCalls=false` AND `strings.TrimSpace(resp.Response.Content) == ""`. | `loop.go:353-385`: substitutes `finalAnswerOnBudget(lastToolResult)`. Also classified via `llm.ErrEmptyOutput` as `BucketContent` (`classify.go:90-92`), triggering up to 3 staircase-temp retries via `RetryClient.Stream`. | First fires retries silently; if still empty, user sees a terse recap of the last tool result with no original LLM contribution. Looks like a non-sequitur reply on Telegram. |
| LLM tool-call arg parse error | Underlying parser detects malformed JSON arguments. Sentinel `llm.ErrMalformedToolCall` (`classify.go:30,93-95`) → `BucketContent`. The OpenAI streaming accumulator (`client.go`) buffers tool-call fragments so consumers never see partial JSON, so this fires only when the fully-accumulated payload is itself malformed. | `retry.go:97-107`: up to 3 retries with staircase temperatures + validation nudge appended as a system message. If exhausted, error bubbles up; loop's `client.Chat` error handler (`loop.go:322-336`) returns the canned "Sorry" reply. | User sees no failure on the retry path. After exhaustion: `"Sorry, I couldn't process your message. Please try again."` |
| sandbox unavailable (Python `execute_code`) | `NewExecuteCodeTool` / `NewExecuteShellTool` are constructed with a nil `sandbox.Executor` (e.g. `SANDBOX_ENABLED=false` or sandbox manager failed to start). Constructor returns nil (`exec.go:51-54,57-65`) so the tool is never registered. | When the LLM nonetheless emits a call for an unregistered tool, the executor's allowlist check at `executor.go:171-175` returns a fatal `FormatFatalToolError("tool %q is not allowed for this agent")` tool result. At call-time inside `Execute` if the manager surface is healthy but the process fails: `exec.go:168-175` returns `"sandbox execution failed: ..."` or `"execution failed (exit=N): <stderr>"`. | LLM receives a tool error and either rephrases without code or apologizes. User sees an answer that explicitly avoids running code. |
| capability deny (identity authorizer) | `authorizeToolExecution` invoked with a tool that has `RequiredCapability()` returning non-empty (e.g. `CapabilitySwarmSpawn` for `run_aurabot_swarm`) and the `identity.Authorizer` in ctx returns `DecisionDeny`. | `registry.go:324-349`: returns error `tool %q is not authorized for capability %q`, wrapped via `identity.ErrUnauthorized`. Executor maps it to a non-fatal tool result. Decision is logged with reason (`store.go:718` writes a denied row). | LLM gets a `Error: tool "<name>" is not authorized for capability "<cap>"` tool result; usually falls back to explaining the limitation. User sees something like "I don't have permission to do that here." |
| phantom tool detection | LLM returns no tool call BUT references a registered tool's name with a past-tense first-person verb within 120 chars (`phantom_guard.go:90-123,131`). Run-pair guard: tool name must NOT already be in `calledThisTurn`. | `loop.go:358-377`: stats `PhantomToolDetections++`; if `state` implements `PhantomCorrector`, adds the original phantom message as the assistant turn and injects `CorrectionText` as a user-side correction nudge, then `continue` to retry the LLM. Capped at `RetriesAllowed()` per turn. Subsequent corrected response increments `PhantomToolCorrected` (`loop.go:387-395`). | User briefly sees the phantom reply (it has already been streamed via Telegram edits ~600 ms throttle), then the loop retries and re-edits the message with the corrected version. STATIC-ANALYSIS-INSUFFICIENT: needs live probe to confirm whether Telegram's edit pipeline replaces the phantom text cleanly or leaves both visible. |
| duplicate tool call (dedup) | Two calls in the same batch with identical `(name, arguments)` (in-batch) OR a call whose `duplicateToolCallKey` matches `seenToolCalls` from a prior iteration AND the prior result is not a retryable `Error:`-prefixed string (`loop_dedup.go:16-22`). | `loop.go:430-468`: identifies via `DedupeToolCalls`; in-batch dup → added to `duplicateToolCalls`, given a stub via `duplicateToolResult` (`loop_dedup.go:24-29`). Cross-iteration dup → same stub. `MaxCallsPerTool` cap → `maxCallsToolResult`. Global `MaxToolCalls` cap → `budgetCapToolResult` + sets `finalizing=true` (`loop.go:583-594`). | Telegram user never sees the dup directly; the LLM sees a synthetic tool result reminding it that "You already called X with these exact arguments earlier this turn. The result is above — read it instead of calling again." Loop continues with the cached evidence. |
| LLM rate-limited (429) | `*llm.APIError{StatusCode:429}` or error message containing "rate limit" / "overloaded". | `classify.go:101-102,121-124`: classified as `BucketTransient`, retryable. `RetryClient.Stream` retries with jittered exp backoff (base 1 s, max 30 s, ratio 0.5, up to `MaxRetries`=5 default — `retry.go:38-47`). | User sees a delay (silent — Telegram shows "typing..." or the partial streamed message stalls) for up to ~30 s per retry, then either the full answer or the canned "Sorry, I couldn't process your message" after exhaustion. STATIC-ANALYSIS-INSUFFICIENT: live probe to time the worst-case wall-clock under sustained 429s. |
| LLM transient network error (connection refused/reset) | `net.Error` with `Timeout()==true`, or generic transport error. Default classify rule treats unknown errors as transient (`classify.go:131-132`). | Same path as 429: `BucketTransient` → up to 5 retries with jitter. `context.DeadlineExceeded` also lands here (`classify.go:82-84`). | Identical UX to the 429 path: silent delay, then either success or the canned fallback. The user has no direct way to distinguish the two. |
