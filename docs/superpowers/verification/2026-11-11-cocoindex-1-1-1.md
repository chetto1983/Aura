# cocoindex 1.1.1 in the ingestion sidecar

Date: 2026-11-11. Dependabot opened #223 (`cocoindex[amazon_s3,postgres]` 1.0.26 → 1.1.1 in
`docker/aura-ingest/requirements.txt`). The operator chose to measure what it writes before the merge
("Procedi con l'opzione a per cocoindex"), not to merge on CI alone.

**Verdict: 1.1.1 writes the same ArcadeDB schema as 1.0.26 and continues from a 1.0.26 state.**
- The ingestion suite passes on both, test for test.
- The schema in every database the suite leaves behind is identical: types, properties, indexes and
  record counts.
- A CocoIndex state written by 1.0.26 is resumed by 1.1.1 with nothing re-extracted or re-embedded,
  and a later modification and deletion are reconciled exactly as 1.0.26 does.

## Setup

- **The stack.** `docker compose up` of `arcadedb` (26.11.1, the compose pin) and `aura-llama-embed`
  (`server-b11960`, CPU, the validated EmbeddingGemma Q8_0 from `scripts/fetch_embedding_model.sh`),
  with CI's environment and `.github/compose.ci-cache.yaml`, as the `Ingestion sidecar` job does.
- **The images.** `docker/aura-ingest/Dockerfile` built twice from master `a0a3f9a3f`, once as is and
  once with the #223 line, and checked inside each image: `cocoindex` 1.0.26 and 1.1.1.
  - The session's network goes through an intercepting proxy. The builds used a local copy of the
    Dockerfile that installs that proxy's CA and fetches apt over HTTPS. Nothing else changed, and
    the copy is not in the repository.
- **The suite.** The `make ingest-test` recipe, run against each image.

## Results

| Measure | 1.0.26 | 1.1.1 |
|---|---|---|
| `services/ingest/tests` | 273 passed | 273 passed |
| Databases left by the suite, snapshotted before each drop | 11 | 11, identical |
| Indexes per database | 22 | 22, identical names, types, properties, uniqueness, null strategy |
| Largest database | 20,001 records | 20,001 records |

- **How the schema was read.** `tests/disposable.py`'s `drop()` was wrapped, in a copy outside the
  repository, to save each database's types with their properties, indexes and per-type record
  counts just before dropping it. The bucket suffixes ArcadeDB appends to index names were
  normalized.

## A 1.0.26 state resumed by 1.1.1

Two text objects went through `ingest.tests.space_driver`, the production indexing path with the
objects passed on the command line instead of read from Garage. Each run used a persistent
`COCOINDEX_DB` and its own disposable database.

| Pass | Control (1.0.26 then 1.0.26) | Upgrade (1.0.26 then 1.1.1) |
|---|---|---|
| First, 1.0.26 | 2 extracted, 4 embed requests | 2 extracted, 4 embed requests |
| Second, unchanged objects | 0 extracted, 0 requests | 0 extracted, 0 requests |
| Rows after the second pass | Passage 2, IndexedDocument 2 | Passage 2, IndexedDocument 2 |
| Third: one object changed, the other deleted | 1 extracted, 2 requests | 1 extracted, 2 requests |
| Rows after the third pass | only the changed object, with its new text | only the changed object, with its new text |

## Found on the way: usage tracking

Both versions send a usage event at startup: `cocoindex_core::telemetry: usage tracking event init`,
to `https://cocoindex.gateway.scarf.sh/python-<version>`. It failed here only because the session's
network refused it.
- **Not new in 1.1.1.** 1.0.26 sends the same event.
- **The opt-out exists in both:** `COCOINDEX_DISABLE_USAGE_TRACKING`, present in `core.abi3.so`.
- **Aura did not set it.** Neither `compose.yaml` nor the Dockerfile set it, so a sidecar with
  outbound network reported its use. On the operator's decision, `docker/aura-ingest/Dockerfile`
  now sets `COCOINDEX_DISABLE_USAGE_TRACKING=1`.
- **The value is enough.** Any value except `""` and `"0"` disables tracking
  (`rust/core/src/telemetry/mod.rs`). Every `space_driver` pass above ran with it set to `1`, and
  none of their logs, on either version, has the attempt. Each suite run without it has one.

## How to reproduce

Nothing below is committed tooling. Each step is a command or a small edit to a throwaway copy.

1. **Bring up the stack** with CI's environment (the `Ingestion sidecar` job's `env` and the workflow's
   top-level `env`), then run `docker compose up -d arcadedb aura-llama-embed`. The model goes in
   with `scripts/fetch_embedding_model.sh` and `docker cp`, as in that job.
2. **Build both images.**
   - `make ingest-image` builds the 1.0.26 image; tag it `aura-ingest:1026`.
   - Change the `cocoindex[amazon_s3,postgres]==` line in `docker/aura-ingest/requirements.txt` to
     `1.1.1`, build again, tag it `aura-ingest:111`, then revert the line.
3. **Run the suite.** Use `make ingest-test`'s `docker run` line with the image tag swapped.
4. **Take schema snapshots.**
   - Copy `services/ingest` and, in the copy's `tests/disposable.py`, make `drop()` first save to a
     mounted `/snap` directory:
     - `select name, type, properties from schema:types`;
     - `select from schema:indexes`, keeping `name` with its `_<digits>` bucket suffix replaced,
       `indexType`, `typeName`, `properties`, `unique` and `nullStrategy`;
     - `select count(*)` per type.
   - Mount the copy in place of `services/ingest`, with `-v <dir>:/snap`, and run step 3 once per
     image on a clean server. Compare the JSON files in order.
5. **Upgrade the state.**
   - Run `python -m ingest.tests.space_driver <db> 'a.txt=<text>' 'b.txt=<text>'` in
     `aura-ingest:1026`, with `COCOINDEX_DB` on a mounted directory.
   - Run the same command in `aura-ingest:111` on the same directory and database.
   - Count the `[extract] ` lines and the `REQUESTS` line, then repeat with `b.txt` changed and
     `a.txt` left out.
   - The control is the same sequence with `aura-ingest:1026` both times.

## What this does not show

- **Not the lab VM,** and not the operator's corpus or a real Garage bucket outside CI's
  reconciliation job.
- **No real model and no agent turn.** The release gate's LLM phases did not run.
- **Not a state written by an older 1.0.x, nor a large state.** The upgrade was measured from a
  1.0.26 state of two objects.
- **Not the extractor matrix or OCR paths with 1.1.1.** The suite and `space_driver` are what ran.
- **Not 1.1.1's release notes item by item.** The comparison is of what it writes, not of every
  changed API.
