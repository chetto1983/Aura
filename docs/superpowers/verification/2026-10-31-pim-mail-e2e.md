## A1, settled by reading the providers (the fork at `7797d52`)

- **M365.** `CreateEventAsync` posts an `Event` with `Attendees` and an HTML `Body` through
  Microsoft Graph. Graph sends invitations for an event created with attendees by default, so on
  an M365 account an invitation with the model's text leaves the appliance.
- **Google.** `Events.Insert` sets no `SendUpdates`, and Google's default is not to email guests.
  A guest on Google can still see the event on their own calendar.
- **CalDAV (`dav`).** The PIM writes the ICS with the attendees, over HTTPS only
  (`DavHostPolicy.IsAllowedHost`). Whether an invitation is sent is the server's implicit
  scheduling (RFC 6638): iCloud, Fastmail and Nextcloud do it.
- **IMAP, ICS, JSON.** These cannot create events, as measured above.
- **A lever that exists today, with no Aura change.** Every account in the PIM carries
  `permissions`, all true by default and intersected with the provider's abilities
  (`Models/AccountPermissions.cs`, `Services/AccountCapabilities.cs`). An operator stops A1 for an
  account by setting `"permissions": {"calendarWrite": false}`.

## What this does not show

- **A model reading the mailbox.** The agent did not run: there is no model key in this container.
  The briefing's own run is the lab VM's acceptance.
- **Aura's managed mount of the PIM.** The tier talks to the sidecar with the test issuer's tokens,
  as CI does, not through the daemon's OAuth server and bridge.
- **M365, Google and CalDAV providers.** None was exercised; A1 for them is read from the code.
- **TLS.** GreenMail ran plain IMAP/SMTP; the provider connects with `SecureSocketOptions.Auto`.
