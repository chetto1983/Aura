## Key findings

- **agent_note is a real bug, not a transport flake.** agent-note-roundtrip is the only baseline FAIL whose mismatch is a DB-truth assertion (agent_notes row missing after set, conversation_id=chat-cli), and the unit suite (agent_note_test.go) passes - meaning Execute writes correctly when called directly but the production wiring on conversation_id=chat-cli is broken. P0 fix candidate.
- **Sandbox-exec is the largest E2E blind spot.** execute_code, execute_shell, subagent_dispatch, run_aurabot_swarm, spawn_aurabot all sit in the sandbox-exec category with zero probe cases. Five P0 entries from a single category - any regression in sandbox plumbing ships silently through cmd/probe_chat.
- **web E2E is reply-only.** web-fetch-summarize-context-engineering greps r.Reply for context/agent/tool and length over 300. It passes when the model hallucinates a plausible summary without fetching. Needs an assertion that the actual fetched body landed on disk or in the tool-result manifest.
- **Lint debt is essentially zero inside tool packages.** 57 of 59 issues are outside internal/agent/tools/*; the only 2 inside are unused legacy helpers in source.go (readSourceMarkdown, readOriginalContent) - dead-code deletion candidates, not behavioral risk.
- **request_dashboard_token has no E2E despite emitting a secret out-of-band via Telegram.** The unit test covers happy-path + revoke-on-send-failure, but no probe verifies the round-trip: token row in api_tokens (SHA-256 hashed) + actual Telegram delivery + response sanitization. P1.
- **MCP coverage is structural only.** mcp_server_tool Execute is unit-tested against a fake client; no probe verifies an actual JSON-RPC roundtrip against any of the configured upstream servers. Acceptable for now (operator-dependent), but tag P1 since the dynamic registration path is a known phantom-tool source.
