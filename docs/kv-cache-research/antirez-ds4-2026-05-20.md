# antirez/ds4 — Intel

**TL;DR.** `antirez/ds4` ("DwarfStar 4") is a from-scratch C/Metal/CUDA inference engine that runs a **single** model (DeepSeek V4 Flash, 284B MoE, released April 2026) on local hardware (96–128 GB Apple Silicon, with a CUDA path for DGX Spark). Crucially, it is **not** a Redis-style data-structure write-up — it is one of the most production-relevant references in the wild for **KV-cache-aware prompt-caching at the server boundary**, including (a) hybrid RAM+disk KV cache keyed by SHA1 of the rendered byte prefix, (b) a per-tool-call "exact DSML replay" map that solves the JSON-round-trip prefix-drift problem, and (c) a hard-won bug report (issue #62) documenting exactly the failure mode Aura would hit if she naively turned on prefix caching for a tool-calling agent loop. It is **highly relevant** to Aura's prompt-cache effort, but as a *teacher of patterns and pitfalls*, not as code to vendor — Aura speaks the OpenAI/Anthropic protocol to upstream LLMs, she does not host the inference engine.

The fact that antirez chose to **ship the agent loop in-process** (no socket boundary between agent and inference) is itself a design statement — and it is the architectural choice that *enables* the most interesting cache patterns below.

## Relevance to Aura KV-cache

DS4 is highly relevant **as a reference design and failure-mode catalogue**, not as code Aura can lift. Aura is a *client* of upstream LLMs (OpenAI-compatible HTTP, Anthropic, etc.), so she lives on the **other side** of the wire from DS4's KV-cache logic. But every pattern below maps directly to a decision Aura must make if/when she wires up Anthropic prompt caching or any provider-side context cache.

### Direct lift-able patterns

1. **Hybrid RAM + disk KV cache, keyed by SHA1 of the rendered byte prefix.**
   - DS4 hashes the *rendered* (post-template, post-tokenization-input) byte stream, not the logical conversation. Aura's takeaway: when computing prompt-cache keys for the wiki-injection or skills-overlay payloads, hash the **rendered post-overlay byte stream**, not the conceptual "system + history + tools" tuple. Logical equality is not byte equality.
   - File layout: 48-byte header (magic `"KVC"`, version, quant bits, created/last-used timestamps, token count, hit count), then rendered text + payload, then optional tool-ID map prefixed `"KTM"`. Aura's prompt-cache audit log could borrow this header shape if she ever caches anything to disk (e.g. embedding cache headers already do something similar).
   - Eviction trigger points: cold (after first long prompt stabilises), continued (at ~10k aligned frontier), evict (before unrelated session displaces live), shutdown. Aura's session archive could use the same four moments to decide when to snapshot conversation context.

2. **"Exact DSML replay" for tool calls — the single most important pattern.**
   - The bug DS4 solves: clients (Aura is one!) round-trip tool calls through normalized OpenAI/Anthropic JSON. If the server re-renders that JSON into the model's native tool format (DSML), the bytes will *almost* match what the model originally sampled — but not exactly. Single byte of drift = KV cache miss = full re-prefill = latency cliff.
   - DS4's fix: server hands each tool call an **unguessable tool ID**, remembers `tool_id → exact sampled DSML block` in a bounded map (default 100k IDs), and when the client returns the result, the renderer substitutes the original sampled bytes back in. Result: cache hits survive multi-turn tool sessions.
   - **Aura analogue**: when Aura caches a conversation prefix (Anthropic `cache_control` blocks, OpenAI prefix caching), the *tool-call argument JSON* the model emitted must be returned verbatim in the next turn's history, not re-serialized through Aura's own JSON formatter. Today Aura archives `tool_calls` JSON in the `conversations` table — verify the column stores the model's literal bytes, not a `json.Marshal` round-trip of a parsed struct, or prompt caching will silently miss.
   - **Aura analogue (deeper)**: if Aura ever ships her own inference path (Wave-N), the tool-ID-map pattern is the canonical solution. File it.

3. **Mixed-temperature sampling within a single tool call.** DS4 uses `temperature=0` for DSML *structure* (tags, headers, punctuation) and normal sampling for *argument payloads*. Aura already does deterministic writes for wiki (`temperature=0`); DS4 confirms the principle generalises: protocol scaffolding wants determinism, content wants entropy.

4. **Cheap-then-expensive prefix check.** Server tries cheap token-ID prefix compare first, falls back to comparing **rendered prompt bytes** against decoded checkpoint bytes. Aura's prompt-cache validator (if she builds one) should mirror this two-tier check.

5. **`--kv-cache-reject-different-quant`** — DS4 will refuse to reuse a Q2 cache for a Q4 request. Aura's analogue: if she caches per-model-id, **never share cache across model upgrades**, even within a family (Claude 4.6 → 4.7). Treat the model ID as a hard cache-partition key.

### Failure mode Aura would hit verbatim (issue #62)

Issue #62 documents: long tool-use session → final assistant text turn (`finish=stop`) → next short user message → **131-second re-prefill** because re-tokenizing the rendered history produces different token IDs than the live checkpoint, so the 56k-token live snapshot is bypassed in favour of a much older 4k disk snapshot. Root cause: tool-call turns are canonicalized after `finish=tool_calls`, but **final assistant text is not canonicalized**, leaving the live checkpoint holding raw sampled tokens that don't match a re-tokenization of the same string.

**Aura implication**: when Aura archives an assistant turn and replays it on the next request, the bytes the upstream LLM sees on round N+1 must be byte-equal to what it sampled on round N. If Aura runs *any* transformation on assistant text between archive and replay (whitespace normalization, mojibake fixing, markdown re-rendering, prompt-overlay re-injection upstream of the cached prefix), she will hit DS4's bug — except the latency penalty hits Anthropic's cache invalidation logic, not a local re-prefill.

**Concrete check for Aura's codebase**: audit `internal/conversation` and the agent loop's history-rebuild path for any string-level transformation between `archive` and `replay`. If found, that's the cache killer.

## Spillover value

Beyond KV-cache lessons, DS4's relevance to other Aura subsystems:

- **`gguf-tools/`** — antirez ships a separate `gguf-tools` subdirectory with utilities for poking at GGUF model files. Aura's `aura-init-models` (Wave 2.10) currently fetches `embeddinggemma` GGUF as a blob; if/when she wants to introspect or repair GGUF files in CI (verify quantization, check tensor shapes), `gguf-tools` is reference code in pure C. **Low priority** — Aura doesn't currently need this.
- **Asymmetric quantization recipe** (Q2 routed-MoE experts + 8-bit shared components) — relevant only if Aura ever quantizes her own models. Not in scope.
- **`dir-steering/`** — likely directory-based prompt/policy steering for the agent. Worth a future skim if Aura wants ideas for per-conversation policy injection beyond the current 4-overlay system, but **no direct connection** to current architecture.
- **Server endpoint shape** — DS4 exposes `/v1/chat/completions`, `/v1/responses`, `/v1/messages`, `/v1/completions`. This confirms the "speak both OpenAI and Anthropic protocols" pattern as canonical. Aura's LLM client is OpenAI-compatible-only; if Anthropic-native is ever needed (e.g. for true `cache_control` blocks), DS4 server.c is a reference impl.

**Nothing in DS4 directly maps to Aura's wiki graph, embedding cache, or conversation archive beyond the header-format aesthetic.**

## Verdict

**STUDY.** Aura should not vendor DS4 code (wrong layer — DS4 is an inference *server*, Aura is an inference *client*), but the README's KV-cache section and issue #62 are required reading before Aura turns on any provider-side prompt caching. The "exact tool-call byte replay" pattern is the single most important takeaway and should drive an audit of how `conversations.tool_calls` is serialized/deserialized in `internal/conversation`.
